# foundry-protocol：Foundry 核心工作規範

本文的每一條都是「可以判定過或不過」的規則，不是原則宣言。與第 2 層角色 skill 衝突時，以本文為準；與使用者的即時指示衝突時，停下來問（見第 4、6 節）。

## 1. 工單骨架

每張 Paperclip issue 的 description 一律用以下四段，順序固定、標題固定，缺任何一段就是不合格工單，接單者有權退回：

```
**Inputs**
- （執行本單需要的每一項素材：檔案路徑、repo、文件、前置工單編號）

**Outputs**
- （本單完成後會存在的具體交付物：檔案路徑、文件、工單、報告）

**驗收標準**
1. （每條都是可驗證的敘述，見下方判準）

**未決事項**
- （沒有就寫「無」；有就逐條列出）
```

### Inputs 的判準

- 每一項都**實際可存取**：路徑打得開、工單編號存在、文件讀得到、憑證拿得到。
- 接單者開工的第一步就是逐項確認可存取；有任何一項打不開，立即把工單轉 `blocked`，並在留言註明是哪一項、需要誰提供。
- 不合格寫法：「參考之前的討論」「沿用大家知道的那份設定」。
- 合格寫法：「`docs/features/auth/PRD.md`」「工單 MYL-2 的產出 repo」。

### Outputs 的判準

- 每一項都是**完成後可以指著看的東西**：檔案、文件、工單、部署結果、報告。
- 動作描述不是 Output。「研究可行性」不合格；「`docs/xxx.md` 可行性評估文件」合格。
- 審查時逐項核對 Outputs 是否存在，缺一項就不能結案。

### 驗收標準（AC）的判準

- 每條 AC 都能回答「**怎麼驗**」：跑哪個指令、開哪個頁面、檢查哪個檔案的什麼內容，驗完能明確判定過或不過。
- 不合格寫法：「程式碼品質良好」「使用者體驗流暢」。
- 合格寫法：「`npm test` 全數通過」「登入頁在未填 email 時送出，顯示『請輸入 email』錯誤訊息」。
- AC 是結案的唯一依據：驗證時逐條核對，並附上證據（指令輸出、截圖、檔案連結）。

### 未決事項的判準

- 誠實列出所有還沒有答案的問題；沒有就明確寫「無」，不留空。
- **有任何一項未解的未決事項，本單不得進入實作**（見第 2、4 節）。
- 把該問的問題藏起來自己猜、或用「合理假設」帶過，都是違規；正確做法是列出來、發互動卡問。

## 2. 狀態機

直接使用 Paperclip 的六個狀態。硬依賴一律用 `blockedByIssueIds` 欄位表達，不用文字描述代替；前置單全部 `done` 之前，本單不得離開 `blocked`。

### `blocked`

- **進入**：有未完成的 `blockedByIssueIds`；或 Inputs 有項目不可存取；或觸發第 4 節 HITL 閘門正在等使用者回覆。
- 進入時必須在留言註明：阻塞原因、解除者是誰、對方做什麼就能解。沒寫解除路徑的 `blocked` 視為不合格。
- 平台限制：Paperclip 的 `unblockDescriptor.owner` 只能填 agent 自己（填別人整筆 PATCH 都不生效）。指望其他 agent 解鎖時，把對方的工單掛進 `blockedByIssueIds` 作一級 blocker，owner 欄位仍填自己、收尾動作寫在 `action`；「解除者是誰」寫在留言即可。（Pilot 卡點 #4）
- **離開**：所有前置單 `done`、Inputs 全數可存取、待答問題已獲回覆 → 轉 `todo`。

### `todo`

- **進入**：四段骨架齊全且各段通過第 1 節判準；無未解阻塞。
- **離開**：執行者領單開工 → 轉 `in_progress`。

### `in_progress`

- **進入**：執行者已逐項確認 Inputs 可存取，且未決事項為「無」或已全數解決。**未決事項還有未解項就開工，視為違規。**
- **離開**：交付物完成且自檢過每一條 AC → 轉 `in_review`；中途遇阻塞或觸發 HITL 閘門 → 轉 `blocked`。

### `in_review`

- **進入**：Outputs 已產出、交接包（見第 3 節）已附在工單上、有明確的審查者或待核准的互動卡。**沒有真實審查路徑不得掛 `in_review`**——「等有人有空看」不是審查路徑。
- **離開**：審查通過 → 轉 `done`；退回 → 轉 `in_progress`，並附具體缺陷清單（不是「再改改」）。

### `done`

- **進入**：AC 逐條有驗證證據，且分支已依第 7 節收尾。**只有宣稱、沒有證據，不得結案。**
- **手冊同步檢查（MYL-12 決議，MYL-32 增訂）**：本單若動到 `docs/handbook/`，結案前必須檢查是否需執行 `scripts/publish-handbook.sh` 同步公開鏡像。該腳本會 push 公開 repo，屬第 4 節「對外發佈」動作，執行前需使用者**當下同意**（除非日後另給常設授權）。已取得同意 → 執行同步並在結案留言附證據；使用者尚未回覆或選擇暫不同步 → 結案留言註明「公開鏡像未同步」與後續處理方式（不因等待同步而卡住結案）。
- 原則上不重開；結案後發現的問題依第 5 節判定退回或開新單。

### `cancelled`

- **進入**：需求不再成立，或被其他單取代（留言註明取代單編號）。取消原因必須寫在留言，不得無聲取消。

## 3. 交接格式

標準流程鏈：**需求（Product Analyst）→ 設計（Tech Lead）→ 工單（Scrum Master）→ 實作（Developer）→ 審查（Code Reviewer）→ 測試（QA）**。每一棒必附的交接物如下；**交接物不齊，下一棒有權直接退回，不開工。**

### 使用者／Product Analyst → Tech Lead

- BRD／PRD（用 `templates/` 的骨架），含已與使用者確認過的驗收條件與優先序。
- 尚未確認的需求點列在文件的未決區塊，不得混進已確認需求。

### Tech Lead → Scrum Master

- HLD／LLD 設計文件，存於 `docs/features/<模組>/`，含技術決策與取捨說明。
- 重大技術決策（選型、架構變更）附 ADR：寫明選項、取捨、結論。

### Scrum Master → Developer

- 合格工單（通過第 1 節全部判準）。
- `blockedByIssueIds` 已設定完成，依賴鏈上沒有 Developer 需要自己去猜的前置。
- 工單內附對應設計文件的 repo 路徑。

### Developer → Code Reviewer

- 三段式交付回報，缺一段即不合格：
  1. **執行項目追蹤**：AC 逐條對應做了什麼、在哪個檔案。
  2. **矛盾與風險警告**：實作中發現的規格矛盾、技術債、已知限制；沒有就寫「無」。
  3. **驗證與測試建議**：審查者要怎麼驗、跑什麼指令、看什麼結果。
- 外加：分支名、commit 訊息草案（見第 7 節）。

### Code Reviewer → Developer 或結案

- 標準審查報告，結尾必有明確 Verdict：`✅ APPROVED` 或 `❌ CHANGES REQUESTED` ＋ 重大瑕疵清單。
- 審查結果回寫到工單留言——退回後 Developer 不需翻對話就能看懂要改什麼。

### QA → Scrum Master／Developer

- 測試計畫（用 `templates/` 骨架）或缺陷報告。
- 缺陷一律用「**重現步驟／預期／實際**」三段式，並附成因工單判定（見第 5 節）。

### 通用規則

- 交接一律發生在**工單留言或工單文件**上，不依賴私下對話。
- 交接物引用文件時給 repo 內路徑，不貼大段內文複製品——複製品會過期，造成兩份真相。

## 4. HITL 閘門

遇到下列任一情況，**立即停止執行、把問題發成互動卡問使用者、把工單轉 `blocked` 等回覆**。判斷口訣：拿不準要不要問的時候，就是要問。

1. **未決事項未解**：工單的未決事項有任何一項還沒有明確答案。
2. **規格矛盾**：設計文件、工單 AC、對話三者之間有衝突（處理方式見第 6 節）。
3. **要花錢**：任何會產生費用的動作——開付費服務、升級方案、呼叫計費 API、購買資源。金額多小都要問，沒有「反正很便宜」的豁免。
4. **要對外發佈**：任何會離開私有環境的動作——開 public repo、發佈網站、對外送出訊息、公開發佈套件。
5. **破壞性操作**：刪除資料、覆寫既有成果、改動 git 歷史、動生產環境。
6. **平台權限之外的動作**：只有使用者能執行的操作——公司層 skill 的匯入／更新（agent 呼叫會被 `skill_actor_restricted` 平台不變式擋下）、公司設定變更等。發卡請使用者執行，不要空轉重試。（Pilot 卡點 #5）

### 鐵律：絕不自作主張採用建議值

文件或對話裡出現「建議用 X」「預設可以是 Y」「一般來說會選 Z」——那是**待確認選項，不是決定**。正確流程：

1. 發互動卡，列出選項與各自的代價／影響。
2. 等使用者明確選定。
3. 把選定結果寫回文件或工單，再繼續執行。

「建議看起來很合理」「照建議做八成沒錯」都不構成跳過確認的理由。

### 發卡後的行為

- 卡片未獲回覆前，只能做**不受該問題影響**的其他工作。
- 不得先斬後奏，也不得用「之後可以改」當理由先做再說——回覆若跟你猜的不同，先做的部分就是浪費加風險。

## 5. 缺陷收容判準

發現缺陷（測試失敗、行為不符預期、審查退件）時，先找**成因工單**——最初該把這件事做對的那張單——再依下表判定：

| 情境 | 判定 | 動作 |
| --- | --- | --- |
| 成因工單的 AC 正確，但實作沒達成 | **退回原單** | 原單轉回 `in_progress`（已結案的單由 Scrum Master 重開），缺陷描述寫進原單留言。不開新單。 |
| 成因工單的 AC 本身寫錯或漏寫 | **改 AC 後退回原單** | 由 Scrum Master 修正 AC 後，原單退回重做。 |
| 行為符合原 AC，但需求後來變了或想加新東西 | **開新單** | 新單走完整四段骨架，Inputs 引用原單編號。不得以「順手」為由夾進舊單。 |
| 缺陷橫跨多張單、找不到單一成因 | **開新單收容** | 新單描述症狀與已排除的成因，`blockedByIssueIds` 掛上相關單（若有）。 |

### AC 寫錯由誰改

- **只有 Scrum Master 有權修改工單的 AC。**
- 其他角色（含 Developer、Code Reviewer、QA）發現 AC 有誤時，回報 Scrum Master 並附理由，不得自行修改——即使錯誤「很明顯」。
- AC 的每次改動都要在工單留言註明：改了哪一條、為什麼改、依據哪份文件。

### 總判準

**能退回就不開新單。** 工單歷史應該反映「這件事在哪裡沒做對」；把同一件事攤成一串新單，會讓缺陷脫離成因、統計失真。

## 6. 文檔權威階序

```
設計文件（docs/ 內的 BRD/PRD/HLD/LLD） > 工單 AC > 對話
```

### 操作規則

- 發現低階與高階文件衝突時，**不得自行判定誰對**——即使高階文件「照理說」是對的。立即停下，依第 4 節發互動卡，把兩邊的說法並列給使用者裁定。
- 裁定結果出來後，由對應負責角色**先改文件、再繼續執行**：設計文件歸 Tech Lead 改，AC 歸 Scrum Master 改。不允許「心裡知道以新的為準」但文件擺爛——下一個讀文件的 agent 會被舊內容誤導。
- 對話裡的指示若與文件牴觸，同樣觸發此流程。即使指示來自使用者本人，也要先確認「是否要同步更新文件」，避免文件與現實脫節。
- 本階序只裁決「衝突時聽誰的」。文件缺漏（高階文件沒寫到的細節）不算衝突：依正常流程補寫，拿不準就發卡釐清。

## 7. commit／分支規則

### 分支

- **一單一分支**。分支名含工單編號：`<類型>/<工單編號>-<簡述>`，例如 `feat/MYL-12-login-form`、`docs/MYL-7-handbook`。
- 不在別人的分支上工作；一個分支塞多張工單的變更即違規。
- 工單結案前分支要收尾乾淨：該合的合、該刪的刪，不留孤兒分支。有審查單的工單由 Code Reviewer 在 APPROVED 時檢查這一項；**不經 Code Reviewer 的工單（如純文件單），由結案前的最後執行者自查，Scrum Master 巡檢兜底**。結案留言須寫明「分支已合併」或保留原因。（Pilot 卡點 #2）
- **合併時點**：掛有審查單的實作分支，合併回 main 一律在審查單 APPROVED **之後**。使用者確認卡的核可＝同意交付進入審查，**不等於**合併授權，兩者不可互相取代。若使用者明確指示先合併，審查單改為對已合入 commit 的核驗，並在審查報告開頭註明。（Pilot 卡點 #3）

### commit

- 訊息格式：**gitmoji ＋ 繁體中文標題**。範例：
  - `✨ 新增登入表單驗證`
  - `🐛 修正結帳頁金額四捨五入錯誤`
  - `📝 撰寫 foundry-protocol 核心規範`
- **commit 需當次同意**：每次 commit 前，把訊息草案與變更摘要給使用者過目，使用者同意這一次、才執行這一次。
  - 上一次的同意不延續到下一次。
  - 「使用者之前都同意」「這次跟上次差不多」都不構成本次授權。
- 視覺／互動相關的改動，commit 前先同步到使用者的即時環境讓其實際測過，不是只給文字 diff；純文件／後端邏輯不受此限。
- 🔓 **暫行放寬（MYL-10，2026-09-03 起，與全域 CLAUDE.md 同步）**：上兩條暫緩執行——允許自動 commit 不必先徵求同意；視覺／互動改動可直接 commit、不強制先實測。恢復嚴格模式時，本條與全域 CLAUDE.md 的對應條款**兩處一起改回**，不得只改一處。（Pilot 卡點 #1）

### push（依 MYL-23 分級授權）

- push 依第 9 節「push 權限分級表」執行：
  - **P1（私有例行推送）／P2（既有公開管道發佈）**：滿足各自前提與證據要求時，
    執行者自行執行，不必逐次徵求同意。
  - **P3（新開公開資源、擴大公開同步範圍、force push／改遠端歷史、刪遠端 repo
    ／未合併分支、涉費用）**：使用者專屬，逐次發卡當下同意，無常設授權。
- 級別拿不準時往上取級；疑似 P3 一律發卡。
- 每次 push 後在對應工單留言記錄分支、commit hash 與遠端；P2 另附發佈證據
  （過濾清單、公開 repo commit、站台 URL）。
- 凡動到 `docs/handbook/` 的工單，結案自檢加一項：變更合併進 main 後，
  是否需執行 `scripts/publish-handbook.sh` 同步公開鏡像（P2）？需要就在收尾時執行。
- 🔓 本節授權依 MYL-23 提案經使用者核可生效（2026-09-03，確認卡
  `confirmation:MYL-23:git-flow-proposal:309758d`；與全域 CLAUDE.md 同步，比照 MYL-10
  模式）；收回或收緊授權時，本節與全域 CLAUDE.md 對應條款**兩處一起改**，不得只改一處。

### git 底層與危險操作

- 動到 git 底層（`stash`、`commit-tree`、`rebase`、直接改 ref、`filter-branch` 等）或其他可能吞掉工作內容的操作前，**先在隔離環境驗證機制**（`/tmp` 的臨時 repo 或 Docker），確認行為符合預期，才對工作中的 repo 執行。
- 特別注意：`git stash push` 不加 `-- <路徑>` 會捲走**所有**已追蹤變更，必須指定路徑。
- 改動 git 歷史屬破壞性操作，同時觸發第 4 節 HITL 閘門。

## 8. 模型與思考程度分層

依 MYL-12 討論結論訂定（MYL-13 增訂）。目標：讓每張工單用「足夠但不過度」的模型與思考程度執行，省下的預算留給真正難的工作。

### 三層預設（依「角色 × 工作類型」綁定）

| 層級 | 模型／思考程度 | 預設適用 |
| --- | --- | --- |
| 高 | 當下可用的最高層級（現為 Fable 級）／`high` | Tech Lead 的設計（HLD／LLD／ADR）、Code Reviewer 的審查、CEO 的裁決與規範修訂 |
| 中 | Opus 級／`high` | Developer 的實作、QA 的測試、Product Analyst 的需求 |
| 低 | Sonnet 級／`medium` | Scrum Master 的機械性流轉：狀態機維護、依模板拆單、巡檢兜底 |

> 各層具體對應（2026-09-03 經使用者於同步卡 `ask:MYL-13:model-tier-sync:v1` 裁定）：高＝`claude-fable-5`／`high`、中＝`claude-opus-5`／`high`、低＝`claude-sonnet-5`／`medium`。

- 分層綁的是「角色做自己的本職工作」。角色偶爾做出層級外的工作（例：Scrum Master 要做缺陷收容判定這類需要推理的事），依下方升級規則調整，不必改預設。

### 升級規則（逐條可判定）

1. **同一條 AC 連續失敗兩次 → 升一級思考程度。** 第三次嘗試前把思考程度升一級（`low`→`medium`→`high`），並在工單留言記錄：哪一條 AC、兩次失敗的證據、升級後的層級。
2. **跨模組介面或安全敏感範圍 → 直接高層級，不等失敗。** 判準（任一成立即觸發）：改動會變更兩個以上模組共用的介面（函式簽名、API 契約、資料格式）；或觸及認證、授權、密鑰、權限、金流、個資。
3. **升級後同一條 AC 仍失敗 → 轉 `blocked`，不得無限重試。** 依第 2 節 `blocked` 規則留言：附各次失敗證據、標明需要誰裁決（通常是 Tech Lead 重看設計，或使用者裁定），等待解除；不得自行降級再試或換個說法重跑。

升級只影響「這張工單接下來的嘗試」，不回寫預設；若同類工作反覆觸發升級，代表預設分層要修——開單修改本節，不要在個案裡默默長期加碼。

### 權威來源與同步

- **本節是分層規則的權威來源。** Paperclip 各 agent 設定（`adapterConfig` 的 `model`／`effort`）是本節的映射；兩者不一致時，以本節為準並發起同步，而不是改本節遷就現況。
- 變更 Paperclip agent 的模型設定屬公司層設定變更，依第 4 節 HITL 閘門第 6 條處理：發卡列出「角色 → 目標 model／effort」對照表，經使用者核可（或由使用者執行）後生效，並在對應工單留言留下同步證據。
- 模型代號會隨版本演進（實際環境可能提供高於 Opus 級的模型）。本節固定的是「三層相對關係與角色歸屬」；各層對應的具體模型代號以同步卡裁定為準，裁定後回寫到上方表格附註，後續模型換代時開單重新裁定並更新附註。

## 9. 組織結構與匯報線

依 MYL-12 討論結論訂定（MYL-14 增訂）。

### 現行結構

```
使用者
└── CEO
    ├── Product Analyst（需求）
    ├── Scrum Master（流程）
    └── Tech Lead（技術）
        ├── Developer
        ├── Code Reviewer
        └── QA Engineer
```

- CEO 直轄三個職能負責人：Product Analyst、Scrum Master、Tech Lead。
- **開發三角（Developer、Code Reviewer、QA Engineer）掛在 Tech Lead 下**：三角內的技術爭議（瑕疵判定異議、設計缺漏、修法歧見）先上報 Tech Lead 裁定，不直接找 CEO；Tech Lead 裁不了、或問題涉及需求取捨／優先序／花錢／對外，再上升 CEO 或依第 4 節發卡問使用者。
- **現階段不在 CEO 下加 PM 層。**

### 匯報線與流程鏈的關係

第 3 節的流程鏈（需求→設計→工單→實作→審查→測試）是「工作交接」順序；本節是「管理與爭議升級」歸屬。兩者互相獨立：Scrum Master 拆單交棒給 Developer，不表示 Developer 匯報給 Scrum Master；Code Reviewer 掛在 Tech Lead 下，不影響其 Verdict 的獨立判定權。

### 加 PM（stream owner）的觸發條件

同時滿足以下兩項才啟動，且是為**每條流**設 stream owner，不是加單一 PM 層：

1. 同時有 ≥2 條獨立 feature 流在進行。
2. CEO 的時間主要花在跨流協調，而非單流內的裁決。

觸發時由 CEO 開單提案（含各流的 stream owner 人選與職責切分），經使用者核可後修訂本節並同步 agent 設定；未觸發前不預先建置。

### 決策權矩陣

目標（MYL-12 使用者裁定）：使用者長期只保留三類決定——**錢與權限、對外動作、產品方向**；其餘決定由下表的拍板者在對應章節的判準內消化，裁不了才沿升級路徑走。

| 決策類型 | 拍板者 | 判準依據 | 升級路徑（裁不了時） |
| --- | --- | --- | --- |
| 需求內容、範圍取捨、優先序 | **使用者** | 第 4 節 | —（本身就是終點） |
| 需求怎麼落成文件（BRD／PRD 結構、FR 切分） | Product Analyst | 角色 skill | 需求本身拿不準 → 發卡問使用者 |
| 技術選型、架構、設計文件內容 | Tech Lead（重大者寫 ADR） | 第 3、6 節 | 涉花錢／對外 → 發卡問使用者 |
| 拆單方式、依賴鏈、工單 AC 修改 | Scrum Master | 第 1、5 節 | 文件互相衝突 → 第 6 節發卡 |

| push／發佈：P1 私有例行推送、P2 既有公開管道發佈 | 執行者本人 | 第 7 節＋本節分級表 | 前提不成立或級別拿不準 → 往上取級／發卡 |

判讀規則：

- 表中拍板者在依據章節的判準內**自行決定、不發卡**——把已授權的決定推回使用者，同樣違反本節（過度上報與越權裁決都是缺陷）。
- 只有兩種情況離開自己的格子：判準覆蓋不了（沿升級路徑走），或觸發第 4 節 HITL 閘門（錢／對外／破壞性／平台權限之外）。
- 本表是既有章節的索引與補全，與各章衝突時以各章原文為準並開單修表。

### push 權限分級表（MYL-23 增訂）

| 級別 | 動作範圍 | 拍板者 | 審查者與審查內容 | 證據要求 |
| --- | --- | --- | --- | --- |
| **P1 私有例行推送** | 私有 repo（現為 agent-foundry）：push 既有分支新 commit、推送工單分支、刪除**已合併**的遠端工單分支 | 執行者本人（MYL-23 核可＝常設授權） | 無事前審查——內容已經該單既有審查鏈把關；Scrum Master 巡檢兜底 | 工單留言／交接包記明分支與 commit hash |
| **P2 既有公開管道發佈** | 使用者已核可建立的公開管道之**內容同步**：現為 `scripts/publish-handbook.sh`（推 foundry-handbook main ＋ gh-pages） | 執行者本人，須前提全數成立：(1) 來源變更已合併進私有 main；(2) 同步範圍僅限既定目錄（`docs/handbook/`）；(3) 私有連結過濾輸出檢查無異常 | 執行 agent 逐項自檢前提；Scrum Master 巡檢兜底 | 工單留言附：過濾清單輸出、公開 repo commit hash、站台 URL |

護欄：

- 級別判斷拿不準時，往上取級（P1↔P2 拿不準按 P2 的前提辦；疑似 P3 一律發卡）。
- P1／P2 推錯內容的補救（revert、強制覆蓋遠端）屬破壞性操作，回第 4 節 HITL 閘門，
  不得為了「趕快蓋掉」而自行 force push。
- 憑證失效、遠端拒絕等執行失敗不重試超過一次，轉 `blocked` 留言。

### 權威來源與同步

- **本節是組織結構的權威來源。** Paperclip 各 agent 的 `reportsTo` 欄位是本節的映射；兩者不一致時，以本節為準並發起同步（同第 8 節模式），而不是改本節遷就現況。
- 變更組織結構（含 `reportsTo`）屬公司層設定變更，依第 4 節 HITL 閘門處理：未經使用者裁定的結構調整先發卡提案；已裁定的結構（如本節）由執行工單直接同步，並在工單留言留下同步證據。
