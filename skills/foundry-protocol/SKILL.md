# foundry-protocol：Foundry 核心工作規範

本文的每一條都是「可以判定過或不過」的規則，不是原則宣言。與第 2 層角色 skill 衝突時，以本文為準；與使用者的即時指示衝突時，停下來問（見第 4、6 節）。

### 怎麼讀規則末尾的標記（MYL-40 增訂，MYL-47 補維護觸發點）

部分硬規則末尾附一行 **違反：**⟨後果⟩——寫的是不遵守會**實際發生的事**，不是訓話。後面的標記表示**這條規則現在有沒有工具會擋**，合法的收尾只有三種：

| 標記 | 含義 |
| --- | --- |
| `【機械】` | 有 lint／pre-commit／腳本閘門會擋下違反，跑不過就過不去 |
| `【自律】` | **沒有任何工具會擋**，只能靠 agent 自覺 |
| `【自律】`＋`【機械】` | 該小節含多條規則、後盾程度不同；哪一條屬哪一種寫在後果散文裡 |

- **沒有「違反：」行的小節是還沒盤點過，不是漏做。** MYL-40 盤的是當時判斷值得配一段後果的那些，其餘留白屬編輯判斷。本節因此**不宣稱全覆蓋**——改寫成「目前覆蓋第 X～Y 節」只是再種一個會過期的數字，而那正是這套標記本身要解決的問題。
- 標記記的是**現況、不是理想**：本文絕大多數硬規則是 `【自律】`。看到 `【自律】` 不代表這條比較不重要——正好相反，它代表這條做錯了不會有紅字提醒你，代價會遲到、但不會不到。
- **想把某條從 `【自律】` 變成 `【機械】`，是去寫檢查器並開單，不是改這裡的標記。** 反方向是同一件事的另一半，也同樣是義務：**新增或擴充任何 `--selfcheck` 檢查項、pre-commit hook、腳本閘門時，回頭複查它有沒有讓某條規則從 `【自律】` 升級為 `【機械】`**，有就在同一顆 commit 改掉。標記過期會從「據實記錄」變成誤導，那比沒有標記更糟。
- 上述三種以外的收尾、有「違反：」行卻沒有標記、或全文冒出第三種值，由 `foundry-lint --selfcheck` 的 `rule-marks` 擋下。它**不管「哪些小節該有違反行」**——那是編輯判斷，交給機械只會逼出一堆為了過檢查而寫的廢話段。

### 平台中立原則（MYL-35）

本文是**平台無關**的流程規範：所有對執行層（工單／狀態／留言／label／里程碑／關聯）的操作，一律以 `skills/foundry-platform/SKILL.md` 的 8 個抽象動詞與六態表述，不寫任何單一平台的欄位名或指令。三類內容各有固定歸屬，**不得互相夾帶**：

| 內容 | 歸屬 | 判準 |
| --- | --- | --- |
| 全平台通用的流程規則 | 本文（規則層 SSOT） | 換平台後字面仍成立 |
| 平台專屬的欄位、限制、API 怪癖 | `skills/foundry-platform/adapters/<平台>.md` 的「平台限制」 | 換平台後字面不成立 |
| 專案專屬的授權邊界（關卡、push） | 該專案 `.foundry/config.yml` | 換專案後值會不同 |

本 repo（agent-foundry）自身的執行層平台是 **Paperclip**（`adapters/paperclip.md`），設定檔為 `.foundry/config.yml`——本 repo 與導入 Foundry 的其他專案跑的是**同一套流程**，差異只落在 adapter 與設定檔。

## 1. 工單骨架

每張工單的**描述欄**（issue description；各平台的實際載體見對應 adapter）一律用以下四段，順序固定、標題固定，缺任何一段就是不合格工單，接單者有權退回：

```
**Inputs**
- （執行本單需要的每一項素材：檔案路徑、repo、文件、前置工單編號）

**Outputs**
- （本單完成後會存在的具體交付物：檔案路徑、文件、工單、報告）

**驗收標準**
1. （每條都是可驗證的敘述，見下方判準）

**未決事項**
- （沒有就寫「無」；有就逐條列出）
```

### Inputs 的判準

- 每一項都**實際可存取**：路徑打得開、工單編號存在、文件讀得到、憑證拿得到。
- 接單者開工的第一步就是逐項確認可存取；有任何一項打不開，立即把工單轉 `blocked`，並在留言註明是哪一項、需要誰提供。
- 不合格寫法：「參考之前的討論」「沿用大家知道的那份設定」。
- 合格寫法：「`docs/features/auth/PRD.md`」「工單 MYL-2 的產出 repo」。

### Outputs 的判準

- 每一項都是**完成後可以指著看的東西**：檔案、文件、工單、部署結果、報告。
- 動作描述不是 Output。「研究可行性」不合格；「`docs/xxx.md` 可行性評估文件」合格。
- 審查時逐項核對 Outputs 是否存在，缺一項就不能結案。

### 驗收標準（AC）的判準

- 每條 AC 都能回答「**怎麼驗**」：跑哪個指令、開哪個頁面、檢查哪個檔案的什麼內容，驗完能明確判定過或不過。
- 不合格寫法：「程式碼品質良好」「使用者體驗流暢」。
- 合格寫法：「`npm test` 全數通過」「登入頁在未填 email 時送出，顯示『請輸入 email』錯誤訊息」。
- AC 是結案的唯一依據：驗證時逐條核對，並附上證據（指令輸出、截圖、檔案連結）。

### 未決事項的判準

- 誠實列出所有還沒有答案的問題；沒有就明確寫「無」，不留空。
- **有任何一項未解的未決事項，本單不得進入實作**（見第 2、4 節）。
- 把該問的問題藏起來自己猜、或用「合理假設」帶過，都是違規；正確做法是列出來、發互動卡問。

## 2. 狀態機

使用 `foundry-platform` §2 的六態，狀態變更一律走 `update_status` 動詞。硬依賴一律用 `link_issues` 的 `blocked_by` 關聯表達（各平台承載欄位見對應 adapter），**不用工單內文的文字描述代替**；前置單全部 `done` 之前，本單不得離開 `blocked`。

### `blocked`

- **進入**：有未完成的 `blocked_by` 前置單；或 Inputs 有項目不可存取；或觸發第 4 節 HITL 閘門正在等使用者回覆。
- 進入時必須在留言註明：阻塞原因、解除者是誰、對方做什麼就能解。沒寫解除路徑的 `blocked` 視為不合格。
- 指望**其他執行者**解鎖時，一律把對方的工單掛成一級 blocker（`link_issues` 的 `blocked_by`），「解除者是誰」寫在留言。平台若對「阻塞負責人」欄位另有限制（如 Paperclip 只能填自己），依該 adapter 的「平台限制」一節處理，不在本文複述。（Pilot 卡點 #4）
- **離開**：所有前置單 `done`、Inputs 全數可存取、待答問題已獲回覆 → 轉 `todo`。

### `todo`

- **進入**：四段骨架齊全且各段通過第 1 節判準；無未解阻塞。
- **離開**：執行者領單開工 → 轉 `in_progress`。

### `in_progress`

- **進入**：執行者已逐項確認 Inputs 可存取，且未決事項為「無」或已全數解決。**未決事項還有未解項就開工，視為違規。**
- **離開**：交付物完成且自檢過每一條 AC → 轉 `in_review`；中途遇阻塞或觸發 HITL 閘門 → 轉 `blocked`。

### `in_review`

- **進入**：Outputs 已產出、交接包（見第 3 節）已附在工單上、有明確的審查者或待核准的互動卡。**沒有真實審查路徑不得掛 `in_review`**——「等有人有空看」不是審查路徑。
- 與 `blocked` 的分界（判準：**有沒有東西要人驗收**）：等待第 4 節**三個抽象關卡**的核可卡回覆 → `in_review`（卡本身就是審查路徑，foundry-gates §3、foundry-adopt §2 同此）；等待**觸發式 HITL 閘門**的回覆 → `blocked`（執行被打斷，沒有待驗收的交付物）。
- **離開**：審查通過 → 轉 `done`；退回 → 轉 `in_progress`，並附具體缺陷清單（不是「再改改」）。

### `done`

- **進入**：AC 逐條有驗證證據，且分支已依第 7 節收尾。**只有宣稱、沒有證據，不得結案。**
- **手冊發佈檢查（MYL-12 決議，MYL-32／MYL-24／MYL-55 增訂）**：本單若動到 `docs/handbook/`，結案前必須走完第 7 節「手冊發佈審查」的**前四步**（合併進 main → 寫審查記錄 → commit → 同步主閱讀面）。同步屬 MYL-23 分級表 **P2**，由執行者自檢前提後自行執行，**不需使用者逐次同意**；結案留言附審查記錄路徑、連結改寫輸出、逐章比對表與閱讀面 URL。第五步（精裝站版本 tag）是**可選**的，**不是結案條件**——它由使用者決定何時發一版（`V1`）。前提不成立而暫不同步時（例如變更還沒合併進 main），結案留言註明「主閱讀面未同步」與後續處理方式，不因等待同步而卡住結案。
- 原則上不重開；結案後發現的問題依第 5 節判定退回或開新單。

### `cancelled`

- **進入**：需求不再成立，或被其他單取代（留言註明取代單編號）。取消原因必須寫在留言，不得無聲取消。

## 3. 交接格式

標準流程鏈：**需求（Product Analyst）→ 設計（Tech Lead）→ 工單（Scrum Master）→ 實作（Developer）→ 審查（Code Reviewer）→ 測試（QA）**。每一棒必附的交接物如下；**交接物不齊，下一棒有權直接退回，不開工。**

鏈上另有兩棒不在主線：**Frontend Verifier** 只在有前端改動時插進來（條件式，不是每張單都跑），**PM → CEO** 是橫向的狀態彙整、不接續任何一棒的產出。兩者的交接物要求同樣適用「不齊就退回」。

### 使用者／Product Analyst → Tech Lead

- BRD／PRD（用 `templates/` 的骨架），含已與使用者確認過的驗收條件與優先序。
- 尚未確認的需求點列在文件的未決區塊，不得混進已確認需求。

### Tech Lead → Scrum Master

- HLD／LLD 設計文件，存於 `docs/features/<模組>/`，含技術決策與取捨說明。
- 重大技術決策（選型、架構變更）附 ADR：寫明選項、取捨、結論。

### Scrum Master → Developer

- 合格工單（通過第 1 節全部判準）。
- `blocked_by` 關聯已設定完成，依賴鏈上沒有 Developer 需要自己去猜的前置。
- 工單內附對應設計文件的 repo 路徑。

### Developer → Code Reviewer

- 三段式交付回報，缺一段即不合格：
  1. **執行項目追蹤**：AC 逐條對應做了什麼、在哪個檔案。
  2. **矛盾與風險警告**：實作中發現的規格矛盾、技術債、已知限制；沒有就寫「無」。
  3. **驗證與測試建議**：審查者要怎麼驗、跑什麼指令、看什麼結果。
- 外加：分支名、commit 訊息草案（見第 7 節）。

### Code Reviewer → Developer 或結案

- 標準審查報告，結尾必有明確 Verdict：`✅ APPROVED` 或 `❌ CHANGES REQUESTED` ＋ 重大瑕疵清單。
- 審查結果回寫到工單留言——退回後 Developer 不需翻對話就能看懂要改什麼。

### QA → Scrum Master／Developer

- 測試計畫（用 `templates/` 骨架）或缺陷報告。
- 缺陷一律用「**重現步驟／預期／實際**」三段式，並附成因工單判定（見第 5 節）。

### Developer／QA Engineer → Frontend Verifier（只在有前端改動時）

- 待驗環境的可存取位址，以及本次要驗的範圍：哪幾條流程、哪些 viewport 與瀏覽器。**沒寫進範圍的就是沒驗**，回程不得外推。
- 可逐條抄成對照表的斷言清單（來源是測試計畫或工單 AC）。抄不出來的斷言由 QA Engineer 或 Scrum Master 改寫，Frontend Verifier 不自己揣測一個近似的來測。
- 回程交付：固定表格（檢查項／預期／實際／過不過／證據）＋宣告本次以哪一個瀏覽器能力等級執行。缺陷依第 5 節收容，能退回原單就不開新單。

### PM → CEO

- 結構化狀態報告：每張在途工單的狀態、卡在誰身上、哪些互動卡待答、哪些單靜默等人。
- 結尾必附「**需要 CEO 決定的事項**」清單；沒有就明寫「無」。
- 每一格填得出證據指標（工單編號、commit sha、留言 id）；查不到的寫「未查證」，不以推論補滿。

### 通用規則

- 交接一律發生在**工單留言或工單文件**上，不依賴私下對話。
- 交接物引用文件時給 repo 內路徑，不貼大段內文複製品——複製品會過期，造成兩份真相。（同 `C3`，完整讀取規則見第 10 節。）

## 4. 關卡與 HITL 閘門

本節有兩套機制：**三個抽象關卡**（常規流程的使用者核可點，粒度可依專案設定調整）與**觸發式 HITL 閘門**（例外通道，遇到就問、不受任何粒度設定影響）。

### 三個抽象關卡（MYL-9／MYL-27 增訂）

常規流程中需要使用者核可的點，收斂為三個抽象關卡。各專案的關卡設定存於 `.foundry/config.yml` 的 `gates` 段（schema 見 `skills/foundry-platform/config-schema.md`），由 `foundry-init` 首次寫入、`foundry-gates` workflow 經使用者確認後調整；**agent 不得自行改動關卡設定**。

| ID | 關卡 | 回答的問題 | 預設核可者 | 可否調整 |
| --- | --- | --- | --- | --- |
| `G-A` | **A 規格核可** | 做什麼？ | 使用者 | 可（經 foundry-gates 由使用者裁定） |
| `G-B` | **B 方案核可** | 怎麼做？ | 使用者 | 可；小型工單（`size:small`）可設 `skip_below: small` 跳過 |
| `G-C` | **C 對外／不可逆核可** | 要不要出去？ | 使用者 | **不可調降——本條寫死**。`gates.external_actions` 只允許 `user`，設定檔出現其他值視為非法、整檔拒用 |

與現行 7 個決策點（handbook 第 4 章）的對照：

| 關卡 | 對應決策點 |
| --- | --- |
| A 規格核可 | 決策點 1（選題）＋ 2（需求取捨）＋ 3（需求定稿） |
| B 方案核可 | 決策點 4（階段交接）之 HLD 核可部分 |
| C 對外／不可逆核可 | 決策點 5（實作交付）之 push／發佈部分 ＋ 7（平台動作） |
| （不屬關卡） | 決策點 6（觸發式 HITL 閘門）——**原樣保留，見下方**，不受 `gates` 任何設定影響 |

補充規則：

- **中段執行決策**（排程、實作、code review、測試、本地 commit、文檔同步、關卡間交接）依第 9 節決策權矩陣由對應拍板者自動執行，使用者只收各階段摘要留言，不逐段發卡。
- 決策點 5 的「驗收實作結果」併入關卡 C 前的摘要報告：使用者核可對外動作時一併驗收，不再單獨發卡。
- **關卡 C 與常設授權的關係**：使用者可透過關卡 C 的一次核可，給予特定動作的常設授權（如 MYL-23 的 P1／P2 push 分級，見第 7、9 節）。已給予的常設授權範圍內動作不再逐次過卡；但**常設授權的給予、擴大、收回本身永遠是關卡 C**，只有使用者能拍板，不可調降、不可由任何設定代行。

**違反：**使用者在規格或方案還沒拍板時就看到既成事實，要改只能推翻已完成的工作。`gates.external_actions` 被填成 `user` 以外的值時，「整檔拒用」不會真的發生——**目前沒有任何程式讀取或驗證 `.foundry/config.yml`**，設定檔看起來合法、關卡 `G-C` 實際已經失效，而且沒有人會收到通知。`【自律】`

### 觸發式 HITL 閘門（不受關卡粒度設定影響）

遇到下列任一情況，**立即停止執行、把問題發成互動卡問使用者、把工單轉 `blocked` 等回覆**。判斷口訣：拿不準要不要問的時候，就是要問。本閘門是例外通道，不屬常規關卡；`.foundry/config.yml` 的任何 `gates` 設定都不改變本閘門的觸發條件。

1. `H1` **未決事項未解**：工單的未決事項有任何一項還沒有明確答案。
2. `H2` **規格矛盾**：設計文件、工單 AC、對話三者之間有衝突（處理方式見第 6 節）。
3. `H3` **要花錢**：任何會產生費用的動作——開付費服務、升級方案、呼叫計費 API、購買資源。金額多小都要問，沒有「反正很便宜」的豁免。
4. `H4` **要對外發佈**：任何會離開私有環境的動作——開 public repo、發佈網站、對外送出訊息、公開發佈套件。
5. `H5` **破壞性操作**：刪除資料、覆寫既有成果、改動 git 歷史、動生產環境。
6. `H6` **平台權限之外的動作**：只有使用者能執行的操作——skill／規範的匯入更新、組織與公司層設定變更等。各平台的實際限制清單見對應 adapter 的「平台限制」一節（Paperclip 例：skill 匯入被 `skill_actor_restricted` 擋下、agent terminate／pause 為 board-only）。發卡請使用者執行，不要空轉重試。（Pilot 卡點 #5）

**違反：**使用者在不知情的狀況下承擔了本該由他拍板的後果——花掉的錢、送出去收不回的內容、刪掉的資料、動過的 git 歷史；這些多半不可逆，事後補問已經沒有意義。沒有任何工具能偵測「你當時該問而沒問」，這條漏掉時整輪工作看起來會完全正常。`【自律】`

### 鐵律：絕不自作主張採用建議值

文件或對話裡出現「建議用 X」「預設可以是 Y」「一般來說會選 Z」——那是**待確認選項，不是決定**。正確流程：

1. 發互動卡，列出選項與各自的代價／影響。
2. 等使用者明確選定。
3. 把選定結果寫回文件或工單，再繼續執行。

「建議看起來很合理」「照建議做八成沒錯」都不構成跳過確認的理由。

**違反：**建議值變成既成決定，使用者以為自己選過、其實從來沒有。這種缺陷通常要到很後面才浮出來——那時整段工作已經建立在一個沒人拍板的前提上，要退回的不只是一條設定。`【自律】`

### 發卡後的行為

- 卡片未獲回覆前，只能做**不受該問題影響**的其他工作。
- 不得先斬後奏，也不得用「之後可以改」當理由先做再說——回覆若跟你猜的不同，先做的部分就是浪費加風險。

**違反：**回覆與你猜的不同時，先做的部分全是白工；更麻煩的是已經寫進 repo 的錯誤前提——下一個 agent 讀到它時不會知道那是猜的，會當成現行規範沿用。`【自律】`

## 5. 缺陷收容判準

發現缺陷（測試失敗、行為不符預期、審查退件）時，先找**成因工單**——最初該把這件事做對的那張單——再依下表判定：

| ID | 情境 | 判定 | 動作 |
| --- | --- | --- | --- |
| `D1` | 成因工單的 AC 正確，但實作沒達成 | **退回原單** | 原單轉回 `in_progress`（已結案的單由 Scrum Master 重開），缺陷描述寫進原單留言。不開新單。 |
| `D2` | 成因工單的 AC 本身寫錯或漏寫 | **改 AC 後退回原單** | 由 Scrum Master 修正 AC 後，原單退回重做。 |
| `D3` | 行為符合原 AC，但需求後來變了或想加新東西 | **開新單** | 新單走完整四段骨架，Inputs 引用原單編號。不得以「順手」為由夾進舊單。 |
| `D4` | 缺陷橫跨多張單、找不到單一成因 | **開新單收容** | 新單描述症狀與已排除的成因，`blocked_by` 掛上相關單（若有）。 |

**違反：**同一件事被攤成一串新單，缺陷脫離成因、統計失真。半年後想查「這個功能當初是在哪裡沒做對」，會查到一堆症狀單、找不到那張該負責的原單。`【自律】`

### AC 寫錯由誰改

- **只有 Scrum Master 有權修改工單的 AC。**
- 其他角色（含 Developer、Code Reviewer、QA）發現 AC 有誤時，回報 Scrum Master 並附理由，不得自行修改——即使錯誤「很明顯」。
- AC 的每次改動都要在工單留言註明：改了哪一條、為什麼改、依據哪份文件。

**違反：**AC 被執行者改成自己做得到的樣子，驗收標準悄悄向實作靠攏，工單於是「全過」但需求沒被滿足。沒留言時更糟：沒有人知道這條 AC 何時、被誰、依據什麼改過，連要退回哪個版本都判不出來。`【自律】`

### 總判準

**能退回就不開新單。** 工單歷史應該反映「這件事在哪裡沒做對」；把同一件事攤成一串新單，會讓缺陷脫離成因、統計失真。

## 6. 文檔權威階序

```
設計文件（docs/ 內的 BRD/PRD/HLD/LLD） > 工單 AC > 對話
```

### 操作規則

- `A1` 發現低階與高階文件衝突時，**不得自行判定誰對**——即使高階文件「照理說」是對的。立即停下，依第 4 節發互動卡，把兩邊的說法並列給使用者裁定。
- `A2` 裁定結果出來後，由對應負責角色**先改文件、再繼續執行**：設計文件歸 Tech Lead 改，AC 歸 Scrum Master 改。不允許「心裡知道以新的為準」但文件擺爛——下一個讀文件的 agent 會被舊內容誤導。
- `A3` 對話裡的指示若與文件牴觸，同樣觸發此流程。即使指示來自使用者本人，也要先確認「是否要同步更新文件」，避免文件與現實脫節。
- `A4` 本階序只裁決「衝突時聽誰的」。文件缺漏（高階文件沒寫到的細節）不算衝突：依正常流程補寫，拿不準就發卡釐清。

**違反：**兩份文件繼續各說各話，下一個讀到舊版的 agent 會照舊版執行。「心裡知道以新的為準」不會傳給下一個 session——session 結束時那份理解就消失了，留在 repo 裡的只有沒改的文件。`【自律】`

### 三層文檔體系的同步方向（MYL-9／MYL-27 增訂）

跨平台架構下，文檔分三層（MYL-9 HLD §1）：**① 規則層**＝repo 內 .md（`skills/`、`docs/`、`templates/`、`.foundry/`），規則與流程的 SSOT；**② 執行層**＝git 平台的工單／看板（`local-md` 模式為 `.foundry/board/`），執行狀態的 SSOT；**③ 說明層**＝文檔網站，永遠是 ① 的投影。

- **同步方向**：規則文檔只在 ① 編輯——③ 由 `publish_docs` 動詞從 ① 投影（本 repo＝`scripts/publish-wiki.sh` 與 `scripts/publish-site.sh`，目標面由 `.foundry/config.yml` 的 `docs` 段決定）、② 的 issue templates／labels 定義由 init workflow 從 ① 產生。執行狀態只在 ② 更新，① 不保存工單進度副本。**禁止直接改 ③、或在 ② 上另寫規則**——那會製造第二份真相。
- **跨層衝突裁決**：規則類內容衝突以 ① 為準、執行狀態類衝突以 ② 為準。無法歸類為單純規則或狀態時，回到本節開頭的階序處理；仍裁不了就依第 4 節發卡。

**違反：**出現第二份真相。直接改 ③ 的內容會在下一次投影時被擋下或被 ① 整份覆蓋，改動連同改它的理由一起消失；在 ② 上另寫規則則永遠不會回流到 ①，於是同一件事在看板和 repo 各有一套說法。`【自律】`

### 永久文件 vs 一次性意圖紀錄（MYL-36 增訂）

不是每份寫出來的 .md 都該進版控。**雙重維護成本**是真實成本：一份實作計畫進了 repo，日後實作改了它沒改，就多一份會誤導人的舊文件——而它當初的用途早在合併那天就結束了。

判準一句話：**「三個月後，還有人需要照它做事嗎？」**

| 類別 | 內容 | 去處 |
| --- | --- | --- |
| `W1` **永久文件** | BRD／PRD／HLD／LLD、`docs/standards/` 契約與已知漂移、templates、skills、審查報告、發佈審查記錄 | **進版控**，依第 6 節階序維護 |
| `W2` **一次性意圖紀錄** | 實作計畫、探索筆記、選項比較、「這輪為什麼這樣取捨」、階段性進度摘要 | **寫工單留言或 commit／PR 描述，不進版控**——未來從工單與 commit 歷史回溯 |

- 判不出來時看**讀者**：寫給「未來要照它做事的人」＝永久；寫給「現在要核可這一輪的人」＝一次性。
- 一次性紀錄**不因為寫得好就升格**。要升格，是把其中「往後仍要遵守的規則」抽出來寫進對應永久文件，而不是把整份計畫書搬進 `docs/`。
- 本條不追溯既有檔案：已在版控裡的一次性文件（如 `docs/features/*/proposal.md`）留著當歷史依據，但**檔首須註明狀態與現行權威出處**，避免讀者誤當現行規範（範例見 `docs/features/git-flow/proposal.md`）。

**違反：**實作計畫進了版控，實作後來改了、它沒改，repo 裡就多一份長得像規範的舊文件。讀者無從判斷手上這份還算不算數，於是要嘛照舊的做、要嘛回頭問——兩種都是這條規則本來要省掉的成本。`【自律】`

## 7. commit／分支規則

### 分支

- **一單一分支**。分支名含工單編號：`<類型>/<工單編號>-<簡述>`，例如 `feat/MYL-12-login-form`、`docs/MYL-7-handbook`。
- 不在別人的分支上工作；一個分支塞多張工單的變更即違規。
- 工單結案前分支要收尾乾淨：該合的合、該刪的刪，不留孤兒分支。有審查單的工單由 Code Reviewer 在 APPROVED 時檢查這一項；**不經 Code Reviewer 的工單（如純文件單），由結案前的最後執行者自查，Scrum Master 巡檢兜底**。結案留言須寫明「分支已合併」或保留原因。（Pilot 卡點 #2）
- **合併時點**：掛有審查單的實作分支，合併回 main 一律在審查單 APPROVED **之後**。使用者確認卡的核可＝同意交付進入審查，**不等於**合併授權，兩者不可互相取代。若使用者明確指示先合併，審查單改為對已合入 commit 的核驗，並在審查報告開頭註明。（Pilot 卡點 #3）

**違反：**一個分支塞多張工單時，任何一張要退回或 revert 都會連帶動到別張的變更，兩張單從此綁死。孤兒分支累積後沒人分得出哪些已合併、哪些是還沒做完的工作，只能一條條開來看。未經審查就合併回 main 則等於把審查降級成事後追認——退件時要改的已經在主線上。`【自律】`

### commit

- 訊息格式：**gitmoji ＋ 繁體中文標題**。範例：
  - `✨ 新增登入表單驗證`
  - `🐛 修正結帳頁金額四捨五入錯誤`
  - `📝 撰寫 foundry-protocol 核心規範`
- **commit 需當次同意**：每次 commit 前，把訊息草案與變更摘要給使用者過目，使用者同意這一次、才執行這一次。
  - 上一次的同意不延續到下一次。
  - 「使用者之前都同意」「這次跟上次差不多」都不構成本次授權。
- 視覺／互動相關的改動，commit 前先同步到使用者的即時環境讓其實際測過，不是只給文字 diff；純文件／後端邏輯不受此限。
- 🔓 **暫行放寬（MYL-10，2026-09-03 起，與全域 CLAUDE.md 同步）**：上兩條暫緩執行——允許自動 commit 不必先徵求同意；視覺／互動改動可直接 commit、不強制先實測。恢復嚴格模式時，本條與全域 CLAUDE.md 的對應條款**兩處一起改回**，不得只改一處。（Pilot 卡點 #1）

**違反：**commit 歷史失去可讀性，日後 `git log` 認不出某次改動屬於哪張工單、為了什麼改。注意 MYL-10 放寬的只有「事前徵求同意」與「視覺改動先實測」兩條，**訊息格式沒有放寬**；`.pre-commit-config.yaml` 目前沒有 commit-msg hook，格式寫錯不會被擋下。`【自律】`

### push（依 MYL-23 分級授權）

- push 依第 9 節「push 權限分級表」執行：
  - **P1（例行推送，不新增公開面）／P2（既有公開管道發佈）**：滿足各自前提與證據要求時，
    執行者自行執行，不必逐次徵求同意。
  - **P3（新開公開資源、擴大公開同步範圍、force push／改遠端歷史、刪遠端 repo
    ／未合併分支、涉費用）**：使用者專屬，逐次發卡當下同意，無常設授權。
- `P1` 的判準是**這次 push 有沒有新增公開面**，不是 repo 現在私有還是公開（MYL-59）。
  本 repo 已是 public，例行推送（既有分支的新 commit、工單分支、刪已合併的遠端分支）
  推的仍是既有可見面裡的新內容，公開面一格未變，仍屬 `P1`；會讓新的東西變成公開的動作
  一律落回 `P3`。
- 級別拿不準時往上取級；疑似 P3 一律發卡。
- 每次 push 後在對應工單留言記錄分支、commit hash 與遠端；P2 另附發佈證據
  （過濾清單、公開 repo commit、站台 URL）。
- 凡動到 `docs/handbook/` 的工單，結案自檢加一項：變更合併進 main 後，
  依下方「手冊發佈審查」流程同步主閱讀面（P2）；要不要順帶發一版精裝站是使用者的決定（`V1`）。
- 🔓 本節授權依 MYL-23 提案經使用者核可生效（2026-09-03，確認卡
  `confirmation:MYL-23:git-flow-proposal:309758d`；與全域 CLAUDE.md 同步，比照 MYL-10
  模式）；收回或收緊授權時，本節與全域 CLAUDE.md 對應條款**兩處一起改**，不得只改一處。

**違反：**把 `P3` 當 `P1` 做掉時，使用者專屬的決定（新開公開資源、改遠端歷史、刪未合併分支）已經發生，而且多半不可逆——事後發卡只能追認。漏記錄分支與 commit hash 則工單失去可追溯性：日後查不出哪個 commit 推到了哪個遠端，`P2` 還會連帶少掉發佈證據。`【自律】`

### 手冊同步戳記（MYL-44 增訂）

`docs/handbook/` 是規則層的說明層。本檔改了而手冊沒跟，公開站就開始騙人——而且騙得很難察覺：站上每一句都曾經是對的。實測 74 顆 commit 裡 16 顆動本檔，其中 10 顆同一顆就同步了手冊，真正會漏的只有 5～6 顆；問題真實但稀疏，所以用機械攔截，不用「每張單自我申報」。

- **戳記掛四章**：`03-workflow.md`、`04-decision-points.md`、`06-org-structure.md`、`07-workflows.md`，各在**章標題後第一個非空行**放一行 `> 最後對照 protocol ⟨sha⟩（YYYY-MM-DD）`（sha 以反引號包住，至少 7 碼）。只有這四章在複述規則層語意；`08-cross-platform.md` 講的是「把流程帶到別的平台」，不隨條文變動，不掛。
- **三層閘門**：層 0 是 pre-commit 觸發器（本次 commit 改了本檔卻沒動 `docs/handbook/` → 擋下）；層 1 是 `foundry-lint --selfcheck` 的 `handbook-stamp`（驗四章戳記存在、格式合法、不落後），跑在 `make check`；層 2 是 agent 的判斷，**只在被層 0 攔下時才跑**——約每 12 顆 commit 一次。
- **推戳記本身就是銷案憑證**。不寫「已同步／不需同步＋理由」那種散文，它會退化成儀式；要交代的是把戳記推到新 sha，那是 diff 上看得見的東西。
- **落後的判準**是「戳記之後的每一顆本檔改動，都要有手冊變更同行」，不是「戳記等於最新 sha」——後者在同一顆 commit 內永遠無法成立，戳記只能指向已存在的 commit、指不到自己這顆。
- **被層 0 擋下時**，讀本次 diff 判斷四章要不要改，然後三選一：
    1. 要改內容 → 改完連戳記一起 commit；
    2. 內容不用改 → 只把戳記推到當前本檔最新 sha ＋今日日期，一起 commit；
    3. 戳記已是該 sha 且日期同天（同一天第二次改本檔）→ 把改動 `git commit --amend` 併進前一顆，或先 `--no-verify` commit 這顆、再補一顆戳記-only commit 把戳記推到新 sha。第 3 條的 `--no-verify` 不是漏洞：漏補戳記的話層 1 會在 `make check` 紅，這條路封閉。

**違反：**pre-commit 直接擋下 commit，`make check` 的 `handbook-stamp` 也會紅。本條因此從 MYL-40 標記表上的 `【自律】` 轉為機械攔截，是那張表第一個被轉換的條目。但機械擋得住的只有「本檔改了而手冊完全沒動」與「戳記落後」兩件事，**擋不住「戳記推了、內容其實沒對照過」**——那一步仍歸層 2 的判斷，差別只在它現在會留下一道 diff 上的痕跡，事後查得出是誰在哪一顆 commit 說自己看過了。`【機械】`

### 手冊發佈審查（MYL-24 增訂，MYL-55 補第五步）

動到 `docs/handbook/` 的工單，結案前依序做完**前四步**；那四步**沒有使用者介入點**——P2 的拍板者是執行者本人（第 9 節分級表），使用者只在結案留言收摘要。第五步是可選的版本發佈，**只有它需要使用者**。

1. **合併進 main**：手冊變更合併回 main 並 push（P1）。沒合併就發佈＝把只存在於工作分支的內容推上公開站。
2. **寫審查記錄**：用 `templates/publish-review.md` 建 `docs/publish-reviews/<工單編號>.md`，逐項自檢 P2 三前提（來源已合併進 main／範圍僅限 `docs/handbook/`／私有連結改寫輸出無異常）＋公開適切性（機敏資訊、內部路徑、連結可達性）。三前提全成立才填 `verdict: APPROVED`。
3. **commit 審查記錄**：`handbook_commit` 欄填 `git log -1 --format=%H -- docs/handbook` 的完整 sha。
4. **同步主閱讀面**：執行 `docs.primary` 指到的那個投影（本 repo＝`bash scripts/publish-wiki.sh`）。腳本的證據閘門會核對記錄，通過才 push。**P2，執行者自行**。
5. **（可選）發一版精裝站**：`docs.mirror_site.trigger: tag` 時，打 `handbook-v<a>.<b>.<c>.<d>` tag（形狀見 `V4`）並 push，CI 用 `mike` 建出帶版本選擇器的 Pages 站。**這一步是使用者專屬**，見下方 `V1`。⚠️ 本 repo 另有一條 `handbook-version-tags` tag ruleset 擋住 `handbook-v*` 的建立，**擋的是所有人、包含使用者本人**：推 tag 前要先到 Settings → Rules → Rulesets 把它切成 Disabled，推完切回 Active。那不是多一道關卡，是 `V1` 換到「防誤推＋留痕」所付的代價，理由見下方違反段。

規則：

- **審查者就是執行者本人**，不另設 Code Reviewer／Tech Lead 前置審查（MYL-23 分級表 P2 明定「無事前審查——內容已經該單既有審查鏈把關」）；巡檢兜底歸 Scrum Master。
- **閘門綁 commit sha，不綁工單號**：審查通過後又改了手冊，舊記錄自動失效，必須重新自檢並更新 `handbook_commit`。想繞過閘門直接跑腳本會被拒跑。
- **戳記-only 的手冊 diff 免寫獨立審查記錄，但照樣發佈**（MYL-44 增訂）：若 `git diff ⟨上次已核可的 handbook_commit⟩..HEAD -- docs/handbook/` 的所有變更行都符合戳記正則，`scripts/lib/publish-gate.sh` 放行，並在輸出印出被略過審查的戳記 commit 清單。條件由 `git diff` 機械判定，是**封閉的洞、不是人治例外**：夾帶任何一行實質內容就落回上面的閘門、`exit 1`。沒有這條旁路的話，戳記-only 的 commit 會換掉手冊 sha、找不到對應的 APPROVED 記錄，公開站會被自己的閘門鎖在舊版——那正是同步戳記要避免的事。
- 自檢有任一前提不成立 → 不要建 APPROVED 記錄，也不要跑腳本；工單結案留言註明「主閱讀面未同步」與原因（見第 2 節 `done`）。
- 發佈範圍或過濾規則本身要改（不只是同步內容），那是 **P3**，發卡問使用者。新開一個目標面（啟用 wiki、開 Pages、新建公開 repo）另屬關卡 C。

**違反：**兩支投影腳本共用的 `scripts/lib/publish-gate.sh` 會拒跑——找不到對應這版手冊 sha 的 `APPROVED` 記錄、或 `handbook_commit` 與 `git log -1 -- docs/handbook` 對不上，都直接擋下，公開面停在舊版。**這是本文少數真的擋得住的規則之一**；但閘門只管「有沒有跑腳本」，繞過腳本手動推公開面它攔不到，那條路的後果是公開面與 repo 不一致而無人察覺。`【機械】`

### 手冊版本 tag（MYL-55 增訂，MYL-63 補 `V3`，MYL-68 補 `V4`）

精裝站（`.foundry/config.yml` 的 `docs.mirror_site`）**打 tag 才發**。手冊因此第一次有了「我讀的是哪一版規則」：`mike` 把每個版本各自留在 Pages 上，站台有版本選擇器，舊版不會被新版蓋掉。

- `V1` **tag 規範與時機**：tag 名為 `handbook-v<a>.<b>.<c>.<d>`（形狀與遞增規則見 `V4`），**只標手冊版本、不動 repo 全域版本號**；且必須在該版手冊的發佈審查 `verdict: APPROVED` **之後**才打——先打 tag 等於發佈一個還沒過審的版本，而版本一旦上站就有人引用得到。打 tag 與 push tag 屬第 9 節分級表「push main、force-push、**tag 發佈**」那一列，**使用者專屬、逐次同意，無常設授權**；agent 不得自行 `git tag` 後 push。
  - **例外——使用者當次明確指示**（MYL-70／MYL-71 增訂）：使用者在該次明確指示 agent 代為打 tag、push tag 或**刪除 tag** 時，agent 得執行；**該指示本身即關卡 `G-C` 核可，不必另發卡**。**授權只及於該次指定的那個 tag，不延續到下一次**，也不因此成為常設授權。執行時附三項義務：(1) 在工單留言記錄當下 `handbook-version-tags` 的 `enforcement` 實測值作為留痕；(2) 動完立刻提醒使用者把 ruleset 切回 `active`——**切換動作本身仍是使用者專屬**，agent 不代勞（agent 的 token 改得動它，但那會把這條規則買到的「留痕」一起買掉，見下方違反段）；(3) 若該次動作違反 `V3`（移動／刪除已發佈的 tag），在工單明文記為破例並寫明理由。沒有這條例外的話，「使用者叫我刪」與「agent 不得自行動 tag」會在每一次都僵住，而僵住時的兩條出路——多發一張問同一件事的卡、或默默照做——都比寫明它差。
- `V2` **開關要真的關得掉**：`docs.mirror_site.enabled: false` 時，**即使打了符合 `tag_pattern` 的 tag 也不發佈**。判斷的權威是設定檔，不是 CI workflow 的 `on: push: tags:`——後者是寫死的靜態 glob，改 `tag_pattern` 不會讓它跟著變，所以它只是粗篩。實作在 `tools/publish-docs/site_docs.py` 的 `mirror_site_decision()`，由 CI 的 `gate` job 呼叫；`enabled` 不是 true 時 `deploy` job 整個不跑。
- `V3` **已發佈的版本不重打**：一個 `handbook-v<a>.<b>.<c>.<d>` 發出去之後，**那個版本號的內容就定了**。手冊要修就**遞增一位**打下一版（哪一位見 `V4`），不要移動、刪除或重打已發佈的 tag。理由是版本化站台的整個用途就是「我引用的那一版還在」——把已發佈的那一版內容換掉，等於讓所有指向那一版的引用悄悄指到別的東西，而且**沒有任何痕跡**：`mike deploy` 對同名版本是直接覆蓋 gh-pages 上那個目錄，不問也不警告。判斷實作在 `site_docs.py` 的 `republish_decision()`，由 `gate` job 在 `publish=true` 之後、`deploy` 之前呼叫，撞版本時以離開碼 3 擋下。**`workflow_dispatch` 的重建路徑刻意放行**——判準是「同一個版本號的內容有沒有變」，不是「跑過幾次 `mike deploy`」；重建同一顆 commit 產出同樣的位元組，而擋死它等於封掉唯一的重建手段。刪除已發佈版本（`mike delete`）不歸本條管，那是使用者專屬的破壞性動作，走 `G-C`。
- `V4` **版本號的形狀與遞增規則**：四位十進位整數 `handbook-v<a>.<b>.<c>.<d>`，遞增採**進位歸零**——動 `a` 則 `b`／`c`／`d` 歸零，動 `b` 則 `c`／`d` 歸零，動 `c` 則 `d` 歸零，動 `d` 只加 `d`。形狀刻意**與本流程的來源專案同形**（SuperOD `scripts/tag_release.py` 的 `v<a>.<b>.<c>.<d>`＋同一條進位歸零規則）：`V1`／`V3` 本來就是從那份 `git_flow.md` 的 `T1`～`T3`／`T5` 移植過來的，版本號形狀是七條裡唯一沒帶走的一條，本條把它補齊，讓兩邊的心智模型可以互換。四位各自的判準是**「讀者要付出什麼代價」**，不是「改了多少字」：
  - `a` **主版號**——**照舊版做事會變成違規**：既有規則 ID 的語意變更或移除、關卡與 push 分級調整。這一位一跳，舊版的心智模型就不能再沿用。此判準與 `.foundry/config.yml` 的 `foundry` schema 版本同義（都是「只在不相容變更時遞增」），差別只在那一欄是相容性契約標記（答「我還解析得動嗎」），本條是發行快照（答「我引用的那一版還在嗎」）。
  - `b` **次版號**——**純新增**：新規則 ID、新章節、新流程，舊版做法照樣合規，讀者只需要知道多了什麼。
  - `c` **修訂號**——**敘述變了但判準沒動**：補例子、修錯字、改寫得更清楚。⚠️ 這一位**不是**日常修訂的出口——錯字修正走主閱讀面（wiki）隨時更新，根本不必發版；只有在「已發佈的那一版敘述會誤導人」時才為它定一版。
  - `d` **建置號**——**手冊一字未改，產出卻不同**：`mkdocs`／`mike`／主題升版後重建。這一位補上 `V3` 裡「重建同一顆 commit 產出同樣的位元組」那句話的角落——那句話只在建置環境沒變時成立，環境變了就該用新的 `d` 發一版，而不是拿 `workflow_dispatch` 去覆蓋舊版。
- **本條定死在 protocol，不開成設定旋鈕**：這是全隊的版本號語意，不是每個專案各自調的參數。要換形狀的專案改 `docs.mirror_site.tag_pattern` 這個既有欄位即可，不必動本條。

**違反：**`V1` 沒有機械後盾中的「時機」那半——CI 不知道審查是哪一天過的，它只核對 tag 指到的那份手冊有沒有對應的 APPROVED 記錄（`publish-gate.sh`），所以「審查前就先打 tag」擋得住的前提是那時還沒寫審查記錄；審查記錄先寫好、tag 晚一點才打則本來就合規。真正擋不住的是 agent 自己 `git tag` 再 push——沒有任何 hook 攔 tag push，那條線純靠自律，而它的後果是使用者沒同意過的版本出現在公開站上。**而且這一段在本 repo 機械化不了，不是「還沒做」**：要擋住它得能分辨「誰在推」，但本 repo 是個人帳號底下的 repo，使用者與所有 agent 共用同一個 GitHub 身分，於是 tag ruleset 的「限制建立者」只塌得成兩種極端——bypass 放 Repository admin 等於一條都擋不住，bypass 留空則連使用者自己也推不了（`docs/standards/known-drift.md` `L22`，與同檔 `R5` 同根：單一 git 身分封死的是**任何以 actor 為單位的授權設計**）。**本 repo 據此仍設了一條 ruleset，但要清楚它買到的是什麼**（MYL-62 裁定 A）：`handbook-version-tags`，target `tag`、enforcement `active`、bypass **留空**、只放 `creation` 一條規則、include `refs/tags/handbook-v*`。它擋的不是「誰」，而是「所有人」——包含使用者本人。買到的是兩項：**防誤推**（`git push --tags`／`--follow-tags` 掃到本地 tag 會被遠端以 `GH013` 拒收，而自律規則抓不到這種失誤）與**留痕**（要違規得先把一條看得見的 guard 切成 Disabled）。**買不到的是限制身分**：agent 這把 token 的 `repo` scope 就改得動 ruleset 本身（`PUT …/rulesets/{id}` 實測改得動 enforcement，`PATCH` 不支援、回 404），所以它是速度墊不是牆，`V1` 的標記**維持 `【自律】`**——別把「有一條 ruleset」讀成有了機械後盾。`V2` 有完整機械後盾（`gate` job ＋ `test_site_docs.py` 的反例測試）。`V3` 的機械後盾**是後盾不是前擋**：它擋在 `deploy` 之前，所以站上那一版原封不動，但 tag 在 git 上已經被移走了。`handbook-version-tags` 替它補了**半格**前擋：已發佈的 tag 被刪掉之後**再也建不回來**（`creation` 命中）。只有半格是因為那條 ruleset **刻意只放 `creation`**——**移動既有 tag（`push --force`）與刪除 tag 都不在規則內**，所以買到的是「不能重建」而不是「不能動」；要補滿得加 `update`／`deletion`，那是改既有 ruleset 的範圍，屬 `G-C`，沒有使用者裁定不要自己加。至於完整的前擋（分辨得出是誰在推）在本 repo 仍然做不出來，理由如上一段。另有一道**刻意留著的缺口**：`workflow_dispatch` 路徑不驗「tag 是否仍指向原本那顆 commit」，先移動 tag 再用 dispatch 重建仍會覆蓋。要擋得住得把來源 sha 記在 gh-pages 上，而 `mike` 的 `versions.json` 只有 `version`／`title`／`aliases`，不帶那個欄位；dispatch 只有具寫入權的人按得動，這一段因此歸人為判斷。`V4` **只有形狀那半有後盾，遞增規則那半完全沒有**：`tag_pattern: 'handbook-v*.*.*.*'` 讓位數不足的 tag（版本號只有一到三位，如 `v1`／`v1.1`／`v1.1.1`）判 `publish=false`、`deploy` job 整個不跑，那是真的擋得住的一格；但 `fnmatch` 只數點不看內容，**多一位（`handbook-v0.0.0.1.2`）與非數字（`handbook-v0.0.0.x`）都通得過**，而「這次該動哪一位」「進位有沒有歸零」更是一個字都驗不到——`d` 打成 `c` 不會有任何東西出聲，錯了又受 `V3` 保護改不掉。本 repo **刻意不補**來源專案那支互動選號腳本（`tag_release.py`）：那支的價值在多系列、高頻率打包，手冊一年發不了幾版，多一支要跟著 `V4` 一起維護的腳本，成本高過它擋得住的那點失誤。`【自律】`＋`【機械】`

### 版本號命名空間（MYL-71 增訂）

`V1`～`V4` 管的是手冊那一個版本號。但 repo 裡看得到的「v 開頭的號碼」遠不只它，而其中絕大多數**不歸這裡管、也不該被改成四碼**。本小節劃的是那條界線：哪些是本 repo 自己發的，哪些是別人發的、我們只是引用。

- `V5` **版本號命名空間**：本 repo 自己發的版本號**只有兩個**，形狀刻意不同，因為它們回答的是不同的問題——
  - ① **手冊發行版本** `handbook-v<a>.<b>.<c>.<d>`（`V1`～`V4` 管），答「**我引用的那一版還在嗎**」；
  - ② **設定檔 schema 版本** `.foundry/config.yml` 的 `foundry`，**單一整數**，答「**我還解析得動嗎**」。權威在 `skills/foundry-platform/config-schema.md`，只在**不相容變更**時 +1，寫入者同該檔（agent 不得自行改）。**不要把 ① 的四碼形狀套到 ②**：相容性契約沒有「修訂號」與「建置號」可言，補上去的後三位永遠是 0，還會讓「遇到不認得的版本就停下報錯」這條判斷變複雜。
  - **repo 內的永久文件不設自有版本欄位。** 文件的版本就是 git sha；要表達「本文對照到規範的哪一版」用**指向 sha 的戳記**（現行實例：手冊四章的「最後對照 protocol ⟨sha⟩」，由 `handbook-stamp` 驗證），不要自訂號碼。手寫的版本欄位是**第二份真相，而且是必然漂移的那一份**——改文件時沒有人會記得回頭改欄位。同一條判準否決過 MYL-39 的「手抄快照」，也寫在 `tools/publish-docs/project_docs.py` 開頭（「機械投影不是第二份真相」）；一件事不能有兩套標準。
  - **提到手冊版本時一律用四碼形狀，佔位符只寫 `handbook-v<a>.<b>.<c>.<d>`。** 這條同樣約束**規則本體、腳本註解與錯誤訊息**——尤其是錯誤訊息，它出現的時機正是有人要決定下一個版本號的當下。
  - **下列版本號不歸本條管，且不得為了「形狀統一」去改它們**（改了會讓證據對不上）：第三方工具的 pin（`actions/checkout@v4`、`mike 2.2.0` 等）、工單與互動卡的識別碼及其修訂號（`ask:MYL-6:pilot-topic:v1`、「MYL-39 計畫 v5」）、里程碑名稱（`skills/foundry-platform/adapters/local-md.md` 的 `milestone: v1`）、反例測試裡刻意寫成違規形狀的字串、以及發佈審查記錄／反悔錄／pilot log 裡綁 commit sha 的歷史敘述。

**違反：**前半（`handbook-v` 的形狀）由 `foundry-lint --selfcheck` 的 `version-shape` 擋下，跑不過就 commit 不了——它只認那個字面前綴，不掃泛用的「v ＋數字」，因為掃得太寬的檢查紅字會被習慣性忽略（MYL-41 的教訓）。本條開條的主因正是它擋得住的那一類：`V3` 的內文與 `republish_decision()` 撞版本時吐出的錯誤訊息，兩處都在用 `V4` 之前的舊形狀舉例，而**規範與錯誤訊息示範錯的形狀，讀者照做就錯**。後半（不設自有版本欄位、豁免清單）**沒有任何工具會擋**，而且兩個方向的後果不對稱：漏管只是多一份必然漂移的第二真相；**誤管更難救**——把反例測試、綁 sha 的歷史證據「修正」成四碼，證據就對不上了，而且沒有人會發現，因為改完看起來更整齊。`version-shape` 的豁免清單是這一格唯一的機械化身，改它之前先問「這一處是本 repo 發的，還是我們只是引用別人的號碼」。`【自律】`＋`【機械】`

### push：跨平台專案的權限設定（MYL-9／MYL-27 增訂）

依已核可的 MYL-9 HLD §5，Tech Lead 的 push 權限下放規則如下。本 repo（agent-foundry）以上方 MYL-23 分級授權為準；**透過 `foundry-init`／`foundry-adopt` 導入 Foundry 的其他專案**，以該專案 `.foundry/config.yml` 的 `push` 段為準（schema 見 `skills/foundry-platform/config-schema.md`）：

| 動作 | 權限 | 依據 |
| --- | --- | --- |
| feature／docs 分支 push、開 PR | **Tech Lead 自動**（`push.branch_push: tech-lead` 時；含 CI 觸發）；設 `user` 即收回 | config `push.branch_push` |
| push main、force-push、tag 發佈 | **使用者當下同意，無例外**——`push.main_push` 只允許 `user`，其他值整檔拒用 | config `push.main_push` |
| 對外發佈（發佈網站、public repo、套件） | **使用者當下同意**——關卡 C，不可調降（第 4 節） | `gates.external_actions` |

- 分支 push 下放僅及於**本單自己的工作分支**：push 前確認不會覆寫他人分支，push 後在工單留言記錄分支名與 PR 連結（有 PR 時）。
- 各專案的常設授權互相獨立：本 repo 的 P1／P2 授權（MYL-23）是使用者對本 repo 的裁定，**不自動延伸到其他專案**；新專案要放寬，走 foundry-gates／關卡 C 由使用者另行裁定。
- **本 repo 的已知例外（MYL-35 G7，使用者 2026-09-03 裁定選項 A）**：`push.main_push` 只允許 `user` 的硬約束**維持不放寬**（schema 未改）；但本 repo 依 MYL-23 P1「合併回 main 後 push origin 由執行者自行」這條授權，**寫不進設定檔**——它的權威來源是上方分級表這段規範文字，不是 `.foundry/config.yml`。此例外**僅對 agent-foundry 本 repo 成立**：`foundry-init`／`foundry-adopt` 導入的專案一律照 `push.main_push: user` 字面執行，main push 無例外，**agent 不得援引本 repo 前例替其他專案放行**。
- 歷史欠推的補推（一次推上大量既有 commit）不屬例行推送：首次補推需使用者明確同意後才納入常規（本 repo 已於 MYL-23 核可選項 A 時完成此程序）。

**違反：**援引本 repo 的例外替別的專案 push main，等於拿一個專案的授權去覆蓋另一個專案使用者的設定——對那位使用者而言，是他沒同意過的動作發生在他的 repo 上。另注意「其他值整檔拒用」目前**沒有實作**：沒有任何程式讀取 `.foundry/config.yml`，`push.main_push` 被改掉不會有任何反應。`【自律】`

### git 底層與危險操作

- 動到 git 底層（`stash`、`commit-tree`、`rebase`、直接改 ref、`filter-branch` 等）或其他可能吞掉工作內容的操作前，**先在隔離環境驗證機制**（`/tmp` 的臨時 repo 或 Docker），確認行為符合預期，才對工作中的 repo 執行。
- 特別注意：`git stash push` 不加 `-- <路徑>` 會捲走**所有**已追蹤變更，必須指定路徑。
- 改動 git 歷史屬破壞性操作，同時觸發第 4 節 HITL 閘門。

**違反：**工作內容直接消失，而且沒有備份可還原——`git stash push` 漏了 `-- <路徑>` 會捲走**所有**已追蹤變更，包含你這輪還沒 commit 的部分。這類操作沒有「先試試看再說」：試的那一次就是出事的那一次。`【自律】`

## 8. 模型與思考程度分層

依 MYL-12 討論結論訂定（MYL-13 增訂）。目標：讓每張工單用「足夠但不過度」的模型與思考程度執行，省下的預算留給真正難的工作。

### 三層預設（依「角色 × 工作類型」綁定）

| 層級 | 模型／思考程度 | 預設適用 |
| --- | --- | --- |
| 高 | 當下可用的最高層級／最高思考程度（現為 Opus 級／`max`） | Tech Lead 的設計（HLD／LLD／ADR）、Code Reviewer 的審查、CEO 的裁決與規範修訂 |
| 中 | Opus 級／`high` | Developer 的實作、QA 的測試、Product Analyst 的需求、**Frontend Verifier 的前端驗證** |
| 低 | Sonnet 級／`medium` | Scrum Master 的機械性流轉：狀態機維護、依模板拆單、巡檢兜底；**PM 的狀態彙整與派工** |

> 各層具體對應（2026-09-03 經使用者於裁定卡 `ask:MYL-33:model-tier-rejudge:v2` 重新裁定，取代同日同步卡 `ask:MYL-13:model-tier-sync:v1`）：高＝`claude-opus-5`／`max`、中＝`claude-opus-5`／`high`、低＝`claude-sonnet-5`／`medium`。
>
> 前次裁定的高層 `claude-fable-5` 因方案額度用盡退場（MYL-33）。此次起高層與中層**同模型、以思考程度區分**：`effort` 實際支援 `low｜medium｜high｜xhigh｜max`（adapter 內建說明字串只寫到 `high`，已過時；adapter 原樣傳給 CLI 不做驗證）。

- 分層綁的是「角色做自己的本職工作」。角色偶爾做出層級外的工作（例：Scrum Master 要做缺陷收容判定這類需要推理的事），依下方升級規則調整，不必改預設。
- **Frontend Verifier 與 PM 兩列的性質不同**（MYL-73 增訂）：**Frontend Verifier 是登記現況**——平台上的實際設定就是中層（`claude-opus-5`／`high`），本次只是把既有事實寫進表裡，沒有變更。**PM 是建議值**——理由是它的本職（跨單狀態彙整、依報告結論派工）屬機械性流轉，與 Scrum Master 同性質；遇到需要推理的判斷依 `M1` 個案升級，不改預設。依「絕不自作主張採用建議值」，PM 這一格在使用者核可前只是待確認選項，**不得據以設定平台**。

### 升級規則（逐條可判定）

1. `M1` **同一條 AC 連續失敗兩次 → 升一級思考程度。** 第三次嘗試前把思考程度升一級（`low`→`medium`→`high`），並在工單留言記錄：哪一條 AC、兩次失敗的證據、升級後的層級。
2. `M2` **跨模組介面或安全敏感範圍 → 直接高層級，不等失敗。** 判準（任一成立即觸發）：改動會變更兩個以上模組共用的介面（函式簽名、API 契約、資料格式）；或觸及認證、授權、密鑰、權限、金流、個資。
3. `M3` **升級後同一條 AC 仍失敗 → 轉 `blocked`，不得無限重試。** 依第 2 節 `blocked` 規則留言：附各次失敗證據、標明需要誰裁決（通常是 Tech Lead 重看設計，或使用者裁定），等待解除；不得自行降級再試或換個說法重跑。

升級只影響「這張工單接下來的嘗試」，不回寫預設；若同類工作反覆觸發升級，代表預設分層要修——開單修改本節，不要在個案裡默默長期加碼。

**違反：**同一條 AC 用同一層級重試到第三、第四次，燒掉的預算換不到不同的結果——失敗的原因不會因為再試一次就變了。`M3` 沒遵守則工單無限重試、卡在 `in_progress` 而不轉 `blocked`，於是沒有人知道它正在等一個裁決。`【自律】`

### 供應商維度（MYL-36 增訂）

上面兩段管的是「用多強的模型」；本段管的是「用**哪一家**的模型」。兩者互相獨立：換供應商不改層級，升層級不換供應商。

使用者裁定的目的（`ask:MYL-36:platform-routing:v1`）是**觀點互補**——不同服務商的模型有不同盲點，讓實作與審查落在不同家，等於用第二種視角覆蓋第一種看不到的地方。不是為了省額度，也不是為了吞吐；這一點決定了下列條款的判準。

1. `M4` **實作與審查不得同一供應商。** 前提兩項同時成立時適用：可用供應商 ≥2 家（以 `tools/model-routing/probe_providers.py` 的輸出為準，不憑印象），且專案已啟用路由（`.foundry/config.yml` 有 `model_routing` 段）。成立時，同一張工單的 Developer 與 Code Reviewer 不得是同一家；只有一家可用時本條**不適用**（是條件未成立，不是違規），在工單留言記一句即可。
2. `M5` **額度耗盡：停下、發卡、不自行降級。** 撞到某供應商的額度或用量上限時：(a) 不重試、不指數退避——額度牆不會因為換個說法而消失；(b) **不得自行改模型或改供應商續跑**，含 CLI 的 fallback 旗標（已實測無效，見 `docs/standards/known-drift.md` 反悔錄 R1）；(c) 走 `foundry-model-routing` 步驟 1 盤點替代供應商，產方案發卡；(d) 臨時改派必須在卡上寫明改回的時機，否則臨時值會靜悄悄變成新預設。
3. `M6` **供應商切換一律經使用者裁定。** 變更任何角色的供應商屬公司層設定變更，觸發 `H6`：`foundry-model-routing` 只負責盤點、產方案、發卡、執行、驗證，**不負責決定**，且不得先改再問。目前**沒有常設授權**；要給予（類比第 9 節 push 的 `P1`／`P2` 分級）走規範修訂在本條登記，未登記前每次都要發卡。

**違反：**實作與審查落在同一家時，審查看不到的盲點正好就是實作看不到的那些——審查照樣會 APPROVED，只是那層保護從一開始就不存在。撞到額度牆還自行換供應商續跑，則臨時值會靜悄悄變成新預設：沒人記得改回來，因為沒有任何地方記著它是臨時的。`【自律】`

執行細節（五個步驟、路由政策表、各平台怎麼落實指派）在 `skills/foundry-model-routing/SKILL.md`；本節只定規則。

### 權威來源與同步

- **本節是分層規則的權威來源。** 執行平台上各 agent 的模型設定（Paperclip＝`adapterConfig` 的 `model`／`effort`）是本節的映射；兩者不一致時，以本節為準並發起同步，而不是改本節遷就現況。
- 變更平台上 agent 的模型設定屬公司層設定變更，依第 4 節 HITL 閘門第 6 條處理：發卡列出「角色 → 目標 model／effort」對照表，經使用者核可（或由使用者執行）後生效，並在對應工單留言留下同步證據。
- 模型代號會隨版本演進（實際環境可能提供高於 Opus 級的模型）。本節固定的是「三層相對關係與角色歸屬」；各層對應的具體模型代號以同步卡裁定為準，裁定後回寫到上方表格附註，後續模型換代時開單重新裁定並更新附註。

## 9. 組織結構與匯報線

依 MYL-12 討論結論訂定（MYL-14 增訂，MYL-73 補登記 Frontend Verifier 與彙整型 PM）。

### 現行結構

```
使用者
└── CEO
    ├── Product Analyst（需求）
    ├── PM（交付彙整與派工）
    ├── Scrum Master（流程）
    ├── Frontend Verifier（前端驗證）
    └── Tech Lead（技術）
        ├── Developer
        ├── Code Reviewer
        └── QA Engineer
```

- CEO 直轄五個：Product Analyst、PM、Scrum Master、Frontend Verifier、Tech Lead。
- **開發三角（Developer、Code Reviewer、QA Engineer）掛在 Tech Lead 下**：三角內的技術爭議（瑕疵判定異議、設計缺漏、修法歧見）先上報 Tech Lead 裁定，不直接找 CEO；Tech Lead 裁不了、或問題涉及需求取捨／優先序／花錢／對外，再上升 CEO 或依第 4 節發卡問使用者。
- **Frontend Verifier 掛在 CEO 下，不在開發三角內**（使用者於 MYL-37 裁定建置，MYL-73 補登記）：它是「代替使用者操作瀏覽器」的執行手，待驗對象橫跨 Developer 的實作與 QA Engineer 的測試計畫，掛在其中任一邊都會讓它變成該邊的自我驗證。它**不核可自己的驗證結果去推進關卡**，關卡核可權依第 4 節。
- **PM 是彙整型，不是 stream owner**（使用者於 MYL-61 裁定，卡 `f80e66b3` Q1）：兩種型態的差別、各自的觸發條件與現況見下節。平台側的 agent 由 MYL-79（T7）建置，在那之前 PM 只存在於本節——這屬下方 `O1` 的第 1 種情形（規範有、平台沒有），已有工單承接，不必另開單。

### 匯報線與流程鏈的關係

第 3 節的流程鏈（需求→設計→工單→實作→審查→測試）是「工作交接」順序；本節是「管理與爭議升級」歸屬。兩者互相獨立：Scrum Master 拆單交棒給 Developer，不表示 Developer 匯報給 Scrum Master；Code Reviewer 掛在 Tech Lead 下，不影響其 Verdict 的獨立判定權。

### 兩種 PM 型態（MYL-73 改寫）

「加 PM」不是一件事而是兩件。兩者解的問題、數量、觸發條件都不同，**不得互相援引**：

| 型態 | 解什麼問題 | 幾個 | 現況 |
| --- | --- | --- | --- |
| **stream owner** | 流太多，CEO 的時間被跨流協調吃掉 | 每條流各一個 | **未觸發**，不預先建置 |
| **彙整型（Delivery Manager）** | CEO 的 context 被原始材料占滿，彙整品質與決策品質互相排擠 | 全公司一個 | **已採用**（MYL-61 卡 `f80e66b3` Q1） |

`O2` **stream owner 的觸發條件不因彙整型 PM 的採用而改變**，仍是以下兩項同時滿足才啟動：

1. 同時有 ≥2 條獨立 feature 流在進行。
2. CEO 的時間主要花在跨流協調，而非單流內的裁決。

觸發時由 CEO 開單提案（含各流的 stream owner 人選與職責切分），經使用者核可後修訂本節並同步 agent 設定；未觸發前不預先建置。**上列兩項現在都不成立。**

彙整型 PM 的位置：讀執行層的機器面（工單、留言、run 記錄、看板、CI）產出結構化報告，讓 CEO 的輸入從原始材料換成報告；偵測異常（無主的待辦、沒有解除路徑的 `blocked`、同一單被起了兩個 run、對帳紅燈）；並依報告結論執行派工。**不做需求取捨、不改 AC、不裁技術爭議、不直接對使用者發卡**——那四項分屬使用者、Scrum Master、Tech Lead、CEO。角色判準寫在 `skills/roles/pm/SKILL.md`，本節只定它在組織裡的位置。

**違反：**把「採用了彙整型 PM」讀成「stream owner 的觸發條件滿足了」，下一次真的出現 ≥2 條流時就不會有人再開那張提案單——規範看起來已經加過 PM 了。反方向是在未觸發時照 stream owner 的規格建置：為每條不存在的流各配一個負責人，多出來的轉手成本沒有對應的協調需求撐著。`【自律】`

### 決策權矩陣

目標（MYL-12 使用者裁定）：使用者長期只保留三類決定——**錢與權限、對外動作、產品方向**；其餘決定由下表的拍板者在對應章節的判準內消化，裁不了才沿升級路徑走。

常規流程中，這三類保留決定的執行形式就是第 4 節的三個抽象關卡（A 規格、B 方案、C 對外／不可逆）；本表其餘格子則是關卡之間的中段執行決策——已下放各拍板者，使用者只收摘要（MYL-9／MYL-27 增訂）。

| 決策類型 | 拍板者 | 判準依據 | 升級路徑（裁不了時） |

| 需求內容、範圍取捨、優先序 | **使用者** | 第 4 節 | —（本身就是終點） |

| 關卡粒度調整（A／B 的核可者與跳過條件） | **使用者**（foundry-gates 盤點建議、使用者確認寫入） | 第 4 節 | —（關卡 C 不可調降，無調整路徑） |
| **錢與權限、對外動作中的 P3 級（新開公開資源等）、常設授權的給予／收回、產品方向** | **使用者專屬** | 第 4、7 節＋本節分級表 | — |

判讀規則：

- 表中拍板者在依據章節的判準內**自行決定、不發卡**——把已授權的決定推回使用者，同樣違反本節（過度上報與越權裁決都是缺陷）。
- 只有兩種情況離開自己的格子：判準覆蓋不了（沿升級路徑走），或觸發第 4 節 HITL 閘門（錢／對外／破壞性／平台權限之外）。
- **「依賴鏈」與「派工」是兩格、兩個拍板者。** 排依賴鏈與指派是兩個獨立動作：Scrum Master 決定鏈怎麼排並自行設定，PM 決定誰做哪一張並執行指派。兩者不互為前提——**已實測：排依賴鏈不需要指派權限**（MYL-73 AC0，2026-09-05，本 repo 執行層），所以 Scrum Master 不必持有指派權也完成得了自己那一格的決定。換平台時這一句要重驗，結果記在該平台 adapter 的「平台限制」。
- **本表的拍板者歸屬沒有平台層的機械後盾。** 本 repo 執行層實測顯示，指派工單的權限旗標並未在 API 層強制（`docs/standards/known-drift.md` `L23`）：「派工歸 PM」是規則層的授權邊界，靠自律維持，不是靠平台擋住其他角色。
- 本表是既有章節的索引與補全，與各章衝突時以各章原文為準並開單修表。

**違反：**兩個方向各有代價。過度上報把已經下放的決定推回使用者，本節「使用者長期只保留三類決定」的目標直接失效；越權裁決則相反——使用者在不知情下失去了那三類本該保留的決定，而且通常要到結果出來才發現。`【自律】`

### 權威來源與同步

- **本節是組織結構的權威來源。** 執行平台上各 agent 的匯報欄位（Paperclip＝`reportsTo`）是本節的映射。
- `O1` **兩者不一致時，先判斷缺口在哪一邊，不要一律往平台端修**（MYL-73 釐清）：
    1. **規範有、平台沒有** → 依本節同步平台（建置 agent 或改匯報欄位）。這是「以本節為準」原本要講的那一種。
    2. **平台有、規範沒有** → **正解是補登記進本節，不是把 agent 從平台移除。** 判準：查得到建置來源的裁定（工單／互動卡）就補登記，並在本節註明來源；**查不到來源才發卡問使用者**該登記還是該移除。
    3. 兩種方向都屬公司層設定變更，依第 4 節 HITL 閘門處理：未經使用者裁定的結構調整先發卡提案；已裁定的結構（如本節）由執行工單直接同步，並在工單留言留下同步證據。
- **判例**：Frontend Verifier 是使用者在 MYL-37 裁定建置、掛在 CEO 下的，但直到 MYL-61 盤點才發現它在本文與手冊出現 0 次。照舊寫法的字面（「以本節為準」）辦，會得到「把它從平台移除」——那等於在沒有任何裁定的情況下推翻一個裁定。MYL-73 依第 2 種情形補登記。
- **違反：**照字面把「以本節為準」讀成「平台上多出來的一律移除」，刪掉的會是使用者親自裁定建置的 agent，而且刪的人有規範可以引——這種錯不會被任何檢查擋下，要到使用者發現某個角色不見了才會知道。反方向的代價是規範持續落後現況：規範沒寫的東西沒有人維護它的模型層、權限與 skill，於是它會慢慢漂到沒有人說得清它該做什麼。`【自律】`

## 10. 上下文預算與減法原則（MYL-36 增訂）

Context 是**有限且共用**的資源：載進來的每一段都排擠了後面真正需要的內容，而且讀錯段落比沒讀更糟——會拿舊規則當現行規則用。本節的條款一律可判定。

### 讀取規則

- `C1` **大檔禁止整份載入。** 超過 **20KB** 的文件先用 `grep -n` 定位段落、再局部讀（`sed -n 'A,Bp'` 或帶 offset 的讀取）。本檔是本 repo 最大的一份，多數工單只需要其中一到兩節。**現值自己 `ls -l`，本條不寫死大小**——寫在散文裡的 KB 數沒有人會回來改，只會愈漂愈遠（MYL-42 已為同一理由把數字移出入口檔 §4，MYL-47 收掉這裡的殘留）。達門檻的完整清單由入口檔（`CLAUDE.md`／`AGENTS.md`）§4 的表維護，漏列會被 `--selfcheck` 的 `big-files` 擋下。
- `C2` **先用結構定位，不要線性掃。** 進入陌生檔案的順序固定：`grep -n '^#\{1,3\} '` 取標題地圖 → 選定目標節 → 只讀該節。
- `C3` **交接與引用一律給路徑，不貼內文。** 交接包、工單留言、審查報告引用文件時寫 `檔案:行號` 或 `檔案 § 節名`，不整段複製——複製出來的那份會過期，且下一個 agent 仍得回頭讀原檔確認。（本條原列於第 3 節通用規則，收攏至此統一表述。）
- `C4` **一次聚焦一張工單。** 不為了「順便看看」載入與當前 AC 無關的模組。順便發現的問題依第 5 節開單或回報，不當場擴大讀取範圍。

### 減法原則

- `C5` **先給最小必要上下文，不滿意才補。** 常見失敗是想先準備「完美的規格書」再開工；正確做法是用最小輸入讓執行者跑一輪，**只有在對輸出不滿意時才針對缺口補充**。「不提供多餘資訊」與「提供必要資訊」同等重要——多餘的資訊會稀釋指令、製造矛盾，而矛盾會觸發 `H2`。
- 本原則不豁免第 1 節的工單骨架要求：AC 與 Inputs 該齊還是要齊。減的是**背景材料**，不是**判準**。

**違反：**整份載入一個大檔會排擠掉後面真正需要的內容，而**讀錯段落比沒讀更糟**——會拿舊規則當現行規則用，且完全沒有自覺。多餘的背景材料則稀釋指令、製造矛盾，而矛盾回頭會觸發 `H2`，等於自己替自己製造了一個閘門。`【自律】`

## 11. 規則 ID 索引（MYL-36 增訂）

本文的可判定條款除了節號之外，另有**穩定 ID**。節號會隨增訂而變動，ID 不會：工單留言、審查報告、lint 規則、其他 skill 一律優先引用 ID（例：「違反 `H3`」而非「違反第 4 節第 3 點」）。

| ID 前綴 | 含義 | 定義所在 |
| --- | --- | --- |
| `G-A`／`G-B`／`G-C` | 三個抽象關卡 | 第 4 節 |
| `H1`～`H6` | 觸發式 HITL 閘門 | 第 4 節 |
| `D1`～`D4` | 缺陷收容判定 | 第 5 節 |
| `A1`～`A4` | 文檔權威階序操作規則 | 第 6 節 |
| `W1`／`W2` | 永久文件 vs 一次性意圖紀錄 | 第 6 節 |
| `P1`～`P3` | push 權限分級 | 第 7、9 節 |
| `M1`～`M6` | 模型升級規則（`M1`～`M3`）與供應商路由（`M4`～`M6`） | 第 8 節 |

| `V5` | 版本號命名空間與豁免範圍 | 第 7 節 |

規則：

- **ID 只增不改、不回收。** 條款作廢時保留 ID 並註明「已作廢，由 `X` 取代」，不得把 ID 讓給新條款——舊工單裡的引用會指到錯的規則。
- 新增可判定條款時，同時在本表登記前綴與範圍。
- `tools/foundry-lint/foundry_lint.py --selfcheck` 會核對：repo 內出現的規則 ID 引用是否都在本表宣告的範圍內、且在對應章節有定義。

**違反：**ID 被回收或改掉時，舊工單與審查報告裡的引用會指到另一條規則——而引用者不會發現自己讀的是別條，錯得無聲無息。這條有部分後盾：ID 打錯、或新條款忘了在本表登記，`--selfcheck` 的 `rule-ids` 檢查會擋下（pre-commit 全域觸發，跑不過不給 commit）；但**「把已作廢的 ID 讓給新條款」它擋不到**，因為前後兩份都是合法登記，那一段只能靠自覺。`【機械】`
