# foundry-gates：關卡粒度調整 workflow

依已核可的 MYL-9 HLD §4.2 制定。三個抽象關卡（A 規格核可、B 方案核可、C 對外／不可逆核可）的定義與執行語意見 `skills/foundry-protocol/SKILL.md` 第 4 節；`gates` 欄位的唯一 schema 權威是 `skills/foundry-platform/config-schema.md`。本文是跨平台純 .md workflow：不依賴特定 runtime，任何 agent（或人）照本文逐步執行即可。

## 0. 邊界與進入模式

- 本 workflow **只讀寫 `.foundry/config.yml` 的 `gates` 段**。其他段落不歸本 workflow 管：
  - `push` 段的調整屬關卡 C／protocol 第 7 節的範圍，不得藉本 workflow 夾帶。
  - `platform` 與檔案的首次建立是 `foundry-init`／`foundry-adopt` 的職權（見 §4 第 3 點）。
- 兩種進入模式：
  - **獨立執行**：任何時點可跑，四步全走。
  - **被 foundry-init 呼叫**：專案尚無歷史工單，**跳過步驟 1**、直接走步驟 2–4；建議值用 schema 預設起手（見 §2 末條）。
- 任何角色都可以執行盤點與建議（那是分析工作），但**寫入的唯一授權來源是使用者在步驟 3 的明確選定**。agent 不得以任何其他理由改動 `gates` 段——這條同時寫在 config-schema.md 與 protocol 第 4 節。
- 硬性約束（本文重複三處是刻意的）：**關卡 C（`gates.external_actions`）不可調降**，建議層（§2）與寫入層（§4）都要各自擋一次。

## 1. 步驟 1：盤點

產出物：**關卡現況表**。

1. 讀專案根目錄 `.foundry/config.yml`：
   - **檔案存在** → 依 config-schema.md 驗證。非法（缺必填、枚舉值錯、`external_actions` 非 `user`）→ 停止並回報問題；修復動作本身也要走完本 workflow 的確認步，不得「順手修好」。
   - **檔案不存在** → 現況視為「未設定」：三關卡依 protocol 第 4 節預設值（A＝使用者、B＝使用者且無跳過、C＝使用者）記入現況表，並註明「無設定檔」。
2. 讀近期工單紀錄：用 `foundry-platform` 的 `list_issues` 加上工單留言／互動卡歷史（平台有互動卡紀錄就用互動卡；沒有就用留言中的核可紀錄）。取樣範圍建議「近 30 天」或「最近 20 單」取樣本較大者。
3. 把每筆核可紀錄歸類到關卡 A／B／C 或**觸發式 HITL 閘門**。閘門（protocol 第 4 節：花錢、對外、破壞性、平台權限之外……）不屬關卡、**不是本 workflow 的調整對象**，但要單獨列一行，避免誤歸進關卡樣本。
4. 現況表欄位：`關卡｜現行核可者｜樣本數（發卡次數）｜平均等待｜通過率（照建議通過的比例）`。
5. 任一關卡樣本數 < 3 → 標「樣本不足」，該關卡在步驟 2 一律建議「維持現狀」。

## 2. 步驟 2：建議

產出物：**建議設置＋逐關卡理由**。判準：

- **B 方案核可**：近期樣本 ≥ 10 筆、全數照建議通過、且平均等待構成可感知成本 → 可建議 `design_approval` 改物件形式並設 `skip_below: small`。樣本不足、有退件、或等待成本可忽略 → 建議維持。樣本接近但未達判準（如 7／7 全過）→ 可以列為「可選項」，但理由欄必須寫明樣本未達判準，不得包裝成強烈建議。
- **A 規格核可**：需求裁定是使用者的核心價值點，**預設不建議調降**；只有使用者已明確把某類選題常規委任（有工單紀錄可引）時，才可建議改 `ceo`／`tech-lead`。
- **C 對外／不可逆核可**：**唯一合法建議值是 `user`**。禁止產出任何調降 C 的建議——即使歷史 100% 通過、即使等待極短、即使使用者曾口頭抱怨麻煩，都只能在報告註明「C 不可調降（protocol 第 4 節寫死）」。這是硬性約束的第一層防線。
- 建議值只能落在 schema 枚舉內（核可者：`user`｜`ceo`｜`tech-lead`；`skip_below` 僅 `small`）。枚舉之外的想法（例如 medium 以上跳過、新增核可者角色）不得成為建議；要提，開規範修訂單走 protocol 第 9 節。
- **被 foundry-init 呼叫時**（無歷史）：建議＝schema 預設（A `user`、B `user`、C `user`），並把「B 是否啟用 `skip_below: small`」列為開放選項交使用者選，不預作傾向。

## 3. 步驟 3：確認——絕不跳過

產出物：**現況 vs 建議差異表＋使用者的明確選定**。

1. 差異表欄位：`關卡｜現況｜建議｜差異｜理由｜影響`。「影響」要寫成使用者看得懂的行為變化（例：「掛 size:small 的工單不再發 HLD 核可卡，由決策權矩陣拍板者自動過」）。無差異的關卡也要列，標「無變更」。
2. 發互動卡給使用者選定：
   - **平台有互動卡機制**（如 Paperclip 的 `ask_user_questions`）→ 差異表放進工單留言，卡上列選項：照建議全收／維持現狀／部分採納或自訂（自由填寫）。
   - **無互動卡機制** → 把差異表輸出成 .md 報告（建議路徑 `.foundry/gates-review-<YYYY-MM-DD>.md`），請使用者在報告或工單上批示，等到明確回覆為止。
3. 鐵律（與 protocol 第 4 節同條）：**卡未回覆前不得寫入**。「建議很合理」「上次也是這樣選」「只是小改」都不構成跳過本步的理由。使用者部分採納，就照部分採納的內容寫入，不多不少。
4. 等待期間工單轉 `in_review`（或無平台時明確標記等待中）；逾時未回不得代答，只能提醒。

## 4. 步驟 4：寫入

產出物：**更新後的 `.foundry/config.yml` ＋ 變更紀錄**。

1. **寫入前防線（硬性約束第二層）**：選定結果若含 `external_actions` 非 `user`——不論來源是誤操作、自由填寫還是任何人的指示——**拒絕寫入該欄**，回報「此條 protocol 寫死不可調」，其餘合法選定照寫。發現既有檔案的 `external_actions` 已非 `user`，視為非法檔，停止並回報（同 §1）。
2. 只改 `gates` 段，檔案其他段落逐字保留。
3. **檔案不存在時本 workflow 不建整檔**——`platform`、`push` 等必填欄位是 foundry-init 的職權。把使用者選定結果完整記錄在工單留言，指引跑 `foundry-init`；init 首次產檔時把該選定帶入。被 foundry-init 呼叫的模式下，則由 init 統一寫檔。
4. 寫入後驗證：重讀檔案、依 config-schema.md 檢查合法性；不合法立即還原並回報，不得留下半套設定。
5. 留紀錄：在對應工單留言（`foundry-platform` 的 `comment` 動詞）寫明——每個變更欄位的「前值 → 後值」、確認卡識別碼（或批示位置）、日期。config 在版控內的專案照常 commit，commit／push 授權依該專案現行規則，不因本 workflow 而放寬。

## 5. 驗收自查

結束前逐項核對，缺一項就不算跑完：

- [ ] 四步各有產出物：現況表（init 模式免）／建議＋理由／差異表＋使用者選定／寫入與紀錄（或「不建檔、選定已記錄」的替代路徑）。
- [ ] 確認步有使用者明確選定的證據（卡片回覆或批示），不是 agent 自行推定。
- [ ] `gates.external_actions` 前後皆為 `user`。
- [ ] 寫入後（若有寫入）config 依 config-schema.md 驗證合法。
