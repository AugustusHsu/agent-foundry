# foundry-init：新專案初始化導入

依已核可的 MYL-9 HLD §6.1 制定。本文是跨平台純 .md workflow：任何 agent runtime（Claude Code、Codex 等）或人類照本文逐步執行即可，不依賴特定 runtime 功能。Claude Code 可把本檔安裝為 slash command（`/foundry-init`）作為可選增強；缺了照樣能照文檔人工跑。

## 0. 邊界與詞彙

- **適用對象**：乾淨的新專案——目標目錄**沒有** `.foundry/config.yml`、沒有既存的 Foundry 骨架。發現下列任一情況即停止並改走對應流程：
  - `.foundry/config.yml` 已存在 → 專案已導入。調關卡走 `foundry-gates`，增開模組走 `foundry-adopt`（S5）。
  - 目標路徑已有 `skills/foundry-*` 或 `templates/` 且內容與來源不同 → 可能是開發中專案，走 `foundry-adopt`；**不得覆蓋既有檔案**。
- **`<SRC>`**：本 skill 所在的 agent-foundry checkout 根目錄（本檔位於 `<SRC>/skills/foundry-init/`）。所有複製動作的來源都是 `<SRC>`，複製前記下其 commit sha 供報告引用。
- **`<TARGET>`**：要導入的專案根目錄。github 模式下必須是已存在的 git repo 且 remote 指向目標 GitHub repo；local-md 模式可以是無 remote 的目錄（尚非 git repo 時先 `git init`——純本地動作，可自動執行）。
- **互動方式**：平台有互動卡機制（如 Paperclip）→ 發卡；無 → 在對話中詢問，或輸出 .md 報告請使用者批示。等到明確回覆為止，不得代答。
- 本 workflow 產生的檔案一律進 `<TARGET>` 版控（步驟 5 收尾 commit）；push 依該專案現行授權規則，本 workflow 不放寬。

## 1. 步驟 1：詢問平台＋前置檢查

1. **發卡問使用者**，一張卡問齊三件事（減少往返；依 protocol 第 4 節，後兩件屬使用者裁定的授權邊界，不得由 agent 預設代選）：
   - **平台**：`github` 或 `local-md`。不得自行猜測（foundry-platform §1 第 5 點）。
   - **branch push 權限**（`push.branch_push`）：`user`（每次 push 都問）或 `tech-lead`（分支 push＋開 PR 自動）。這是常設授權的給予，屬關卡 C，只能使用者拍板；卡上未選視同 `user`。
   - **平台側資源建立同意**（僅 github 模式需要）：卡上明列步驟 3 將建立的資源——標準 label 集、milestone 容器、名為「Foundry」（或使用者指定標題）的 ProjectV2＋三個 view。此欄的同意即 protocol 決策點 7（平台動作）的授權證據；未同意前不得執行步驟 3。
2. **前置檢查**（依選定平台，任一項不過就停下回報，不得帶病續跑）：
   - **github**：`gh` 已安裝且 `gh auth status` 通過，token scopes 含 `repo` 與 `project`（缺 `project` 時請使用者跑 `gh auth refresh -s project`——互動式授權，agent 不能代跑）；`jq` 可用；`<TARGET>` 是 git repo 且 `gh repo view` 解析得到目標 repo。
   - **local-md**：`<TARGET>` 目錄可寫；尚非 git repo 時 `git init`。無其他外部依賴。

## 2. 步驟 2：產生 `.foundry/config.yml`＋複製 protocol／templates

1. 再次確認 `<TARGET>/.foundry/config.yml` 不存在（存在即停，見 §0）。
2. 依 `<SRC>/skills/foundry-platform/config.example.yml` 為底、`config-schema.md` 為準產生 `<TARGET>/.foundry/config.yml`：
   - `foundry: 1`；`platform`：步驟 1 選定值；`platform_options`：github 填 `project_title`／`project_owner`（未指定用預設），local-md 填 `id_prefix`（未指定用 `FND`）。
   - `gates`：**先寫 schema 預設**（A `user`、B `user` 無跳過、C `user`）——預設值未放寬任何授權，可不經卡直接寫；使用者的實際選定由步驟 4 帶入。**例外**：目標專案已有經使用者確認、記錄於工單的 gates 選定（foundry-gates §4 第 3 點「不建檔、選定已記錄」的替代路徑），直接帶入該選定寫檔、毋須重新發卡，報告引該確認卡識別碼。
   - `push`：`branch_push` 填步驟 1 選定值；`main_push: user`（寫死，同 `external_actions` 不可調降）。
   - 檔首加註解記錄產生來源：`# generated by foundry-init from <SRC repo> @ <commit sha> on <YYYY-MM-DD>`。
3. 複製流程檔到 `<TARGET>`，**保持與 `<SRC>` 相同的相對路徑**（各 skill 之間以相對路徑互引，搬位置會斷）：
   - `skills/foundry-protocol/SKILL.md`
   - `skills/foundry-platform/`（全目錄：SKILL.md、adapters/、config-schema.md、config.example.yml）
   - `skills/foundry-gates/SKILL.md`
   - `templates/`（全目錄）
   - 不複製：`skills/foundry-init/`（目標專案用不到）、`skills/roles/`（組織分工屬 agent-foundry 自身設定，MYL-14 範疇）。
4. 逐檔規則：目標檔不存在 → 複製；已存在且內容相同 → 跳過；已存在且不同 → 停止並回報（見 §0）。
5. 驗證：`.foundry/config.yml` 依 config-schema.md 逐欄檢查合法（必填齊、枚舉值合法、`external_actions` 與 `main_push` 皆 `user`）；複製清單逐檔存在。

## 3. 步驟 3：呼叫 adapter `init_structure`

1. github 模式先核對步驟 1 卡上的平台側資源建立同意已取得；local-md 模式全屬本地檔案操作，無需額外同意。
2. 依 `<TARGET>/.foundry/config.yml` 的 `platform` 載入 `skills/foundry-platform/adapters/<值>.md`，照其 `init_structure` 一節逐步執行（在 `<TARGET>` 工作目錄內）。
3. 照該 adapter 的**查證**條目驗證：github＝`type:*` label 計 8、project 建立成功；local-md＝三個 view 檔與 `milestones.md` 存在。重跑一次確認冪等（無報錯、內容不變）。
4. **github 模式的人工步驟**：Status 欄位補選項（In Review／Blocked／Cancelled）與三個 view 的建立目前無 API，須在網頁完成（adapter 文檔步驟 4–5）。把這些列成待辦清單放進步驟 5 的報告，不算 init 失敗——但報告必須明列，不得靜默略過。

## 4. 步驟 4：呼叫 foundry-gates 設定關卡

1. 依 `skills/foundry-gates/SKILL.md` 的「被 foundry-init 呼叫」模式執行：**跳過步驟 1（盤點）**，直接走步驟 2–4——建議＝schema 預設，「B 是否啟用 `skip_below: small`」列為開放選項交使用者選，不預作傾向；步驟 3 確認卡照 gates workflow 發，**卡未回覆前不得寫入**。
2. 使用者選定後由本 workflow 統一寫檔（gates §4 第 3 點）：只改 `gates` 段，其他段逐字保留；寫後依 config-schema.md 重新驗證。
3. 步驟 2 的例外已帶入既有選定者，本步整步跳過（選定已是使用者確認過的，不重複發卡），報告註明出處。
4. 硬性約束（與 gates workflow 同條，兩處各擋一次）：`gates.external_actions` 只允許 `user`，任何來源的其他值都拒寫。

## 5. 步驟 5：初始化報告＋下一步指引

產出 **初始化報告**（.md；有工單系統就貼工單留言，無則存 `<TARGET>/.foundry/init-report-<YYYY-MM-DD>.md`），內容：

1. **摘要**：平台、`<SRC>` commit sha、執行日期、執行者。
2. **產出清單**：config 路徑與各欄最終值（gates 選定含確認卡識別碼或既有選定出處）、複製的檔案清單、`init_structure` 建立的平台側資源與查證結果。
3. **待辦**：github 模式的人工步驟清單（§3 第 4 點）；其他未竟事項。
4. **下一步指引**（連到說明層網站 foundry-handbook <https://augustushsu.github.io/foundry-handbook/>）：
   - 首次上手與日常指令 → 第 1、2 章（first-run、commands）
   - 開發流程與工單骨架 → 第 3 章（workflow）
   - 三關卡與決策點對照 → 第 4 章（decision-points）
   - 常設 workflow（gates 調整等）→ 第 7 章（workflows）
5. 收尾 commit：把本次新增的所有檔案（`.foundry/`、`skills/`、`templates/`、報告）在 `<TARGET>` commit（gitmoji 風格、繁中標題）；push 依該專案 push 授權規則，未授權就停在本地並於報告註明。

## 6. 驗收自查

結束前逐項核對，缺一項就不算跑完：

- [ ] 步驟 1 有使用者的平台選定與（github 模式）平台側資源建立同意證據；前置檢查全過。
- [ ] `.foundry/config.yml` 依 config-schema.md 驗證合法；`external_actions` 與 `main_push` 皆 `user`。
- [ ] 複製清單逐檔在 `<TARGET>` 存在且與 `<SRC>` 一致；未覆蓋任何既有檔案。
- [ ] `init_structure` 查證通過且重跑冪等；github 模式的人工待辦已列入報告。
- [ ] gates 段是使用者選定（確認卡回覆或既有選定紀錄），非 agent 推定。
- [ ] 初始化報告已產出並含下一步指引；新增檔案已 commit。
