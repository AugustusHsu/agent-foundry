# foundry-ai-platform：軸 A 能力面與降級規則

依 MYL-78 制定，源頭是使用者在 MYL-61 卡 `f80e66b3` Q4 的補充指示：

> 對於「換平台會有相同能力」方面，我的意思是對於 skill、組織關係、開發流程等等的需要紀錄下來，
> 換成像是 claude code 或是 codex 等等的平台的時候要盡可能有相同的能力……讓本專案的開發流程
> 能盡可能的和目前 paperclip 的開發流程有相同的能力。

所以本文的目標**不是把三個平台講得一樣好**，而是**讓落差可查、可降級、可留痕**：
換平台之前就知道哪幾步會掉、掉了改用什麼頂上、頂上之後拿什麼當證據。

## 0. 兩條軸，本文管哪一條

| 軸 | 管什麼 | 設定欄位 | 權威 |
| --- | --- | --- | --- |
| **軸 A：AI 平台** | agent 在哪個殼裡跑、被誰喚醒、組織長在哪 | `ai_platform` | **本文** |
| **軸 B：文檔與協作工具** | 工單／狀態／看板／文檔面在哪 | `devtools_platform`（＋`docs` 段） | `foundry-platform` |

兩軸**正交且可自由組合**（Codex＋GitHub、Claude Code＋Paperclip……）。
第三個相關但不同的東西是**模型供應商**（`model_routing`，管「哪一家的模型在跑這個角色」），
權威在 `foundry-model-routing`；它與軸 A 的關係見 §6 最後一條——**軸 A 會限縮它的可行值域**。

⚠️ 本文**不定義任何抽象動詞，也不改既有動詞的定義**。軸 A 現在有一個動詞
`provision_team`（MYL-77 增訂，把 `.foundry/org.yml` 的宣告套到平台上），但**它的權威在
`foundry-platform` §8，不在本文**——本文的形狀仍是**能力矩陣＋降級規則**，
不是「介面＋adapter」。新增一個 AI 平台要做的是填滿 §3 的一欄（見 §7），不是覆蓋九個動詞
——那是軸 B 的完整性定義，別套過來；`provision_team` 同樣不適用「寧缺勿殘」，
做不到就走 §4 的 `AP-4`（同 `foundry-platform` §5 的 MYL-77 裁定）。

## 1. 什麼時候載入本文

| 觸發 | 情境 | 進入點 |
| --- | --- | --- |
| `AP-T1` **導入／盤點** | `foundry-init` 步驟 1、`foundry-adopt` 步驟 1 要問或要盤點 `ai_platform` | §2 → §3 |
| `AP-T2` **某步做不到** | 流程走到一半發現當前平台缺某項能力 | §4 找對應降級規則 |
| `AP-T3` **新增 AI 平台** | 要把 Foundry 帶到第四個平台 | §7 |
| `AP-T4` **改雙入口檔** | 要動 `CLAUDE.md`／`AGENTS.md` 的分工或新增入口檔 | §5 |

不屬本文範圍：換模型供應商或撞額度上限（走 `foundry-model-routing`）、
瀏覽器能力的實際探測與補齊（走 `foundry-browser`，本文只在 §3 引用它的判級結果）。

## 2. 能力面：九項，以及 Foundry 的哪一步靠它

分兩組。**這個分組是本文最重要的一件事**——不分組就會得出「Paperclip 樣樣都行」的錯誤結論。

- **甲組（工具面）**：agent 手上有哪些工具。由**實際在跑的那個殼**提供。
- **乙組（編排面）**：誰派工、誰喚醒、怎麼問人。由**AI 平台本身**提供。

| 代號 | 能力 | Foundry 流程的哪一步靠它 |
| --- | --- | --- |
| `CAP-1` | **載入角色規範** | 每個 agent 開工前掛 `foundry-protocol`（唯一豁免＝CEO，`O3`）＋自己的角色 skill。缺了就沒有共同規則 |
| `CAP-2` | **局部讀檔** | context 預算 `C1`～`C5`：超過 20KB 的檔禁止整份載入，要能 `grep` 定位再讀區間 |
| `CAP-3` | **執行指令** | `make check`、`foundry_lint --selfcheck`、以及軸 B 九個動詞的全部指令（`gh`／`curl`／檔案操作） |
| `CAP-4` | **向使用者提問並取得裁定** | `H1`～`H6` 觸發式 HITL、三個關卡 `G-A`／`G-B`／`G-C`、`P3` push 授權。**全流程最關鍵的一項**——缺了它，所有需要人拍板的關卡都會變成 agent 自己說了算 |
| `CAP-5` | **被指派＝被喚醒** | 第 3 節六態流轉與交接鏈：Developer → Code Reviewer → CEO 每一棒都靠「指派把下一個人叫起來」 |
| `CAP-6` | **子代理／多角色並行** | 第 9 節組織：九個角色分工、`M4` 實作與審查異廠 |
| `CAP-7` | **背景任務** | CI、發佈腳本、`probe_providers.py`／`browser-probe` 等長跑盤點 |
| `CAP-8` | **瀏覽器／視覺** | Frontend Verifier 的驗收、手冊發佈後的實站比對（判級與補齊規則在 `foundry-browser`，本文不重複） |
| `CAP-9` | **版控操作** | 第 7 節 git 規範：一單一分支、gitmoji commit、`P1`～`P3` push 分級 |

甲組＝`CAP-1`／`CAP-2`／`CAP-3`／`CAP-6`／`CAP-7`／`CAP-8`／`CAP-9`；乙組＝`CAP-4`／`CAP-5`。

⚠️ 分組切的是「**這項能力由誰提供**」，而那個答案**跟平台有關**：`CAP-1`／`CAP-6`／`CAP-7`
在 `claude-code`／`codex` 上確實是殼給的工具（所以歸甲組），在 `paperclip` 上卻是平台的編排面
自己在做。§3 的 `paperclip` 欄因此有三格例外，讀表前先看該節須知第 1 點。

## 3. 對照表：四欄 × 九項

**格式**：✅ 原生支援｜⚠️ 降級（附 §4 規則編號）｜❌ 做不到｜❓ 未驗證。
**先讀這三句，否則會誤讀整張表**：

1. **`paperclip` 欄的甲組多半是「借來的」。** Paperclip 自己不提供工具，它**生一個 adapter**
   （本 repo 現為 `claude_local`）去跑，所以 `CAP-2`／`CAP-3`／`CAP-8`／`CAP-9` 填的是
   「＝所生 adapter」而不是 ✅——把這四格讀成「Paperclip 原生支援」是錯的。
   **另三格是 ✅ 而且不是筆誤**：`CAP-1`（skill 由 runtime materialize 後進 context）、
   `CAP-6`（多 agent 各自獨立 run）、`CAP-7`（heartbeat run）在 Paperclip 上**根本不經過殼**，
   換掉 adapter 它們還在，所以填平台自己的實況。這三格是 §2 分組在本欄的例外，不是反例——
   分組的歸屬本來就隨平台而變（見 §2 末的警語）。
2. **`claude-code` 在軸 A 上是轉發層。** 它不持有工單、不持有喚醒機制、不持有組織：
   乙組兩項它都拿不到，要靠底下的軸 B 或真人推動。**它與 Paperclip 不對等**，
   表面上甲組更漂亮只是因為它就是那個被生出來的殼。
3. **`codex` 欄大量是 ❓。** 本 repo **從未在 Codex 上跑過任何一輪 Foundry 流程**，
   證據等級見 §3.1。❓ 一律是「沒驗過」，不是「不支援」，也不得當成「應該可以」使用。

| 代號 | 能力 | `paperclip` | `claude-code` | `codex` | 其他／無工具（人工） |
| --- | --- | --- | --- | --- | --- |
| `CAP-1` | 載入角色規範 | ✅ runtime materialize 後自動進 context | ⚠️ `AP-3`：`CLAUDE.md` 自動進，skill 要自己讀 | ⚠️ `AP-3`：`AGENTS.md` 自動進，skill 要自己讀 | ⚠️ `AP-3`：人自己讀 |
| `CAP-2` | 局部讀檔 | ＝所生 adapter | ✅ `Read` 帶 `offset`／`limit` | ❓ 未驗證（一般 shell 可 `sed -n 'A,Bp'`） | ⚠️ 人自己翻 |
| `CAP-3` | 執行指令 | ＝所生 adapter | ✅ `Bash` | ❓ 未驗證 | ⚠️ 人自己下 |
| `CAP-4` | **提問並取得裁定** | ✅ 互動卡（`POST /interactions`，三種 kind） | ❌ **無互動卡** → `AP-1` | ❌ **無互動卡** → `AP-1` | ❌ → `AP-1` |
| `CAP-5` | **指派＝喚醒** | ✅ 指派即喚醒（`S7`） | ❌ **無**（無工單、無排程） → `AP-2` | ❌ **無** → `AP-2` | ❌ → `AP-2` |
| `CAP-6` | 子代理／多角色並行 | ✅ 多 agent，各自獨立 run | ⚠️ `AP-4`：有子代理，但同一 session 同一身分 | ❓ 未驗證 | ❌ → `AP-4` |
| `CAP-7` | 背景任務 | ✅ heartbeat run | ⚠️ `AP-6`：背景指令限單次 session 生命週期 | ❓ 未驗證 | ❌ → `AP-6` |
| `CAP-8` | 瀏覽器／視覺 | ＝所生 adapter（`.mcp.json` 綁情境不綁人，`GAP-5`） | ⚠️ 三把鑰匙齊了才有（`L8`），判級走 `foundry-browser` | ❓ 未驗證（見 §3.1 第 3 點） | ❌ → 走 `foundry-browser` §2.4 |
| `CAP-9` | 版控操作 | ＝所生 adapter | ✅ `Bash` 下 git | ❓ 未驗證 | ⚠️ 人自己下 |

### 3.1 證據等級

同 `adapters/gitlab.md` 附錄 B 的作法——**每一欄講清楚它憑什麼這樣填**：

1. **`paperclip`＝實跑**。本 repo 自 MYL-6 起全部流程都在 Paperclip 上執行，
   表中每一格都有工單紀錄可回溯。
2. **`claude-code`＝實跑，但一直是被 Paperclip 生出來的**。本 repo 的 `claude_local`
   adapter 生的就是 Claude Code，甲組七項全部實際用過。**乙組兩個 ❌ 是推導不是實測**：
   推導依據是它在本 repo 從來沒有自己持有過工單或喚醒別人——每一次喚醒都來自 Paperclip。
   **獨立安裝的 Claude Code（不掛 Paperclip）在本 repo 未曾跑過。**
3. **`codex`＝未跑過，一格實測都沒有**。工作區裡有一份**未進版控**的
   `.codex/config.toml`，內容是 `.mcp.json` 那兩個瀏覽器 MCP server 的 TOML 版
   （`[mcp_servers.<名稱>]`）。**那是一份宣告，不是一次驗證**：沒有任何 Codex run
   的紀錄，也沒有人確認過它載得起來。因此 `CAP-8` 的 codex 格仍是 ❓。
   ⚠️ 順帶一提，它未進版控這件事本身是個缺口——同一組瀏覽器能力現在要用兩種格式各宣告一次，
   而且只有 `.mcp.json` 那份跟著版控走，兩份漂了不會有任何地方報錯。該檔的處置權在使用者，本文不代決。
4. **「其他／無工具」＝定義而非觀測**。這一欄是「一個人拿著這份 repo 照做」的下限，
   格子填的是規則要求，不是某次實測。

## 4. 降級規則

**不能只寫「不支援」。** 每一條都要能驗收，所以固定四欄：**降級成什麼／誰負責／證據長什麼樣／硬約束**。
證據的共同要求：**留在該工單的永久紀錄上**（`W1`／`W2` 的分界照舊——裁定本身是永久的，
過程摘要是一次性的）。唯一不用這個格式的是 `AP-5`，理由寫在該條。

### `AP-1` 沒有互動卡 → HITL 裁定怎麼取得並留痕

這是 AC3 點名的題目，也是**落差最大的一項**：`H1`～`H6` 與三個關卡全都靠它。

| | 內容 |
| --- | --- |
| **降級成什麼** | agent 產出一份**裁定請求**：一句話問題 ＋ 逐項選項 ＋ 每個選項的後果 ＋ 「不選會怎樣」。載體依軸 B 而定：GitHub／GitLab＝在該 issue 留言；`local-md`＝寫進 `.foundry/board/` 對應工單檔；完全無平台＝輸出 .md 檔請使用者批示 |
| **誰負責** | **提出請求的 agent 本人**，不得轉嫁。取得回覆後由**同一個 agent**把裁定抄回工單 |
| **證據長什麼樣** | ①使用者原話的引用區塊（不是轉述、不是摘要）②來源位置（留言 URL／檔案路徑／commit sha）③時間。三者缺一不算數 |
| **硬約束** | **等到明確回覆為止，不得代答、不得逾時自動採用預設值。** 「鐵律：絕不自作主張採用建議值」在任何平台都成立，沒有互動卡不是放寬它的理由。`G-C`（對外／不可逆）在降級狀態下**一樣不可調降** |

⚠️ 降級後**真正會掉的東西是「擋不擋得住」**：互動卡在 Paperclip 上會讓 run 停下來等，
留言不會。所以降級狀態下這一步從【機械】變成【自律】——導入報告要明寫這句，不要讓人以為換平台沒有代價。

### `AP-2` 沒有「指派＝喚醒」 → 交接鏈怎麼走

| | 內容 |
| --- | --- |
| **降級成什麼** | 交接改為**兩段式**：①把工單狀態與 assignee 改成下一棒（讓看板是對的）②**另外用一個真的會通知到人的管道**告知。沒有這種管道時，交接鏈**退化為單人依序扮演**——同一個人依 protocol 第 3 節的順序，一個角色做完換下一個角色的判準重讀一次 |
| **誰負責** | 交出這一棒的 agent；單人模式下由該人自己維持角色切換的紀律 |
| **證據長什麼樣** | 工單上一則交接留言，寫明：交給誰、下一步做什麼、通知走的是哪個管道（或「單人模式，無通知」） |
| **硬約束** | 單人依序扮演時，**`M4`（實作與審查異廠）失效**——同一個人同一個模型不可能異廠。導入報告必須明列這一條失效，不得靜默略過 |

### `AP-3` 沒有 skill 自動載入 → 角色規範怎麼進 context

| | 內容 |
| --- | --- |
| **降級成什麼** | 把 `skills/foundry-protocol/SKILL.md` 與自己的角色 skill 當**一般檔案讀進來**。⚠️ 仍受 `C1`～`C5` 約束：protocol 是全 repo 最大的一份，**先 `grep -n '^#\{1,3\} '` 取標題地圖再讀需要的節**，不要整份載 |
| **誰負責** | 開工的 agent 自己，開工第一件事 |
| **證據長什麼樣** | 該輪工作的第一則留言或報告載明「已讀入哪幾節」 |
| **硬約束** | 目標專案**沒有 `AGENTS.md` 就先補**——這是換到非 Claude 殼的硬前置（原寫在 `foundry-model-routing` §3.2，MYL-78 起以本條為準） |

### `AP-4` 沒有子代理／只有單一身分 → 角色分工怎麼維持

| | 內容 |
| --- | --- |
| **降級成什麼** | 一人分飾多角，**靠「換角色就重讀該角色 skill」做隔離**，而不是靠記憶。每次換角色在工單留一行「以 `<角色>` 身分接手」 |
| **誰負責** | 執行者本人 |
| **證據長什麼樣** | 工單上每次角色切換各一行，且該角色的產出符合其角色 skill 的判準 |
| **硬約束** | 分飾多角**不會產生第二個觀點**。`M4` 的目的是觀點互補，單身分下它只是形式上成立——`G-B`／`G-C` 該問使用者的照問，不得以「已自審」代替 |

### `AP-5` 沒有瀏覽器／視覺

⚠️ **本條刻意不用上面的四欄格式**，因為它不自己定規則：判級（L0～L3）、補齊（三把鑰匙）、
補不了怎麼降級與怎麼寫報告，全部以 `foundry-browser` 為準（該 skill §2.4 就是降級條款）。
本文只負責兩件事：①在 §3 的 `CAP-8` 列標出各平台的起點；②提醒**判級不得憑設定檔外觀**，
要跑 `make browser`（`L8`）。

⚠️ **本條有一個可攜性前提**：它指到的兩樣東西必須真的在該專案裡——
`skills/foundry-browser/SKILL.md`（規則本體）與 `tools/browser-probe/`（`make browser` 的腳本）。
`foundry-init` §2 第 3 點的複製清單兩項都已列入（MYL-78 補），導入時漏帶就等於本條無法執行。

### `AP-6` 沒有背景任務 → 長跑工作怎麼辦

| | 內容 |
| --- | --- |
| **降級成什麼** | 改為**前景執行並接受阻塞**，或拆成「啟動」與「稍後查結果」兩張工單 |
| **誰負責** | 發起該長跑工作的 agent |
| **證據長什麼樣** | 指令的完整輸出（截斷要註明），或第二張工單的編號 |
| **硬約束** | **不得用輪詢等待冒充背景執行。** 前景阻塞就誠實寫成阻塞、拆單就誠實開第二張單；輪詢只會把一次長跑變成一串看起來有在動、實際上什麼都沒推進的 run |

## 5. 雙入口檔的維護規則

`CLAUDE.md` 與 `AGENTS.md` 是軸 A 目前**唯一**的機械化落點，規則正式化如下。

| 段落 | 範圍 | 規則 |
| --- | --- | --- |
| **共用正文** | `<!-- FOUNDRY:SHARED-BODY:BEGIN -->` 與 `:END` 之間 | **兩檔逐字相同**，由 `--selfcheck` 的 `entry-sync` 機械比對。改一份就要改另一份 |
| **各 harness 專屬** | `:END` 之後的「§8 工具名對應」 | 各自不同，**無機械比對**——只有這一段允許分岔 |

- **哪些東西屬 §8（可分岔）**：文件裡的中性說法在該殼裡叫什麼（「載入 skill」「局部讀取檔案」
  「執行指令」「發互動卡」「slash command」）。**判準：只換說法、不換規則。**
  一句話若在別的殼裡**字面上不成立**，它屬 §8；若只是做法不同但要求相同，它屬共用正文。
  （同 `foundry-platform` §5 最後一條對 adapter 的判準，刻意一致。）
- **絕不放進 §8 的**：任何規範內容。§8 是對照表不是規則層——規則進 protocol 或本文。

### 新增一個 AI 平台要動哪些檔

先問一題：**它讀不讀 `AGENTS.md`？**

- **讀**（Codex 及多數通用 harness）→ **不新增入口檔**。只在 `AGENTS.md` §8 的表格加列／加註，
  並填 §3 對照表的新欄。這是預設路徑。
- **不讀，堅持自己的檔名** → 才新增第三個入口檔。此時要動的是：
  1. 新入口檔本身（共用正文逐字照抄，接上自己的 §8）
  2. `templates/entry-file.md` 增一個 §8-x 區塊
  3. **`tools/foundry-lint/foundry_lint.py` 的 `check_entry_sync`**——⚠️ 它目前
     **寫死只比對 `CLAUDE.md` 與 `AGENTS.md` 兩個檔名**。不改它，第三份入口檔的共用正文
     **漂了不會有任何地方報錯**。這是已知的機械層上限，寫在這裡免得日後有人以為自檢會兜住。
  4. 若新檔 ≥12KB，還要進共用正文的大檔清單（`big-files` 會擋）

## 6. 誠實上限

**只在 Paperclip 成立、換平台就沒有的：**

- **指派＝喚醒。** GitHub／GitLab 的 issue 指派**不會喚醒任何 agent**（`S7`，
  也是 `foundry-platform` §7 對照表的最後一列）。整套「交接鏈自動往下跑」建立在這一條上，
  它是 Foundry 目前**最不可攜的一件事**——降級走 `AP-2`。
- **互動卡會讓 run 停下來等。** 其他平台的留言不會擋住任何人（`AP-1`）。
- **一張工單可以掛結構化的 blocker 並在解除時自動送喚醒事件。** 這是 Paperclip 的排程能力，
  留言慣例模擬得了語意、模擬不了喚醒。

- **把 `org.yml` 的宣告變成一支真的存在的團隊。** 軸 B 的九個動詞裡沒有任何一個是「建組織」；
  補這個缺口的是軸 A 的 `provision_team`（`foundry-platform` §8，MYL-77 增訂），而它
  **只在有 agent 註冊表的平台上跑得動——軸 A 三個值裡只有 Paperclip 有**。
  所以**可攜的是那份宣告，不是那支團隊**：`claude-code`／`codex` 上 `org.yml` 一字不改仍然
  合法、`org-sync` 照樣綠，但它從那一刻起只是一份約束人的文件，降級走 `AP-4`。

**任何平台都做不到（不是換平台就會好）：**

- **per-role 模型供應商路由在單 session 的殼上沒有承載處。** `ai_platform: claude-code`
  或 `codex` 時，一個 session 就是一家供應商，`model_routing` 的 per-role 設定**無處落地**——
  這不是 bug，是軸 A 對模型供應商可行值域的**限縮**。要真的異廠只能開兩個 session 分別扮演，
  且該狀態下 `M4` 只是形式成立（同 `AP-4` 的硬約束）。
- **瀏覽器工具綁情境不綁人。** `.mcp.json`／`.codex/config.toml` 放在 repo 裡，
  該 repo 的所有 agent 都拿得到（`GAP-5`）。這在每個殼上都一樣。

## 7. 新增一個 AI 平台的檢查清單

1. 在 `config-schema.md` 的 `ai_platform` 枚舉補值（**只有這一處是枚舉權威**）。
2. 填滿 §3 對照表的新欄——**九項全填**，未驗證就寫 ❓，不得留空、不得推論。
3. 在 §3.1 補一段該欄的證據等級。
4. 依 §5 決定要不要新增入口檔，照該節清單動檔。
5. 有任何一項是 ⚠️ 或 ❌ 時，確認 §4 有對應的降級規則；沒有就補一條（四欄格式）。
6. 跑 `python3 tools/foundry-lint/foundry_lint.py --selfcheck` ＋ `make check`。

⚠️ **本文沒有「全覆蓋否則不得上線」的門檻**，這與軸 B 刻意不同：軸 B 少一個動詞會讓流程當場斷掉，
軸 A 少一項能力則是**降級**——只要 §4 有規則、報告有寫，帶著缺口上線是允許的。
把軸 B 的「寧缺勿殘」套到軸 A 會讓每個平台都不合格，那不是誠實，是把標準訂到沒人用得了。
