    6. 團隊是怎麼編制的？¶

    最後對照 protocol 316f06e（2026-09-06）

    本章記錄 MYL-12 討論、MYL-14 落地、MYL-61／MYL-73 改寫、MYL-96／MYL-115 重整的組織結構決議。規則本體在 skills/foundry-protocol/SKILL.md 第 9 節；本章解釋它對你（使用者）的意義。

    組織圖¶

    你（使用者）
└── CEO ─────────────────── 你唯一的對口
    └── Product Manager ─── 開單中樞：單由它開、由它派
        ├── Product Analyst（需求）
        ├── Frontend Verifier（前端驗證）
        └── Tech Lead（技術）
            ├── Developer
            ├── Code Reviewer
            └── QA Engineer
    • CEO 只直轄 Product Manager 一個。 CEO 維持薄：它讀報告、做決定、對你發卡，不讀原始材料。
    • Product Analyst、Frontend Verifier、Tech Lead 掛在 Product Manager 下。
    • 開發三角（Developer、Code Reviewer、QA Engineer）掛在 Tech Lead 下，位置沒變。
    • Frontend Verifier 不在開發三角內。理由：它要驗的東西橫跨 Developer 的實作與 QA Engineer 的測試計畫，掛在其中任一邊就變成那一邊的自我驗證。它是你在 MYL-37 裁定建的，MYL-73 補寫進規範（過程見下面「規範落後現況時怎麼辦」），MYL-115 從 CEO 底下改掛 Product Manager。

    這對你有什麼影響¶

    1. 你的對口不變：一律對 CEO 說話（見第 2 章），不需要理解內部匯報線。
    2. 技術爭議不會吵到你面前：Developer 與 Code Reviewer 對瑕疵判定有異議、實作發現設計缺漏，這類技術面爭議由 Tech Lead 裁定收斂；只有涉及需求取捨、優先序、花錢、對外的問題才會以互動卡的形式升到你這裡（清單見第 4 章）。
    3. 匯報線 ≠ 流程鏈：第 3 章的交接順序（需求→設計→工單→實作→審查→測試）照舊，不因組織結構改變。Product Manager 拆單交棒給 Developer，走的是流程鏈；Developer 的匯報對象仍是 Tech Lead。

    哪些決定會回到你手上¶

    長期只有三類（MYL-12 你的裁定）：

    1. 錢與權限——任何會產生費用或變更權限的動作，含常設授權的給予、擴大、收回。
    2. 對外動作——push main／force-push／tag、新開公開資源、發布、公開任何東西（protocol 第 9 節分級表的 P3 級）。你已透過 MYL-23 核可把 P1（例行推送）與 P2（手冊公開鏡像同步）改為常設授權自動執行——P1 的判準是「這次推送有沒有讓新的東西變成公開」，不是 repo 本身公開與否（MYL-59；這個 repo 現在是 public，但推一條工作分支不會多公開任何東西）；跨平台專案中，分支 push＋開 PR 依 .foundry/config.yml 下放 Tech Lead（MYL-9）。
    3. 產品方向——需求內容、範圍取捨、優先序。

    常規流程中，這三類決定的執行形式就是第 4 章的三個關卡（A 規格、B 方案、C 對外／不可逆）。其餘決定都有明文的拍板者：技術選型歸 Tech Lead、拆單方式／依賴鏈／AC 修改歸 Product Manager、派工歸 Product Manager、審查結論歸 Code Reviewer、缺陷成因工單判定歸 Tech Lead、技術爭議歸 Tech Lead 裁定、分支 push＋開 PR 歸 Tech Lead（跨平台專案）。完整的「誰拍板、裁不了怎麼升級」矩陣在 foundry-protocol 第 9 節。如果你被問到矩陣內已授權的決定，可以直接回「這由 {角色} 依規範決定」，把決定推回去。

    Product Manager 是做什麼的？跟以前說的「不加 PM」是不是矛盾？¶

    不矛盾，但要說清楚是哪一半改了。「加 PM」不是一件事而是三件：

    stream owner 彙整型（Delivery Manager） 開單中樞（現在這一個）
    解什麼問題 流太多，CEO 的時間被跨流協調吃掉 CEO 的 context 被原始材料占滿 調度沒有下放：開單者近半是 CEO
    幾個 每條 feature 流各一個 全公司一個 全公司一個
    現況 還沒觸發，不預先建置 已被開單中樞吸收 現行（你在 MYL-96 核可卡上選的）

    你在 MYL-61 的裁定卡上寫過「PM 是彙整型、現階段不加管理層」。MYL-96 改的是後面那半句，不是前面那半句：

    • 仍然有效：PM 不是 stream owner。stream owner 的觸發條件沒有改——(1) 同時有 ≥2 條獨立 feature 流在進行；(2) CEO 的時間主要花在跨流協調。這兩項現在都還不成立，真的觸發時 CEO 會開單提案、發卡請你裁定。
    • 已被取代：「不加管理層」。實查顯示彙整型 PM 上線之後，開單者仍有近半是 CEO、而 PM 一張單都沒開過——「把 PM 加進來」沒有變成「把 PM 放到中間」。所以這次把它放到中間。

    實際差別：以前別的角色想開單就自己開；現在要開單先找 Product Manager，由它判斷後自己開、自己指派。拆單方式、依賴鏈、工單 AC 修改也一併歸它（原本歸 Scrum Master）。彙整報告那一段沒有取消，只是不再是它唯一的工作。它不做需求取捨、不裁技術爭議、也不直接對你發卡——要問你的事一律經 CEO。

    「只有三個人能開單」是查出來的，不是擋下來的¶

    開單者的白名單是你、CEO、Product Manager 三者（你在 MYL-96 的卡上選的）。有一件事值得你知道，因為它決定了你看到的是什麼：

    • 平台上關不掉任何 agent 的開單權——實查它的權限開關裡沒有任何一把管得到「開單」。所以這條規則沒有閘門，違規的單開得出來；make check 的 開單者白名單 那一項是在事後把它報給你看。
    • 開出來之後也改不了作者——平台沒有這個操作。所以處置不是刪單，是把那張單交回 Product Manager 覆核，由它判要不要退回。覆核完成後，覆核者要在那張單留一則以 I1-覆核完成： 起頭的留言寫明判了什麼，make check 讀到它就不再報那一張。這一步聽起來像形式，但少了它整條規則會反過來咬人：作者改不了，紅字就永遠在，而這項檢查跑在每一次 commit 之前——一張違規的單會擋住每個人的每一次 commit，最後只會逼人把整項關掉。標記只認覆核者留的（Product Manager，或你自己）：讓違規的那位自己留一則，就等於自己特赦自己。標記也不會把違規抹掉——留言和作者欄都還在單上，消掉的只是那條紅字。
    • 平台自己開的單不算違規（例如它自動開的生產力審查單，那種單沒有作者）。規則裡明文寫了收容，不會拿它來吵你。
    • 規則生效前開的舊單不回溯：2026-09-06 當下有 37 張是別的角色開的，那些改不了，硬要算會變成永遠修不掉的紅字。

    另外一項是給 Product Manager 自己的：它開的每一張單，四個欄位在開單當下就要齊——指派給誰、掛在哪張母單底下、被誰擋住、驗收標準。這條的來源是你說的「開單要足夠詳盡明確、盡量避免多次來回」：少一欄，接單的人第一輪就得回頭問一次。make check 的 開單必備欄位 會盯著這幾格。

    「被誰擋住」那一格有兩種寫法都算數（其他三格都是「有填就過」）：依賴欄填得出來就填；填不出來的時候，在描述裡寫一行 **上游**：前置 MYL-97 已於 2026-09-05 結案，本單可獨立開工——要寫得出單號。會有第二種寫法，是因為這一格真正要回答的是「這張單從哪來、為什麼現在可以做」，而依賴欄回答的是「誰做完我才會醒」。多數時候是同一件事，但有兩種很常見的情況不是：前置在開單那一刻就已經做完了，或者上游根本是母單（那不能填，見下一段）。兩件事先說清楚：掛在哪張母單底下不能拿來抵這一格（它本來就是必填的，拿它抵等於這一格永遠算過），而那一行寫了什麼機械看不懂——它只認得「有沒有寫出單號」，寫一句空話它擋不住。

    原本還有第五格「擋住誰」，2026-09-07 拿掉了：那一欄開單的人填不動——依賴在平台上是一條邊、兩個看法，能寫的只有「被擋的那張單自己去填誰擋著它」。所以要讓一張單有下游，得等後來的單來填。取而代之的是一句沒有機械後盾的要求：開單當下已經知道要接著做的事，就把單一起開出來。

    同一項檢查還多看一格反過來的：母單不可以同時被填成「擋住自己的單」。平台不擋這件事，但兩邊會互等——母單等子單做完才結、子單等母單結了才醒——結果是一張再也不會被叫醒的單。單面上看起來欄位還是齊的，所以只能靠檢查報出來。

    第三條：agent 開的單都要掛得到樹上¶

    2026-09-07 加的（make check 的 上位單 那一項）。這一條只管 agent 開的單，你自己開的一張都不會被動到——這是你在 MYL-96 卡上定的。理由不是「你的單特別」，是你是從系統外面開單的，你的單就是這棵樹的根：要求它們掛到別的單底下，等於要求每個新目標都得先屬於某個舊目標。

    會有這條，是因為沒有母單的單不會報錯、也擋不住任何人，它只是從工作線上消失：看板按樹展開的時候它不在任何一條線底下，母單結案時沒有人會回頭看它，於是它既沒被做完、也沒被撤掉。這批單是這樣積出來的——沒有哪一張是有人決定讓它飄著，是每一張都少填了一格。

    之前積下來的 29 張已經在 2026-09-07 補掛完畢，每一張改成什麼、憑什麼，都逐張記在 docs/standards/issue-parent-backfill.md（那份不是規範，是給你事後查帳用的）。補的時候有一件事值得你知道：29 張裡沒有一張是真正無所歸屬的，每一張都在自己的描述裡指名了來源單——其中 15 張還是 CEO 開的。這說明 agent 開單基本上都是在對系統裡既有的東西作反應（某張單的審查意見、某次結案的溢出、實作時發現的缺陷），而那個「既有的東西」永遠是一張既有的單。

    規則仍然留了一個例外：真的掛不到任何一張單底下（它是一整條新工作線的起點），在描述裡寫一行 **頂層單**：<為什麼>，檢查讀到就放它過。但這個例外預期是空的——今天一張都沒有用到它。所以如果你在哪張單上看到這一行，那是值得問一句的訊號，不是常規寫法。

    這個訊號不用你自己去翻單：有誰用了這條例外，make check 會在「上位單」那一行的結尾把張數和單號印出來——放它過，但不讓它靜悄悄地過。之所以要這一格，是因為例外寫在描述裡，而描述誰都改得動、包括開單的 agent 自己；不印出來的話，一張單只要自己補一行「頂層單：因為我不想掛」就能讓紅字消失，而且沒有任何人會知道。上面那條「開單者」的收斂標記不同——它寫在留言、平台擋得住冒名，所以不需要這一格。

    還有一點與上面那條「開單者」不同，值得對照著看：母單這一格是改得動的（補掛 29 張就是這麼做的），所以違規的正解是把母單補上，不像作者那格改不掉、只能靠覆核標記收斂。也因此規則裡特別寫了一句：不要為了讓檢查變綠，把單掛到不相干的母單底下——那是把樹弄髒來換一個綠燈，而樹正是這條規則要保護的東西。

    想讓一張單先停著？要加 blocker，不能只用講的¶

    這一條是 2026-09-06 用一次實際的意外換來的，寫在這裡是因為它需要你配合一個動作。

    那天你交代「MYL-61 先處理完再動其他的」，agent 也照做了——但那張單在平台上的狀態一直是「進行中」，沒有任何東西擋著它。結果平台自己開的一張子單結案時，觸發了「子單全完成」事件，把它叫醒跑了一整輪，事後才有人發現它本來不該跑。

    留言擋得住 agent 自己往下走，擋不住平台把它叫醒——而叫醒它的那個事件不來自任何人的動作。所以規範現在明訂（protocol O5）：要讓一張單暫時不往下走，就替它加一個 blocker（在看板上設一條「被某張單擋住」的依賴關係），不是靠留言紀律。你只要交代一句話就好，把它落成 blocker 是 agent 的事；但如果你在看板上看到一張「說好要停、狀態卻還在跑」的單，那就是這一條沒有被執行，可以直接指出來。

    反過來也一樣：解除暫停是拿掉 blocker，不是宣布解除。而且理由消失時要先查還有沒有別的理由撐著——同一張單常常被不只一件事擋著。

    Scrum Master 去哪了¶

    它退場了，2026-09-08 完成。 MYL-96 裁定把它的工作併進 Product Manager（拆單、依賴鏈、AC 修改）與 Tech Lead（缺陷成因工單判定）。規範這一側（組織圖、決策權矩陣、.foundry/org.yml）先落地，平台那一側由你在 2026-09-08 00:22 按完。所以曾經有一段時間平台上查得到一個組織圖裡沒有的 Scrum Master——那一段已經結束，現在兩側一致：agent 名冊上是 8 名，沒有 Scrum Master。

    ⚠️ 這一節原本寫錯了一件事，值得你知道，因為它關係到你下次按哪顆鈕。 舊版說退場方式是 pause ＋ leave、「兩個動作都可以一鍵還原」——兩半都不對：

    • 實際按的是 pause ＋ Terminate，而 Terminate 不可逆。被 terminate 的 agent 再也 resume 不回來（伺服器會直接拒絕），它的 API key 也在那一刻全部作廢。
    • 面板上那顆名字看起來就是退場的 Leave agent，其實完全不動 agent——它只把那個 agent 從你自己的側邊欄收起來，agent 照樣在名冊上、照樣會被喚醒。

    所以下次要讓一個角色退場：想留退路就只按 pause（隨時 resume 得回來）；Terminate 按下去沒有回頭路，只有你按得動，agent 不會也不該替你按。技術細節與源碼依據在 docs/standards/known-drift.md 的 L35。

    規範落後現況時怎麼辦¶

    這一節是 MYL-61 盤點時撞到的實例，寫下來是因為它會再發生。

    Frontend Verifier 是你在 MYL-37 裁定建的，平台上一直都在，但規範與手冊裡一次都沒提過它。而第 9 節原本寫著「規範是權威來源，兩者不一致時以規範為準」——照字面辦，結論會變成「把 Frontend Verifier 從平台移除」，等於在沒有任何裁定的情況下推翻你的裁定。

    所以 MYL-73 把那條拆成兩個方向：

    • 規範有、平台沒有 → 去把平台補上。
    • 平台有、規範沒有 → 補寫進規範，不是把它從平台拿掉。查得到當初的裁定來源（工單／互動卡）就直接補登記；查不到來源才發卡問你。

    上一節的 Scrum Master 看起來像第二種，其實不是：查得到的那條裁定正好是要它退場的，所以它是「規範先行、平台後跟」，規範這邊不用補。

    結構與平台設定的對應¶

    Paperclip 上各 agent 的 reportsTo（匯報對象）設定是上面組織圖的映射。PM 曾經只存在於規範裡，2026-09-06 已在平台上建置完成，並在同日依 MYL-96 正名為 Product Manager；各角色除下述一處刻意保留的例外外，其餘逐格一致，是逐格核對過的（讀平台的實際權限與掛載，不是看設定面板的開關，那兩者會給出相反的答案）。

    那一處例外是 Frontend Verifier 的「可否指派工單」：平台上這個旗標解出來是開的，而規範沒有給它派工權。之所以留著，是因為關掉它的那支 API 是單向門——開過再關並不會回到原狀。至於「那誰能把它真正清乾淨」，這件事其實由兩半組成，而兩半的把握程度不一樣，所以分開講：agent 這一側動不了，是實測過的——MYL-79 審查期間以 agent 身分試過三支會動到成員權限的 API（改權限、改角色與授權、讀成員清單），三支全部被擋下來，一律回 403；「在面板上動得了」那一半，目前仍是推論——沒有人真的示範過，而且它只有你驗得到（要有你的面板身分才試得了），所以在你實際試過之前，那是目前最合理的猜測，不是已經確認的事實。實際影響是零：這個旗標本來就不是平台層的閘門（誰能派工是規則層的自律邊界），所以規範說了不算數的事，平台開著也不會有人去做。你在 MYL-79 決定不處理它，這是知情下的保留，不是漏同步。 其餘不一致仍依上一節的兩個方向處理。

    角色還沒建出來的那段期間，誰拍板¶

    規範先寫、平台後建，中間隔著幾張單——那段時間差本身是預期的。真正麻煩的是決策權矩陣裡那一格的人還不存在：矩陣說「派工由 PM 拍板」，但 PM 還沒建，於是每一次交棒都落進一個沒有主人的格子。MYL-73 期間就發生過一次，當時是執行者臨時自己裁定、寫在留言裡，下一棒讀不到。

    所以補了一條通則：拍板者尚未建置時，由他的匯報對象暫代，並在矩陣那一格註明暫代者與終止條件——承接建置的工單一結案就把註記撤掉。暫代不擴權：暫代的人只能在原本的判準內決定，不能順手改寫那一格的判準或升級路徑。

    這條寫成通則而不是「PM 的個案」，是因為個案寫法在 PM 建出來的當下就作廢了，而下一次任何角色先寫進規範、後建置時，同樣會撞到這一格。
