## 1. 系統脈絡

foundry-lint 是 `agent-foundry` repo 內的一個單機 CLI 工具，位於 `tools/foundry-lint/`。它在 Foundry 流程鏈（需求 → 設計 → 工單 → 實作 → 審查 → 測試）中扮演「交棒前自檢」的角色：各角色 agent 產出 `docs/` 下的交接文件後、依 foundry-protocol 第 3 節交棒前，執行 foundry-lint 判定文件是否含對應模板的全部必備章節。

與既有部分的互動只有兩條，且都是**唯讀**：

- **讀 `templates/`**（MYL-4 產出物）：六份模板檔是必備章節清單的唯一權威來源（BRD 第 5 節假設）。
- **讀受檢文件**：使用者以參數指定的任一 Markdown 檔（通常在 `docs/` 下）。

不呼叫任何網路服務（NFR-1）、不寫入任何檔案、不整合 CI／git hook（BRD 第 4.2 節明確不做）。

## 2. 架構與元件

單一可執行 Python 檔 `tools/foundry-lint/foundry_lint.py`，內部依職責切成四個元件（同檔內的函式群，不拆多檔——規模不值得）：

```
使用者指令
   │
   ▼
[CLI 入口] ──參數合法──▶ [規則來源] ──必備章節清單──▶ [章節檢查器] ──檢查結果──▶ [輸出器] ──▶ stdout/stderr + exit code
                              │                            │
                              ▼                            ▼
                        讀 templates/<type>.md        讀受檢文件
```

| 元件 | 職責 | 對應的 FR |
| --- | --- | --- |
| CLI 入口（`main`／argparse） | 解析 `--type`、`--format`、檔案路徑；參數不合法時以 exit 2 回報使用方式錯誤 | FR-3, FR-4 |
| 規則來源（`load_required_sections`） | 讀取 `--type` 對應的模板檔，抽出二級標題作為必備章節清單 | FR-2 |
| 章節檢查器（`extract_headings`＋`check`） | 讀取受檢文件、抽出二級標題、與必備清單比對，產出缺漏清單 | FR-1 |
| 輸出器（`render_text`／`render_json`） | 依 `--format` 輸出人類可讀文字或 JSON，並決定 exit code 0／1 | FR-4, FR-5 |

## 3. 技術決策（ADR）

三項決策均不涉及花錢、對外發佈或文件間規格矛盾，不觸發 foundry-protocol 第 4 節 HITL 閘門；技術選型權責依 BRD 第 5 節明文歸 Tech Lead 於本文定案。

### ADR-1：語言與執行環境選型

- **選項**：
  1. **Bash script**：零額外執行環境，但字串／陣列處理原始，實作 `--format json` 與多行標題比對極易出錯，測試困難。
  2. **Python 3（僅標準函式庫）**：`argparse`、`re`、`json`、`pathlib` 全在 stdlib，單檔即可完成；Linux 環境普遍內建，且本 repo 已用 mkdocs（Python 生態）建文件站，技術棧一致。
  3. **Node.js**：語言能力足夠，但 repo 現況無任何 Node 痕跡（無 package.json），會為一個小工具引入全新執行環境與版本管理負擔。
- **取捨**：Bash 省了執行環境卻把複雜度轉嫁到最不擅長的字串解析上，可維護性最差；Node 功能等價於 Python 但違反「與既有技術棧一致優先於新穎」的選型立場；Python stdlib 兼顧零依賴（NFR-1 離線可執行）、可測試性（stdlib `unittest`）與棧一致性，代價僅是要求環境有 `python3`（mkdocs 已隱含此前提）。
- **結論**：**Python 3（≥3.9），僅用標準函式庫，單檔實作**。不引入任何第三方套件，不需要 `pip install`，`python3 tools/foundry-lint/foundry_lint.py` 即可執行。

### ADR-2：規則定義方式

- **選項**：
  1. **規則寫死在程式碼**：六種類型的必備章節清單以常數維護在程式內。
  2. **執行期解析 `templates/`**：每次執行時讀對應模板檔，動態抽出必備章節。
  3. **產生式規則檔**：以腳本從模板產生 rules.json 進版控，執行期讀規則檔。
- **取捨**：選項 1 執行最快、不依賴模板檔存在，但模板一改就與規則脫鉤，違反 BRD 第 5 節「模板是唯一權威來源」假設，且 BRD 要求 HLD 確認「規則與模板的同步機制」——寫死等於把同步交給人腦。選項 3 有規則檔可審閱，但引入「產生步驟忘了跑」的新失敗模式，兩份真相。選項 2 讓規則與模板**結構上不可能脫鉤**（同步機制＝不存在需要同步的副本），代價是模板檔讀不到時工具無法運作（以 exit 2 明確回報，屬合理行為）、以及對模板標題格式有依賴（見 ADR-3 與第 6 節風險）。
- **結論**：**執行期解析 `templates/<type>.md`**，模板即規則，無任何副本需要維護。

### ADR-3：必備章節的判定粒度與比對規則

- **選項**：
  1. **二級標題（`## `）逐字比對**：模板的每個二級 ATX 標題即一個必備章節；受檢文件須有標題文字完全一致的二級標題。
  2. **全層級標題比對**：一、二、三級標題全數列為必備。
  3. **寬鬆比對**：忽略編號（「1.」）或做模糊比對。
- **取捨**：選項 2 不可行——六份模板的一級標題（`# BRD：{功能／專案名稱}`）與三級標題（`### FR-1：{功能名稱}`、`### ADR-1：{決策標題}`）含 `{}` 佔位文字或屬可重複項，無法逐字要求；已逐一檢視六份模板，**二級標題全部是固定文字、無佔位符**（含 review-report 的 `## Verdict`），恰好構成穩定的必備集合。選項 3 的模糊比對會讓「過／不過」判定失去可預期性，與單級嚴格度（缺＝不過）的需求精神相悖，且實作與說明成本都更高。選項 1 規則最簡單、可預期、對照模板肉眼可驗，代價是文件標題須與模板逐字一致（含編號）——這正是「模板為權威」要的行為。
- **結論**：**必備章節＝模板中的二級 ATX 標題，逐字比對**（忽略 `##` 後空白數與行尾空白；圍欄程式碼區塊內的行不視為標題）。細節規格見 LLD 第 3、4 節。

## 4. 資料流

單一主流程（一次執行檢查一份文件）：

1. **參數 → CLI 入口**：解析 `--type <六值之一>`、`--format text|json`（預設 text）、受檢檔案路徑。不合法 → stderr 使用方式錯誤（含合法值清單）、exit 2，流程終止。
2. **type → 規則來源**：以固定映射 `<type> → templates/<type>.md` 定位模板（模板目錄預設以腳本自身位置回推 repo 根）。讀檔、掃描二級標題，得**必備章節有序清單**。模板讀不到 → exit 2。
3. **檔案路徑 → 章節檢查器**：讀受檢文件（讀不到 → exit 2），掃描其二級標題得集合；空檔案自然得空集合。
4. **比對**：缺漏清單 ＝ 必備清單中不存在於文件標題集合者，保持模板順序。
5. **結果 → 輸出器**：依 `--format` 輸出至 stdout；exit 0（無缺漏）或 1（有缺漏）。

## 5. 跨模組影響

- **`templates/`（MYL-4 產出物）**：唯讀依賴，不需對方配合修改。但自本設計定稿起，**模板的二級標題成為機器介面**：未來改模板二級標題（增、刪、改字）都會即時改變 lint 判定，且新增「含佔位文字的二級標題」會破壞 ADR-3 前提——模板維護者改動時應以 foundry-lint 對既有文件自測（此約束後續由 Scrum Master 評估是否入手冊，本單不擴scope）。
- **`docs/` 既有文件**：已抽驗 BRD.md／PRD.md（本功能自身文件）之二級標題與模板逐字一致，設計落地後可直接通過檢查，無需回改既有文件。
- 其他模組：無。

## 6. 風險與待驗證假設

| 風險 | 影響 | 驗證／緩解方式 |
| --- | --- | --- |
| 執行環境無 `python3`（≥3.9） | 工具完全無法執行 | Developer 開工第一步執行 `python3 --version` 驗證；mkdocs 已隱含 Python 環境，風險低 |
| 未來模板改版引入含佔位文字或可重複的二級標題 | 規則失真：要求文件逐字含佔位標題 | ADR-3 已載明此約束；模板改動時以 foundry-lint 對範例文件自測即可立即發現 |
| 受檢文件的圍欄程式碼區塊內含 `## ` 開頭的行（如 shell 註解） | 誤判為章節標題，漏報缺漏 | 掃描時追蹤圍欄狀態、跳過區塊內行（LLD 第 4 節），單元測試覆蓋此情境 |
