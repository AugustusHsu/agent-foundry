## 1. 背景與問題

Foundry 的流程鏈（需求 → 設計 → 工單 → 實作 → 審查 → 測試）靠 `templates/` 下六份文件模板交接；依 `skills/foundry-protocol/SKILL.md` 第 3 節，交接物不齊下一棒有權直接退回。但「文件是否符合模板必備章節」目前只能靠交接雙方肉眼逐節比對：撰寫者可能漏章節而不自知，審查者要逐份對照模板，缺漏往往在交接後才被發現，造成退回與返工。

foundry-lint 是一個小 CLI，自動檢查 BRD／PRD／HLD 等文件是否符合 foundry-protocol 模板的必備章節，讓「交接物齊不齊」在交棒前就能機器判定。本題目同時是 MYL-6 Pilot 的練手案：用自家規範當題目，完成後直接拿來守護後續流程。

## 4. 範圍

### 4.1 本次要做（In Scope）

- 一個 CLI 工具：讀取指定文件，對照 `templates/` 對應模板的必備章節，回報過／不過與缺漏章節。
- 檢查對象的全集為 `templates/` 下六份模板（brd／prd／hld／lld／review-report／test-plan）；本次實際涵蓋哪幾種文件類型，待使用者確認（見第 7 節）。

### 4.2 明確不做（Out of Scope）

- 內容品質的語意判斷（章節寫得好不好、是不是空話）——只判定結構，不判定內容。
- 自動修復或自動補章節。
- 模板本身的產生或維護（模板歸 MYL-4 產出物，foundry-lint 只讀取）。
- CI／git hook 整合（先做可手動執行的 CLI，整合留線索給未來單）。

## 5. 限制與假設

- **限制**：不引入需付費的外部服務；技術選型由 Tech Lead 於 HLD 決定，本文不指定。
- **假設**：`templates/` 六份模板是章節結構的唯一權威來源；模板章節若變動，lint 規則需同步更新（驗證方式：HLD 設計時確認規則來源與模板的同步機制）。

## 6. 優先序

- **必須有**：核心章節檢查——對單一文件判定必備章節是否齊備並列出缺漏（此為題目定義本身，已由使用者於 MYL-6 互動卡選定）。
- 其餘範圍項（涵蓋哪些文件類型、嚴格度分級、介面與輸出形式）的優先序，待第 7 節未決事項經互動卡確認後填入，不預設。

## 7. 未決事項

以下待使用者透過互動卡 `ask:MYL-16:lint-requirements:v1` 回答；全部確認前本文件不得交棒 Tech Lead：

- 要檢查哪些文件類型：六份全上，或先做子集？（影響第 4.1、6 節）
- 檢查規則的嚴格度／分級：只有缺章節＝不通過，還是分 error／warning 兩級？（影響第 4.1、6 節與 PRD 功能需求）
- CLI 的使用介面：文件類型如何指定（自動判別／參數指定／混合）？（影響 PRD 第 4 節）
- 輸出形式：純人類可讀文字＋exit code，還是另需機器可讀格式（JSON）？（影響 PRD 第 4 節）
