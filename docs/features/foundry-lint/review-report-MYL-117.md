### 3.2 新發現：分支基底已落後，合併時有一顆會**靜默壞掉**的衝突

不是瑕疵、不影響 Verdict，但**合併的人必須先知道**，否則會踩下去。

第 1 輪之後 main 前進了 21 顆 commit（MYL-128／129／130／131／133 五條線），
本分支動到的 10 個檔案裡**有 8 個 main 也動過**。實測 `git merge origin/main` ⇒
**5 個檔案衝突**：

1. **四處自檢名稱清單**（`.pre-commit-config.yaml`／`Makefile`／`CLAUDE.md`／`AGENTS.md`）——
   兩邊各加了一項（main 加 `模型路由宣告`、本單加 `上位單`），**解法是兩項都留**。
   注意這四處**兩種分隔符與括號形狀不同**：`Makefile` 那行沒有括號，其餘三處是
   `（…）`，新項要加在**右括號之內**。我第一次解錯（加到括號外）就被 `selfcheck-names`
   當成「錨點漂了」擋下——這道閘門是有效的。
2. **`tools/foundry-lint/foundry_lint.py`** —— ⚠️ **這一顆有陷阱**。衝突區是兩邊
   各自新增的一整塊（main 的 `model-routing-sync`、本單的 `check_issue_parent`），
   兩塊都要留；但衝突區**後面緊接著一行共用的 `    return res`**，它會歸屬給
   排在後面的那一塊。天真地「兩塊都保留」貼在一起，前面那塊就**沒有 return 了**——
   `check_model_routing_sync()` 回 `None`，而它是 `--selfcheck` 的一項。
   我實際踩了這一下：測試 **56 個 error**（`'NoneType' object has no attribute 'passed'`）。
   正解是**替前一塊補回自己的 `return res`**。

**合併後的狀態我已經驗過**（隔離 clone，`git clone --shared --no-hardlinks`，
另加一條 GitHub remote 讓 `mirror-recon` 真的跑得起來而不是跳過）：

```
python3 -m unittest discover tools/foundry-lint  → Ran 376 tests, OK
foundry-lint --selfcheck                         → 19 項全部通過
```

19 項含合併後才並存的 `model-routing-sync` 與 `issue-parent`，兩項互不干擾；
`issue-parent` 讀到「MYL-125 起 agent 開了 11 張，全部 135 張」，例外提示為空
（符合條文說的預期為空）。

## 4. 次要建議

1. **`test_I2xI3_只違反_I3` 的 docstring 有一句宣稱是假的，建議合併時順手改掉**
   （`test_foundry_lint.py:2638`，測試本體在 `:2634`）。那句寫「兩項的射程若哪天被合併成同一份，**這一列會變
   `(True, True)`**」——**不會**。`i2_i3()` 把射程判斷寫在測試自己身上
   （`if agent == self.PM else []`），所以射程是在 helper 裡假的、不是問來的。
   我把真正的射程過濾器改寬（`foundry_lint.py:3184` 的 `it.author_agent != pm_id`
   → `not it.author_agent`，＝ `I2` 改成與 `I3` 同射程）實測：
   **`IssueRuleCrossCheckTest` 整個 class 全綠、一列都沒紅**；要跑到整份測試才會被
   `test_pm_以外的人開的單不進_I2_射程` 抓到。
   ⇒ **覆蓋是有的（在別的測試裡），少的只是這句話的準確度**，所以列在次要建議而不是
   瑕疵。但它剛好是第 1 輪瑕疵 #2 的同一species——「留著一句假的覆蓋宣稱，比沒有測試
   更糟」——所以值得改。**只要改敘述，不要改測試**：那一列本身（驗射程差的結果）是對的，
   建議改成「射程差寫在 helper 裡；真正的射程過濾器由
   `test_pm_以外的人開的單不進_I2_射程` 守著」。
2. **`render_selfcheck_json()` 不輸出 `summary`**（`foundry_lint.py:3580`），
   而例外提示整個掛在 `summary` 上 ⇒ 走 `--json` 的消費端看不到它。
   本輪確認**目前沒有任何消費端**（repo 內唯一的 `--json` 是 `gh issue list --json`），
   所以不是活的破口，也**不建議現在改**。純粹是留一句：哪天有人拿 `--json` 接 CI，
   「被看見」這個保證在那條路上是不成立的。
3. **第 1 輪次要建議 #4 仍未有單接著**（每 run 跨單寫入上限 20 筆 → `known-drift` 的
   `L` 分類）。第 1 輪已註明不在射程、不代開單，本輪維持同一處置，但它到現在還是沒人接。
   **建議 Tech Lead 合併本單時一併回報 Product Manager**，否則它會跟著本單一起結案消失。
