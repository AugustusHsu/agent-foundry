**第五則我另外打穿過一次**，因為「兩端皆綠」在這個 repo 的標準下等同於
「永遠會通過的檢查」的嫌疑犯。做法是把實作突變成交付回報明說**不做**的那個過寬版
（`^[ \t]*(?:[-*+][ \t]+)?\*\*[^*]*違反：[^*]*\*\*`＝「粗體裡出現『違反：』就算」），
再單獨跑那一則：**FAIL，`30 != 29`**。它是真守門，不是裝飾。

所以這批突變不會因為 protocol 措辭漂掉而退化成 no-op 空轉——這是同類修正最常見的
失效方式，這裡已經被堵住。

## 4. 次要建議

1. **`# 行首容許縮排與清單項目符號`（`foundry_lint.py:242`）比實作寬。**
   實作只放行無序項目符號 `[-*+]`，但 markdown 的有序清單項目（`1. `／`1) `）同樣是
   清單項目，目前 `1. **違反：**⟨後果⟩` 仍會**靜默掉出覆蓋**——正是本單要消滅的那個
   失效形態。`> **違反：**`（blockquote）同理。
   兩條出路，擇一即可，重點是註解與實作講同一件事：
   - 補上：把項目符號那格改成 `(?:[-*+]|\d+[.)])[ \t]+`。**我先驗過才寫進來**：
     對現行 protocol 覆蓋數 28 → 28、兩個方向的集合差都是空（不多抓也不少抓），
     `1. **違反：**`／`1) **違反：**`／`` 12. **`O4` 違反：** `` 三種中，而 §7 現存的
     `5. **（可選）發一版精裝站**：…` 這類有序粗體散文**不中**（`：**` 前不是「違反」）。
   - 或把註解收窄成「無序清單項目符號」，把有序那半明記為刻意不收。
2. 兩段前綴限定語（`` **`O4`（本節矩陣）違反：** ``）同樣不算。這個**我不建議補**——
   它就是交付回報說的「開放組合」那條線，補了就開始往散文滑。列在這裡只是讓下一個人
   知道它是已知取捨、不是漏想。
