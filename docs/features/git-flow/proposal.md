## 1. Git flow 設計

### 1.1 分支策略：沿用「一單一分支」

現行 protocol 第 7 節的分支規則**不變**：

- 一單一分支，分支名 `<類型>/<工單編號>-<簡述>`。
- main 為唯一整合分支，不設 develop／release 長期分支——團隊產出以文件與腳本為主、
  無多版本並行需求，多層分支只會增加合併成本。
- 工單結案前分支收尾（合併＋刪除），規則同現行第 7 節。

### 1.2 合併觸發條件：維持審查制，不引入 PR

- **合併時點不變**：掛審查單的實作分支，在 Code Reviewer APPROVED 後合併回 main；
  純文件單由結案執行者自查後合併（現行 Pilot 卡點 #2、#3 規則）。
- **不引入 GitHub PR 作為合併閘門**。理由：審查職能已由 Code Reviewer 工單鏈承擔
  （交接包、Verdict、回寫留言都在 Paperclip 上），PR 只是同一審查的第二份表單，
  會造成兩份真相。待未來有多人／多 agent 同時寫 code 的真併發需求時再開單評估。
- 開始常規 push 後（見 1.3），**工單分支也可推上 origin** 作為工作中備份；
  合併後由收尾動作一併刪除遠端分支。

### 1.3 私有 repo 是否常規 push origin（✅ 已裁定：選項 A）

> 提案當下的未決事項，已於 2026-09-03 由使用者裁定**選項 A** 並執行完畢。
> 以下保留當時的三個選項與代價評估，作為裁定依據的紀錄。

提案當下的現況（**已過時**）：main 領先 origin **27 個 commit** 未推送。三個選項：

| 選項 | 內容 | 代價／風險 |
| --- | --- | --- |
| **A（建議）** | 核可本提案後立即補推現有 commit；之後**每次合併回 main 即 push origin**，工單分支也可隨時推送備份 | 遠端與本地即時一致、有異地備份、遠端 CI／Actions 變可用、公開鏡像觸發點可靠。風險極低：私有 repo、不對外 |
| B | 僅在**工單結案時** push 一次 | 備份粒度較粗；工作中變更仍只存在本機 |
| C | 維持現狀，不常規 push | 27+ commit 持續只存在本機，單點故障即全失；與選項 c 全自動發佈的方向矛盾 |

**建議 A**。核可本提案並選 A，即視為對「補推現有 commit ＋ 後續常規推送」的常設授權
（歸入下方 P1 級）。

### 1.4 文檔更新觸發點

- 凡是動到 `docs/handbook/` 的工單，**結案自檢**加一項：「是否需同步公開鏡像？」
  需要就在收尾時執行發佈（見 1.5）——這是 MYL-12 選項 (a) 的落實，
  寫進 protocol 第 7 節（草案見 3.）。
- `docs/features/`、`docs/pilot/`、`skills/` 等私有內容不觸發發佈。

### 1.5 發佈觸發點

- **觸發條件**：`docs/handbook/` 的變更**已合併進私有 main**（代表該單已走完
  審查／確認流程）。
- **執行者**：該工單的結案執行者，於分支收尾後執行 `bash scripts/publish-handbook.sh`。
- **授權**：歸入下方 P2 級——本提案核可後即為常設授權，不再逐次問（MYL-12 選項 c）。
- **證據**：工單留言附執行輸出（過濾清單、公開 repo commit、站台 URL）。

### 1.6 一個 workflow 還是兩個？（回覆 MYL-12 使用者提問）

**建議合併為一套「push 權限分級表」管理，不另立獨立的 push 審批 workflow。**

- push 審批的本質是「決策權矩陣的一列」：誰可拍板、憑什麼判準、留什麼證據——
  這正是 protocol 第 9 節既有的管理粒度，放進去即可，單獨成 workflow 會造成兩份真相。
- 手冊發佈流程（1.4／1.5）則是**引用**分級表的一個作業流程：它自己不定義權限，
  只在觸發點引用「P2 級可自動執行」。未來任何新增的自動化（例如私有 CI 部署）
  也一樣：流程歸流程、權限歸分級表，一處修訂全隊生效。

## 2. push 權限分級表（protocol 第 9 節增訂草案）

| 級別 | 動作範圍 | 拍板者 | 審查者與審查內容 | 證據要求 |
| --- | --- | --- | --- | --- |
| **P1 私有例行推送** | 私有 repo（現為 agent-foundry）：push 既有分支新 commit、推送工單分支、刪除**已合併**的遠端工單分支 | 執行者本人（本提案核可＝常設授權） | 無事前審查——內容已經該單既有審查鏈把關；Scrum Master 巡檢兜底 | 工單留言／交接包記明分支與 commit hash |
| **P2 既有公開管道發佈** | 使用者已核可建立的公開管道之**內容同步**：現為 `scripts/publish-handbook.sh`（推 foundry-handbook main ＋ gh-pages） | 執行者本人，須前提全數成立：(1) 來源變更已合併進私有 main；(2) 同步範圍僅限既定目錄（`docs/handbook/`）；(3) 私有連結過濾輸出檢查無異常 | 執行 agent 逐項自檢前提；Scrum Master 巡檢兜底 | 工單留言附：過濾清單輸出、公開 repo commit hash、站台 URL |
| **P3 使用者專屬** | 新開公開資源（public repo／網站／套件／網域）、擴大公開同步範圍（動 P2 的過濾規則或來源目錄）、force push／改遠端歷史、刪除遠端 repo 或未合併分支、任何涉費用的動作 | **使用者**，逐次發卡當下同意 | 發卡列明動作、影響、回退方式 | 互動卡核可紀錄 |

三個判例（對應本單 AC 2）：

| 動作 | 級別 | 由誰同意 |
| --- | --- | --- |
| 私有 repo push origin | P1 | 本提案核可後常設授權，執行者自行 |
| 公開鏡像 push（publish-handbook.sh） | P2 | 本提案核可後常設授權，前提成立時執行者自行 |
| 新開公開資源 | P3 | 使用者逐次同意，無常設授權 |

**護欄**：

- 級別判斷拿不準時，往上取級（P1↔P2 拿不準按 P2 的前提辦；疑似 P3 一律發卡）。
- P1／P2 推錯內容的補救（revert、強制覆蓋遠端）屬破壞性操作，回第 4 節 HITL 閘門，
  不得為了「趕快蓋掉」而自行 force push。
- 憑證失效、遠端拒絕等執行失敗不重試超過一次，轉 `blocked` 留言。
