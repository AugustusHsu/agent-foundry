# 7. 團隊有哪些固定 workflow？

> 本章把散在規範各節的「固定跑法」收攏成一份總覽：每條 workflow 一句話講清楚它是什麼、什麼情況會啟動、規則本體在哪一節。規則本體永遠以 [`skills/foundry-protocol/SKILL.md`](../../skills/foundry-protocol/SKILL.md) 為準；本章只做索引與簡介。

## 1. 主開發流程鏈

**一句話**：從你的一句話需求到結案的完整交棒順序——需求（Product Analyst）→ 設計（Tech Lead）→ 工單（Scrum Master）→ 實作（Developer）→ 審查（Code Reviewer）→ 測試（QA）。

- **觸發條件**：你對 CEO 提出需求（怎麼講見[第 2 章](02-commands.md)）。之後每一棒由前一棒的合格交接物觸發，交接物不齊，下一棒有權退回不開工。
- **權威章節**：[`foundry-protocol` 第 3 節（交接格式）](../../skills/foundry-protocol/SKILL.md)定義每一棒必附的交接物；第 2 節（狀態機）定義工單在各棒之間的狀態流轉。
- **手冊對應**：[第 3 章](03-workflow.md)用 Pilot 真實案例把整條鏈走了一遍。

## 2. 缺陷收容

**一句話**：發現缺陷時不是直接開新單，而是先找「成因工單」——最初該把這件事做對的那張單——再依判定表決定退回原單、改 AC 後退回、或開新單。

- **觸發條件**：測試失敗、行為不符預期、審查退件。
- **權威章節**：[`foundry-protocol` 第 5 節（缺陷收容判準）](../../skills/foundry-protocol/SKILL.md)——含完整判定表、「AC 寫錯只有 Scrum Master 有權改」、與總判準「能退回就不開新單」。
- **手冊對應**：[第 5 章](05-troubleshooting.md)有實際踩過的案例。

## 3. HITL 發卡

**一句話**：遇到六種閘門情況（未決事項未解、規格矛盾、要花錢、要對外發佈、破壞性操作、平台權限之外），agent 立即停止執行、發互動卡問你、把工單轉 `blocked` 等回覆。

- **觸發條件**：六種閘門任一成立；判斷口訣是「拿不準要不要問的時候，就是要問」。卡沒回，流程就停在那裡等你。
- **權威章節**：[`foundry-protocol` 第 4 節（HITL 閘門）](../../skills/foundry-protocol/SKILL.md)——含鐵律「絕不自作主張採用建議值」與發卡後的行為限制。
- **手冊對應**：[第 4 章](04-decision-points.md)逐一列出你會被問到的決策點與不同選擇的後果。

## 4. 模型分層與升級

**一句話**：每張工單用「足夠但不過度」的模型與思考程度執行——三層預設依「角色 × 工作類型」綁定，失敗到一定程度才逐級升，省下的預算留給真正難的工作。

- **觸發條件**：每張工單開工時依執行角色自動套用預設層級；跨模組介面或安全敏感範圍**直接用高層級、不等失敗**。
- **權威章節**：[`foundry-protocol` 第 8 節（模型與思考程度分層）](../../skills/foundry-protocol/SKILL.md)。

三層預設（MYL-12 討論、MYL-13 增訂）：

| 層級 | 模型／思考程度 | 預設適用 |
| --- | --- | --- |
| 高 | 當下可用的最高層級／最高思考程度（現為 Opus 級／`max`） | Tech Lead 的設計（HLD／LLD／ADR）、Code Reviewer 的審查、CEO 的裁決與規範修訂 |
| 中 | Opus 級／`high` | Developer 的實作、QA 的測試、Product Analyst 的需求 |
| 低 | Sonnet 級／`medium` | Scrum Master 的機械性流轉：狀態機維護、依模板拆單、巡檢兜底 |

升級規則（逐條可判定）：

1. **同一條 AC 連續失敗兩次 → 升一級思考程度**，並在工單留言記錄失敗證據與升級後層級。
2. **跨模組介面或安全敏感範圍 → 直接高層級**，不等失敗。
3. **升級後同一條 AC 仍失敗 → 轉 `blocked`**，等 Tech Lead 或你裁決，不得無限重試。

升級只影響該張工單，不回寫預設；同類工作反覆觸發升級，代表預設分層要修——走下面的[規範修訂](#5)，不在個案裡默默長期加碼。各層對應的具體模型代號以同步卡裁定為準（protocol 第 8 節附註），模型換代時開單重新裁定。

## 5. 規範修訂

**一句話**：規則本體（protocol、角色 skill）的任何修改都走「CEO 提案 → 你核可 → 改文件 → 重新匯入 skill」的固定路徑，不允許在個案裡默默偏離規範。

- **觸發條件**：現行規則不敷使用（判定表覆蓋不了、預設分層要修、組織結構要調、觸發加 PM 條件）；或平台設定與規範不一致需要同步。
- **權威章節**：[`foundry-protocol` 第 9 節（決策權矩陣）](../../skills/foundry-protocol/SKILL.md)——「規範修訂」的拍板路徑是 CEO 提案、你核可後生效；第 8、9 節的「權威來源與同步」定義規範與平台設定不一致時以規範為準、發起同步。
- **注意**：公司層 skill 的匯入／更新只有你能執行（平台限制，見 protocol 第 4 節閘門 6）——修訂核可後，agent 會發卡請你做最後的重新匯入。

## 6. 手冊發佈同步

**一句話**：`docs/handbook/` 是手冊的唯一真相；內容變更後執行 `scripts/publish-handbook.sh`，單向同步到公開鏡像 repo（`foundry-handbook`）並重建 GitHub Pages 站台，私有連結在同步時自動拆為純文字。

- **觸發條件**：手冊任何一章的內容或章節結構（nav）變更後。
- **權威章節**：腳本本體 `scripts/publish-handbook.sh`（MYL-8 建置，含過濾規則與部署步驟的註解）；push 權限依 [`foundry-protocol` 第 7 節「手冊發佈審查」與第 9 節分級表](../../skills/foundry-protocol/SKILL.md)——你在 MYL-23 給過 **P2 常設授權**：來源已合併進 main、範圍僅限手冊目錄、私有連結過濾無異常，三前提成立時執行者自檢後自行發佈；每次發佈前必須留下審查記錄（`docs/publish-reviews/`，MYL-24 證據閘門），沒有對應記錄腳本會拒跑。
- **手冊對應**：公開站網址與鏡像原則見公開站首頁的「公開鏡像」說明。

## 7. 機械層閘門

**一句話**：能用指令證明的事，就不要靠人記得——`foundry-lint` 會在 commit、PR、開審前自動擋下四類已經踩過的錯誤。

- **觸發條件**：每次 `git commit`（pre-commit hook）、每個 PR 與推上 main（GitHub Actions）、Code Reviewer 開審前的第一步。三個地方跑的是**同一組檢查**，所以 CI 紅燈一定能在本機重現。
- **擋什麼**（每一項都對應一個真實發生過的缺陷，不是預想的風險）：

  | 檢查 | 擋下的問題 |
  | --- | --- |
  | `entry-sync` | 兩份接手入口檔（`CLAUDE.md`／`AGENTS.md`）的共用正文被改了其中一份 |
  | `nav-sync` | 新增手冊章節時只改了一份 nav，導致公開站漏章 |
  | `anchors` | 手冊內部連結寫成中文字面錨點，點了不會跳轉 |
  | `rule-ids` | 引用了不存在的規則編號（例如把閘門寫成第九條，但閘門只到 `H6`） |

- **審查分三層**：Code Reviewer 開審時先跑機械層（上表＋測試＋分支檢查），**過不了直接退件**，不進入人工判斷。理由很簡單——判斷力是最貴的一層，不該花在機器能證明的事情上。機械層退件不寫瑕疵清單、不佔複審次數。
- **權威章節**：protocol 第 10 節與 `tools/foundry-lint/`。本機用 `make check` 可一次跑完。
- **這條 workflow 的設計原則**：若人工審查抓到一個「其實可以機械化」的缺陷，審查報告會建議把它加進自檢——**同一個缺陷不該被人工抓第二次**。

## 這對你有什麼影響

- 這七條都是**自動跑或依規則觸發**的：你日常只需要記得第 1 條的入口（對 CEO 說需求）和第 3 條的回卡（收件匣的互動卡要回）。
- 第 4、5 條平常不需要你介入；只有升級後仍失敗的 `blocked`、或規範修訂的核可，會以互動卡回到你手上。
- 第 6 條自 MYL-23／24 起走常設授權：三前提成立時 agent 自檢＋留審查記錄後自行發佈，你只在工單結案留言收摘要；要收回這個授權，走第 5 條的規範修訂。
- 第 7 條完全不需要你介入，它的價值是**讓某幾類錯誤不再有機會走到你面前**——過去手冊漏章、死連結這類問題是發佈之後才被發現的，現在在 commit 當下就被擋住。
