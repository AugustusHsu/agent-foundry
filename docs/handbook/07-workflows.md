## 1. 主開發流程鏈

**一句話**：從你的一句話需求到結案的完整交棒順序——需求（Product Analyst）→ 設計（Tech Lead）→ 工單（Scrum Master）→ 實作（Developer）→ 審查（Code Reviewer）→ 測試（QA）。

- **觸發條件**：你對 CEO 提出需求（怎麼講見[第 2 章](02-commands.md)）。之後每一棒由前一棒的合格交接物觸發，交接物不齊，下一棒有權退回不開工。
- **權威章節**：[`foundry-protocol` 第 3 節（交接格式）](../../skills/foundry-protocol/SKILL.md)定義每一棒必附的交接物；第 2 節（狀態機）定義工單在各棒之間的狀態流轉。
- **手冊對應**：[第 3 章](03-workflow.md)用 Pilot 真實案例把整條鏈走了一遍。

## 2. 缺陷收容

**一句話**：發現缺陷時不是直接開新單，而是先找「成因工單」——最初該把這件事做對的那張單——再依判定表決定退回原單、改 AC 後退回、或開新單。

- **觸發條件**：測試失敗、行為不符預期、審查退件。
- **權威章節**：[`foundry-protocol` 第 5 節（缺陷收容判準）](../../skills/foundry-protocol/SKILL.md)——含完整判定表、「AC 寫錯只有 Scrum Master 有權改」、與總判準「能退回就不開新單」。
- **手冊對應**：[第 5 章](05-troubleshooting.md)有實際踩過的案例。

## 3. HITL 發卡

**一句話**：遇到六種閘門情況（未決事項未解、規格矛盾、要花錢、要對外發佈、破壞性操作、平台權限之外），agent 立即停止執行、發互動卡問你、把工單轉 `blocked` 等回覆。

- **觸發條件**：六種閘門任一成立；判斷口訣是「拿不準要不要問的時候，就是要問」。卡沒回，流程就停在那裡等你。
- **權威章節**：[`foundry-protocol` 第 4 節（HITL 閘門）](../../skills/foundry-protocol/SKILL.md)——含鐵律「絕不自作主張採用建議值」與發卡後的行為限制。
- **手冊對應**：[第 4 章](04-decision-points.md)逐一列出你會被問到的決策點與不同選擇的後果。

## 4. 模型分層與升級

**一句話**：每張工單用「足夠但不過度」的模型與思考程度執行——三層預設依「角色 × 工作類型」綁定，失敗到一定程度才逐級升，省下的預算留給真正難的工作。

- **觸發條件**：每張工單開工時依執行角色自動套用預設層級；跨模組介面或安全敏感範圍**直接用高層級、不等失敗**。
- **權威章節**：[`foundry-protocol` 第 8 節（模型與思考程度分層）](../../skills/foundry-protocol/SKILL.md)。

三層預設（MYL-12 討論、MYL-13 增訂）：

| 層級 | 模型／思考程度 | 預設適用 |
| --- | --- | --- |
| 高 | 當下可用的最高層級／最高思考程度（現為 Opus 級／`max`） | Tech Lead 的設計（HLD／LLD／ADR）、Code Reviewer 的審查、CEO 的裁決與規範修訂 |
| 中 | Opus 級／`high` | Developer 的實作、QA 的測試、Product Analyst 的需求 |
| 低 | Sonnet 級／`medium` | Scrum Master 的機械性流轉：狀態機維護、依模板拆單、巡檢兜底 |

升級規則（逐條可判定）：

1. **同一條 AC 連續失敗兩次 → 升一級思考程度**，並在工單留言記錄失敗證據與升級後層級。
2. **跨模組介面或安全敏感範圍 → 直接高層級**，不等失敗。
3. **升級後同一條 AC 仍失敗 → 轉 `blocked`**，等 Tech Lead 或你裁決，不得無限重試。

升級只影響該張工單，不回寫預設；同類工作反覆觸發升級，代表預設分層要修——走下面的[規範修訂](#5)，不在個案裡默默長期加碼。各層對應的具體模型代號以同步卡裁定為準（protocol 第 8 節附註），模型換代時開單重新裁定。

> 這一條管的是**「用多強的模型」**；**「用哪一家的模型」**是另一條軸，見下面第 8 條。兩者互相獨立。

## 5. 規範修訂

**一句話**：規則本體（protocol、角色 skill）的任何修改都走「CEO 提案 → 你核可 → 改文件並 commit」的固定路徑，不允許在個案裡默默偏離規範。

- **觸發條件**：現行規則不敷使用（判定表覆蓋不了、預設分層要修、組織結構要調、觸發加 PM 條件）；或平台設定與規範不一致需要同步。
- **權威章節**：[`foundry-protocol` 第 9 節（決策權矩陣）](../../skills/foundry-protocol/SKILL.md)——「規範修訂」的拍板路徑是 CEO 提案、你核可後生效；第 8、9 節的「權威來源與同步」定義規範與平台設定不一致時以規範為準、發起同步。
- **注意**：修訂核可、改動 commit 進 repo 之後**就生效了，你不必做任何事**——skill 是參照式安裝，每次喚醒 agent 都直接讀 repo 當下的檔案。（早期手冊寫「須由你重新匯入」，那是誤診，已更正；見[第 5 章](05-troubleshooting.md)案例 5。）

## 6. 手冊發佈同步

**一句話**：`docs/handbook/` 是手冊的唯一真相，對外有**兩個閱讀面**——主閱讀面（wiki）在手冊變更合併進 main 後由 agent 自動同步；精裝站（版本化的 GitHub Pages）**只有你打版本 tag 時才發**。

| 閱讀面 | 什麼時候更新 | 誰按下去 |
| --- | --- | --- |
| **主閱讀面**：wiki | 手冊變更合併進 main 後，收尾時同步 | 執行 agent（P2 常設授權） |
| **精裝站**：版本化 Pages | 你打 `handbook-v<N>` tag 時，CI 自動建站 | **你**——打 tag 是 tag 發佈，屬你專屬 |

- **觸發條件**：主閱讀面＝手冊任何一章的內容或章節結構（nav）變更後；精裝站＝你決定「這一版可以定版了」的時候。
- **為什麼精裝站要用 tag**：這樣手冊才第一次有了「我讀的是哪一版規則」。站上同時留 `v1`、`v2`…與 `latest`，右上角有版本選擇器，舊版不會被新版蓋掉——你在工單裡引用「當時的規則」時，那一版還在。
- **權威章節**：[`foundry-protocol` 第 7 節「手冊發佈審查」與第 9 節分級表](../../skills/foundry-protocol/SKILL.md)——你在 MYL-23 給過 **P2 常設授權**：來源已合併進 main、範圍僅限手冊目錄、連結改寫與逐章比對無異常，三前提成立時執行者自檢後自行同步主閱讀面；每次發佈前必須留下審查記錄（`docs/publish-reviews/`，MYL-24 證據閘門），沒有對應記錄兩支腳本都會拒跑。
- **兩個開關在你手上**：`.foundry/config.yml` 的 `docs.primary` 決定主閱讀面是哪一個；`docs.mirror_site.enabled` 決定要不要有精裝站——**關掉之後就算打了 tag 也不會發佈**。
- **打 tag 前要先解鎖**：repo 上有一條 `handbook-version-tags` 規則擋住 `handbook-v*` 的建立，擋的是**所有人、包含你自己**（見[第 4 章](04-decision-points.md)）。Settings → Rules → Rulesets 切 Disabled → 推 tag → 切回 Active。它換到的是**防誤推＋留痕**，不是「只有你能打 tag」——這個 repo 分不出誰在推，所以規則文字上這條仍算自律。附帶效果：已發佈的 tag 就算被刪掉也**建不回同一個名字**，除非先關掉這條規則。
- **發出去的版本不重打**：`v1` 上站之後，那個版本號的內容就定了。想改就發下一版（`handbook-v2`），**別把 `handbook-v1` 刪掉重打**——CI 會擋下來要你 bump，因為覆蓋掉的是別人引用得到的那一版，而且覆蓋不留痕跡。站台設定改過、想用同一版重建一次站，走 GitHub Actions 頁面的手動觸發（`workflow_dispatch`）輸入原本那個 tag，那條路是通的。
- **手冊對應**：站台網址與投影原則見站台首頁的「本站是機械投影」說明。

## 7. 機械層閘門

**一句話**：能用指令證明的事，就不要靠人記得——`foundry-lint` 會在 commit、PR、開審前自動擋下四類已經踩過的錯誤。

- **觸發條件**：每次 `git commit`（pre-commit hook）、每個 PR 與推上 main（GitHub Actions）、Code Reviewer 開審前的第一步。三個地方跑的是**同一組檢查**，所以 CI 紅燈一定能在本機重現。
- **擋什麼**（每一項都對應一個真實發生過的缺陷，不是預想的風險）：

  | 檢查 | 擋下的問題 |
  | --- | --- |
  | `entry-sync` | 兩份接手入口檔（`CLAUDE.md`／`AGENTS.md`）的共用正文被改了其中一份 |
  | `nav-sync` | 新增手冊章節時忘了改 nav，或有人又在腳本裡手寫第二份 nav（兩者都會讓對外站漏章） |
  | `anchors` | 手冊內部連結寫成中文字面錨點，點了不會跳轉 |
  | `rule-ids` | 引用了不存在的規則編號（例如把閘門寫成第九條，但閘門只到 `H6`） |

- **審查分三層**：Code Reviewer 開審時先跑機械層（上表＋測試＋分支檢查），**過不了直接退件**，不進入人工判斷。理由很簡單——判斷力是最貴的一層，不該花在機器能證明的事情上。機械層退件不寫瑕疵清單、不佔複審次數。
- **權威章節**：protocol 第 10 節與 `tools/foundry-lint/`。本機用 `make check` 可一次跑完。
- **這條 workflow 的設計原則**：若人工審查抓到一個「其實可以機械化」的缺陷，審查報告會建議把它加進自檢——**同一個缺陷不該被人工抓第二次**。

## 8. 模型供應商路由

**一句話**：管的是「哪一家的模型在跑這個角色」——目的是**觀點互補**：讓寫 code 的和審 code 的來自不同服務商，用第二種視角覆蓋第一種的盲點。

- **觸發條件**：① 某家額度耗盡、② 你想改哪個角色用哪一家、③ 裝了新的 CLI 或某家不再用。
- **權威章節**：[`foundry-protocol` 第 8 節「供應商維度」](../../skills/foundry-protocol/SKILL.md)（`M4`～`M6`）；流程細節在 `skills/foundry-model-routing/SKILL.md`。

三條規則：

| 規則 | 內容 |
| --- | --- |
| `M4` | **實作與審查不得同一家**。可用供應商 ≥2 且已啟用路由時生效；只有一家可用時本條不適用。 |
| `M5` | **額度耗盡時：停下、發卡、不自行降級。** 不重試、不偷換模型續跑——CLI 的 fallback 旗標對「額度用盡」無效，這是實測過的。 |
| `M6` | **換供應商一定要問你。** workflow 只負責盤點、產方案、發卡、執行、驗證，**不負責決定**，也不得先改再問。 |

第一步是機械盤點，不靠 agent 憑印象回答：

```bash
python3 tools/model-routing/probe_providers.py
```

它只看兩件可驗證的事——CLI 在不在、憑證檔在不在——輸出「可用／已安裝未登入／登入狀態不明／未安裝」。
**「設定欄位填得下某一家」不等於「那一家能用」**：平台的欄位枚舉列了七、八家，實機當時只有兩家真的裝了。

- **目前狀態：能力就位，開關沒開。** 你在 MYL-36 裁定「先不實際改任何 agent 設定，提供這樣的功能即可」——
  所以盤點、規則、workflow、設定欄位都做好了，但 7 個 agent 仍全部在同一家。
  **這是你的決定，不是待修的漏洞**；要啟用時說一聲，或由 agent 依 `M6` 發卡問你。

## 這對你有什麼影響

- 這八條都是**自動跑或依規則觸發**的：你日常只需要記得第 1 條的入口（對 CEO 說需求）和第 3 條的回卡（收件匣的互動卡要回）。
- 第 4、5 條平常不需要你介入；只有升級後仍失敗的 `blocked`、或規範修訂的核可，會以互動卡回到你手上。
- 第 6 條自 MYL-23／24 起走常設授權：三前提成立時 agent 自檢＋留審查記錄後自行同步主閱讀面，你只在工單結案留言收摘要；要收回這個授權，走第 5 條的規範修訂。**但精裝站發版例外**——那要你打 tag，沒有常設授權（MYL-55）。
- 第 7 條完全不需要你介入，它的價值是**讓某幾類錯誤不再有機會走到你面前**——過去手冊漏章、死連結這類問題是發佈之後才被發現的，現在在 commit 當下就被擋住。
