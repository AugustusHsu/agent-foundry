# 2. 我該下什麼指令？

## 丟給誰

**丟給 CEO。** CEO 是你的對口，負責把需求轉給 Product Analyst 開需求單；你不需要自己判斷該找哪個角色、也不需要自己開工單。

直接找特定角色（例如直接叫 Developer 寫程式）會被規範擋回：foundry-protocol 規定設計文件必須先於工單、工單必須先於實作，跳過前面的棒次，接單的 agent 有權退回。

## 第一句話怎麼講

一句話講清楚「做什麼」，再附上三件資訊——這三件正是 Product Analyst 訪談卡一定會問的（見其角色 skill「先問清楚再寫」），先附上可以省一輪往返：

1. **解決誰的什麼問題**
2. **現在怎麼做、痛在哪**
3. **做到什麼程度算成功**

### 可直接複製的句型

```
幫我做「〔功能名稱〕」：〔一句話說明它做什麼〕。

- 解決的問題：〔誰〕在〔什麼情境〕遇到〔什麼痛〕。
- 現況：目前是〔怎麼做的〕，痛點在〔哪裡〕。
- 成功標準：〔做到什麼程度算成功，最好可驗證〕。
```

### 實際範例（Pilot 的 foundry-lint，回填成主動提出的寫法）

```
幫我做「foundry-lint」：一個檢查文件是否符合 foundry-protocol 模板必備章節的小 CLI。

- 解決的問題：我們的 BRD／PRD／HLD 等文件靠人工核對模板章節，漏了沒人發現。
- 現況：審查時肉眼比對 templates/ 的骨架，費時且不穩定。
- 成功標準：對 docs/features/ 下的文件跑一個指令，缺必備章節就報出來並以 exit code 表示不通過。
```

Pilot 中這個題目實際是透過選題互動卡選定的（`ask:MYL-6:pilot-topic:v1`），其後四項行為取捨（檢查範圍、嚴格度、`--type` 指定、輸出格式）由需求卡確認（`ask:MYL-16:lint-requirements:v1`）——你第一句話沒講到的細節，Product Analyst 會用卡片補問，不會自己猜（protocol 第 4 節鐵律：不自作主張採用建議值）。

## 附什麼

- **有現成素材就給路徑**：相關文件、既有程式碼、參考範例的 repo 路徑。工單 Inputs 要求每項素材「實際可存取」，你給的路徑會被逐項打開驗證。
- **有硬性限制講明**：deadline、技術限制、不想動到的東西——這些會進 BRD 的範圍與 Out of Scope。
- **沒想清楚的就說沒想清楚**：規範要求未決事項誠實列出、發卡來問；你不需要假裝已有完整規格。

## 講完之後會發生什麼

CEO 把需求轉給 Product Analyst 開需求單，接著你會收到訪談卡→定稿確認卡，之後流程照[第 3 章](03-workflow.md)跑。你被問到的每個點都列在[第 4 章](04-decision-points.md)。

## 其他常見指令情境

| 你想做的事 | 怎麼講 | 會發生什麼 |
| --- | --- | --- |
| 回報 bug | 對 CEO 描述：重現步驟／預期／實際（三段式） | 依 protocol 第 5 節找成因工單：實作沒達成 AC → 退回原單；AC 本身錯 → Scrum Master 改 AC 後退回；需求變了 → 開新單。 |
| 加需求、改需求 | 對 CEO 講新需求，指明影響哪個功能 | 走「開新單」：新單走完整四段骨架，不夾進舊單。Product Analyst 會把加範圍的代價擺給你選。 |
| 改團隊規範 | 直接說要改 `foundry-protocol` 或某角色 skill 的哪條 | 修正回寫 repo 並 commit 後**即刻生效**，你不必做任何事——skill 是參照式安裝，每次喚醒 agent 都直接讀 repo 當下的檔案。（早期手冊寫「須由你重新匯入」，那是誤診，已更正；見[第 5 章](05-troubleshooting.md)案例 5。） |
| 更新使用手冊（`docs/handbook/`） | 對 CEO 說要改哪章、改什麼 | 修訂合併進 main 後，執行 agent 自己做發佈審查（寫審查記錄→跑 `scripts/publish-handbook.sh`），公開站直接更新，**不會再問你一次**——這是你在 push 分級表裡給的 P2 常設授權。結案留言會附審查記錄與站台 URL。（四個步驟見[第 3 章](03-workflow.md)「第 7 段：結案」） |
| 催進度／問狀態 | 問 CEO 某單現在卡在哪 | 依留言與狀態機回報；若卡在等你回卡，會請你回卡（見[第 5 章](05-troubleshooting.md)）。 |
