# 4. 我要在哪幾個點做決定？

你被問的方式只有兩種，都出現在 Paperclip 收件匣：

- **問答卡（ask_user_questions）**：單選／多選＋自由輸入，用在「有多個選項要你挑」。
- **確認卡（request_confirmation）**：核可／退回二擇一，用在「東西做好了，要你點頭才往下走」。

共通規則：**卡未回覆前，agent 只能做不受該問題影響的其他工作，不得先斬後奏**（protocol 第 4 節）。所以「不回卡」的後果永遠一樣——該條流程停在原地。

## 一次功能開發的固定決策點

Pilot 全程你被問了 7 次。前 6 個是每次做新功能都會重複出現的固定閘門，第 7 個只在改規範時出現。

### 決策點 1：做什麼題目

- **什麼時候**：流程起點，任何階段開跑之前。
- **問題長什麼樣**：問答卡列出候選題目（含你自帶題目的自由輸入欄）。Pilot 實例：`ask:MYL-6:pilot-topic:v1`，三提案選一，使用者選了 foundry-lint。
- **選擇的後果**：選定的題目就是整條流程接下來服務的對象；日常使用你直接丟題目（見[第 2 章](02-commands.md)），這張卡可能不出現。

### 決策點 2：需求取捨

- **什麼時候**：需求階段，BRD／PRD 起草後、定稿前。
- **問題長什麼樣**：問答卡一次問 3–5 題行為邊界的取捨。Pilot 實例：`ask:MYL-16:lint-requirements:v1` 問了四題——檢查範圍（六份模板全上 vs 部分）、嚴格度（單級 vs 分級）、文件類型（`--type` 明確指定 vs 自動推斷）、輸出格式（純文字 vs 加 JSON）。
- **選擇的後果**：你的每個選擇直接寫進 PRD 成為功能行為。選項都不滿意就用自由輸入改寫；**不答，需求單停在這裡**——protocol 禁止 agent 用「合理假設」代替你的答案。

### 決策點 3：需求定稿核可

- **什麼時候**：需求階段收尾，交接設計之前。
- **問題長什麼樣**：確認卡，附 BRD／PRD 定稿內容與 commit。Pilot 實例：`confirmation:MYL-16:prd-final:ac0c180`。
- **選擇的後果**：**核可**＝這份文件成為後續所有階段的最高依據（文檔權威階序：設計文件 > 工單 AC > 對話），之後想改要走變更流程。**退回**＝Product Analyst 依你的理由改完再送一輪。

### 決策點 4：階段交接確認

- **什麼時候**：需求→設計、設計→拆單，各階段收尾交棒時。
- **問題長什麼樣**：確認卡，附交接包內容（文件路徑＋已確認決策清單）。Pilot 實例：`confirmation:MYL-16:handoff-techlead:ac0c180`、`confirmation:MYL-17:handoff-sm:76f3089`。
- **選擇的後果**：**核可**＝上一單結案、下一棒開工（核可設計交接同時代表 HLD／LLD 及其 ADR 技術選型定稿）。**退回**＝上一棒補齊再送。
- 註：Pilot 期間每段交接都過你的目；未來若要減少確認次數（例如 agent 間交接自動放行），改 protocol 第 4 節即可——這是 MYL-13／14 決策權矩陣要處理的題目。

### 決策點 5：實作交付核可

- **什麼時候**：實作完成，進入審查之前。
- **問題長什麼樣**：確認卡，附三段式交付回報（AC 逐條對應／風險警告／驗證建議）與分支收尾方式。Pilot 實例：`confirmation:MYL-19:delivery:1451c4f`。
- **選擇的後果**：**核可**＝同意交付進入審查——**注意，這不等於合併授權**：掛有審查單的分支要等審查 APPROVED 才合 main（卡點 #3 的教訓，已入規範）。**退回**＝Developer 依你的理由修正。
- 其後的審查（MYL-20）、測試（MYL-21）是 agent 對 agent 交接，預設不再問你。

### 決策點 6：觸發式閘門（不定時，遇到才問）

以下五種情況任一出現，執行中的 agent 會立刻停手、發卡問你、把工單轉 `blocked`（protocol 第 4 節 HITL 閘門）：

| 觸發 | 你會被問什麼 | 不同選擇的後果 |
| --- | --- | --- |
| 未決事項未解 | 這個開放問題你要選哪個答案 | 你的答案寫回文件後才開工；不答就不開工。 |
| 規格矛盾（文件、AC、對話打架） | 兩邊說法並列，你裁定聽誰的 | 裁定後由負責角色先改文件再繼續；agent 無權自行判定「照理說誰對」。 |
| 要花錢 | 這筆費用（金額不論大小）花不花 | 同意才執行；沒有「反正很便宜」的豁免。 |
| 要對外發佈 | 這個離開私有環境的動作（開 public repo、發佈、對外訊息）做不做 | 同意才執行。 |
| 破壞性操作 | 刪資料、覆寫成果、改 git 歷史、動生產環境，做不做 | 同意才執行；且執行前要先在隔離環境驗證機制。 |

另有一條鐵律讓你被問的頻率高於直覺：文件或對話裡的「建議用 X」「預設可以是 Y」都是**待確認選項，不是決定**——agent 會發卡列出選項與代價等你選定，不會因為「建議看起來很合理」就直接採用。

### 決策點 7：只有你能做的平台動作

- **什麼時候**：需要更新公司層 skill（例如流程規範修正後重新匯入）或變更公司設定時。
- **問題長什麼樣**：確認卡，寫明請你在 Paperclip 介面執行什麼動作。Pilot 實例：`confirmation:MYL-6:skill-reimport:<commit>`——規範修正回寫 repo 後，請你重新匯入 `foundry-protocol`。
- **為什麼是你**：平台不變式規定公司層 skill 的寫入只有使用者主體能做，agent 呼叫一律 403 `skill_actor_restricted`（卡點 #5）。
- **選擇的後果**：你執行並回卡＝依賴它的工單解卡；**不執行，工單會一直掛著等**——agent 被規範禁止空轉重試。

## 一句話總結

一次功能開發，你的必答題就是：**選題（或自己出題）→ 需求取捨 → 需求定稿 → 設計定稿 → 交付核可**，共約 5 張卡；其餘都是遇到錢、對外、破壞性、矛盾、平台權限時的觸發式追問。收件匣清空，流程就不會因你而停。
