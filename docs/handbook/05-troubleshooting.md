# 5. 故障排除

流程卡住時的通用三步，加上 Pilot 實際踩過的六個卡點案例（完整記錄見 [`docs/pilot/pilot-log.md`](../pilot/pilot-log.md) 第二節）。

## 通用診斷三步

### 第 1 步：看工單狀態與留言

所有交接、阻塞原因、審查結果都規定寫在**工單留言**（不在私下對話），所以看留言就能還原現場。`blocked` 的單必附三件事：阻塞原因、解除者是誰、對方做什麼就能解——沒寫解除路徑的 `blocked` 本身就是不合格，可以直接要求補。

### 第 2 步：判斷卡的類型

| 你看到的 | 多半是 | 怎麼推 |
| --- | --- | --- |
| 收件匣有未回的問答卡／確認卡 | **在等你**（最常見） | 回卡。這是唯一設計成「等使用者」的停點。 |
| `blockedByIssueIds` 掛著未完成的前置單 | 在等前置單 | 去看前置單卡在哪，遞迴用同一套診斷。 |
| 留言說 Inputs 某項打不開 | 素材不可存取 | 補路徑／合併分支／給權限，然後留言通知接單者。 |
| `in_progress` 很久沒動靜也沒留言 | agent 停擺或忘了回報 | 對 CEO 問該單狀態；要求依狀態機補留言或轉正確狀態。 |
| 留言出現兩份規範互相矛盾 | 規格矛盾 | 依文檔權威階序（設計文件 > 工單 AC > 對話）發卡裁定，裁定後**先改文件再繼續**。 |

### 第 3 步：推完把證據留下

每次人工介入（合分支、改路徑、裁定矛盾）都要在工單留言記一筆做了什麼、為什麼——Pilot 的規矩是「事件發生當下就記，不事後補寫」，這讓下一次同樣的卡有案例可查。

## Pilot 實際踩過的六個卡點

每個案例都含「症狀 → 原因 → 當下怎麼解 → 現在的規範」。再遇到同類症狀，先對照這裡。

### 案例 1：兩份規範對同一行為給出相反指示

- **症狀**：agent 停下來問「commit 到底要不要先徵求同意」——protocol 說要，全域 CLAUDE.md（MYL-10 暫行放寬）說不用。
- **原因**：放寬只改了一處，兩份規範沒同步。
- **當下怎麼解**：依權威階序由使用者即時指示優先，先照放寬條款走。
- **現在的規範**：protocol 第 7 節已加註放寬條款並互相引用；**恢復嚴格模式時兩處一起改回，不得只改一處**。改任何規範時檢查有沒有第二處寫著同一件事。

### 案例 2：工單 Inputs 在 main 上打不開

- **症狀**：開單時引用 `templates/brd.md`，接單者確認 Inputs 發現 main 上沒這個檔。
- **原因**：產出該檔案的工單（MYL-4）結案時分支沒合入 main——檔案存在，但只在孤兒分支上。
- **當下怎麼解**：把分支 fast-forward 合入 main（非破壞性），解除阻塞。
- **現在的規範**：不經 Code Reviewer 的工單（如純文件單），分支收尾由結案前最後執行者自查、Scrum Master 巡檢兜底；結案留言必寫「分支已合併」或保留原因。**遇到「檔案應該存在卻打不開」，先 `git branch -a` 查是不是在未合併分支上。**

### 案例 3：先合併、後審查，順序倒置

- **症狀**：審查單開審時發現分支已合入 main，「審查通過才合併」變成「對已合入的 commit 做核驗」。
- **原因**：使用者確認卡的「核可」被理解成含合併授權，Developer 核可後就合了。
- **當下怎麼解**：審查照做，報告開頭註明是對已合入 commit 的核驗（例外程序就地追認）。
- **現在的規範**：掛有審查單的分支一律 APPROVED 後才合併；確認卡核可＝同意進入審查，不等於合併授權。**已經倒置的不必回退**——改為核驗模式並在報告註明即可。

### 案例 4：把工單掛 `blocked` 時整筆 PATCH 失敗

- **症狀**：API 回 `Agents may only name themselves as an unblock owner`，且 status、`blockedByIssueIds` 全都沒寫入。
- **原因**：`unblockDescriptor.owner` 依規範直覺填了「解除者」（別的 agent），但平台限制 owner 只能填自己；錯一個欄位整筆不生效。
- **當下怎麼解**：owner 改填自己、重送整筆 PATCH。
- **現在的規範**：指望其他 agent 解鎖時，把對方的工單掛進 `blockedByIssueIds` 作一級 blocker，owner 一律填自己，「解除者是誰」寫留言。**PATCH 失敗時當作整筆都沒寫入，修正後全部重送。**

### 案例 5：agent 更新 skill 一律 403

- **症狀**：規範修正回寫 repo 後，agent 呼叫 skill 更新／匯入 API 連續回 403 `skill_actor_restricted`。
- **原因**：平台不變式——公司層 skill 的寫入只有使用者主體能做。這不是壞掉，重試幾次都一樣。
- **當下怎麼解**：停止重試，發確認卡請使用者在 Paperclip 介面重新匯入，工單轉 `in_review` 等卡。
- **現在的規範**：HITL 閘門第 6 條——平台權限之外的動作一律發卡請使用者執行；開工單 AC 時不得把此類動作寫成 agent 交付項。**看到 `skill_actor_restricted`，答案永遠是「請使用者做」。**

### 案例 6：交付物只存在工單留言，repo 裡沒有

- **症狀**：結案核對 Outputs 時發現審查報告只貼在留言，`docs/features/<模組>/` 下沒檔案。
- **原因**：角色 skill 寫「報告貼工單留言」，工單 Outputs 卻要求進 repo——兩層規範對交付位置定義不一致。
- **當下怎麼解**：把留言逐字轉錄成 repo 檔案（附轉錄說明，內容不改動）。
- **現在的規範**：審查報告貼留言**並**同步 commit 進 repo；留言給流程用，repo 檔案才是正式交付物。**結案核對一律以 repo 內容為準，不接受「留言裡有」。**

## 最後手段

診斷三步走完還是不知道卡在哪：直接問 CEO「MYL-x 現在卡在哪、要誰做什麼才能動」。CEO 依規範必須給出可判定的答案（阻塞原因＋解除路徑），給不出來就是流程本身有洞——照 Pilot 的做法把它記成新卡點，修規範，讓下一次不再卡。
